# FS-106 — Sound Design Techniques

| Field | Content |
|---|---|
| **Feature ID** | `FS-106` / `FEAT-1060` |
| **Title** | Sound Design Techniques (arpeggio, vibrato, portamento, duty-cycle variation) |
| **Purpose** | Give the three pitched channels (pulse A, pulse B, wave) richer, more chiptune-idiomatic timbral behavior — implying chords on a single channel (arpeggio), adding expressive pitch motion (vibrato, portamento), and varying pulse timbre (duty cycle) — per `R216`'s concrete, cited technique survey, without adding a new input control or new PRNG source. |
| **Scope** | All 3 pitched channels' note-onset and per-frame register-write behavior. Noise channel (percussion) explicitly out of scope — `FR-1170` already traces its existing behavior as satisfying R216's percussion-synthesis convention; nothing changes there. |
| **Requirements Implemented** | FR-1130 (arpeggio), FR-1140 (vibrato), FR-1150 (portamento), FR-1160 (duty-cycle variation), FR-1170 (percussion trace, no new behavior), NFR-1040 (ROM/WRAM budget), NFR-1050 (per-frame timing budget) |
| **User Workflows** | 1. Listener boots the ROM (or presses Select) → hears the existing generation, now with audibly richer per-note character: arpeggiated chords on pulse channels, subtle pitch wobble, glides between notes, and (at least) one pulse channel's timbre varying note to note. No new button — the effects are always-on, layered onto every existing generation/steering/reset workflow (`FS-100`-`FS-103`'s workflows are unchanged, not superseded). 2. Developer/coding agent extending a fourth technique later reads this spec's Module Responsibilities to find where each effect lives. |
| **System Behaviour** | **Arpeggio** (FR-1130): on note-onset, instead of writing one frequency and holding it for the note's full duration, the channel's frequency register is rewritten every few frames (a fast sub-tick, faster than the note's own onset cadence) cycling through 2-3 precomputed scale-degree offsets from the current root (e.g. root, +2 scale steps, +4 scale steps — a triad-like shape within the active scale) — for that note's full duration, then the next onset event picks a new root and the cycle restarts. **Vibrato** (FR-1140): every frame (or a fixed small number of frames), a small signed offset from a short precomputed table is added to the currently-held frequency value before it's written to the frequency register — the offset table's phase advances every write and wraps; `CUR_DEGREE_*`/dissonance-scoring state is unaffected (computed from the *base* note, per FR-1140's explicit requirement). **Portamento** (FR-1150): on a note-onset where the new degree differs from the previous one, instead of writing the new frequency immediately, the engine steps the frequency register from the old value toward the new value over a fixed small number of frames (a glide), reaching the new value by end of glide; if the note repeats the same degree, no glide is needed (already at target). **Duty cycle** (FR-1160): pulse A's `NR11` duty bits (currently fixed `0x80`, 50%) vary across onsets — e.g. degree-linked (a small lookup by `CUR_DEGREE_PA mod 4` into the 4 duty-cycle options) rather than a second random source, keeping `NFR-1040`'s "no new PRNG" implicit constraint (R213's existing seed model stays the sole randomness source). Edge case: arpeggio + vibrato + portamento all touch the same frequency register in the same note's lifetime — order of operations is: portamento (if gliding) determines the *base* frequency this frame, arpeggio's sub-tick cycling (if mid-note) selects *which* of the 2-3 chord frequencies is the base for this sub-tick, vibrato's offset is added last, immediately before the register write. Only one write per channel per frame either way — no double-writing risk. |
| **Module Responsibilities** | All four effects live in `music_engine.py`, inside/adjacent to the existing shared `_emit_channel_gen` routine (GDS-03 §1's "one job per file" — generation, including its timbral variation, stays the engine module's job; no new module). `build_rom.py` gains no new responsibility beyond emitting whatever new small data tables (arpeggio intervals, vibrato offsets) `music_engine.py` defines, same pattern as every existing preset table. `input_map.py`/`visuals.py` are unaffected — no new control, no new visualizer signal. |
| **Interfaces Used** | The existing `CHANNELS`-list-driven parameterization of `_emit_channel_gen` (now formally documented — [GDS-09 §1](../architecture/09-interface-specification.md) records the `CHANNELS`-driven parameterization as part of `music_engine.py`'s real public surface, so this feature extends a specified contract rather than an unwritten one). |
| **Data Model Changes** | New WRAM (against GDS-07, which does not yet reserve these — a genuine data-model addition, to be reflected in GDS-07 by whichever package implements this, per that document's own "live doc, corrected in place" discipline): one small sub-tick/phase counter per pitched channel (arpeggio+vibrato can likely share one counter per channel, or use two — an implementation-package-level sizing decision, not fixed here) and one glide-remaining counter per pitched channel (portamento). New ROM-resident data: an arpeggio-interval table (2-3 entries), a vibrato-offset table (small, e.g. 4-8 entries), a duty-cycle-by-degree lookup (4 entries, reusing existing `SCALE_IDX`-independent degree data). |
| **State Changes** | No new engine *state machine* — arpeggio/vibrato/portamento are per-frame *modulations* of the existing note-onset/note-timer state machine (GDS-01's loop), not a new state. Select-reset (`FR-1070`) must additionally zero the new sub-tick/phase/glide counters, same as every existing per-channel field `IP-0005` already audited `init_engine` for completeness against. |
| **Error Handling** | No new failure mode — these are bounded, always-computable modulations (table lookups + bounded counters), no new external input, no new randomness source to fail. |
| **Performance Considerations** | NFR-1050: the added per-frame work is a small, bounded number of extra table lookups/additions per pitched channel per frame (arpeggio's sub-tick check, vibrato's offset add, portamento's glide-step) — verified the same way NFR-1010 already is, via extended headless stress runs, not static cycle analysis (`R101`'s "no gap yet" conclusion). |
| **Integrity Considerations** | None — no save data, no checksums beyond the existing header (`NFR-1000`, unaffected). Determinism: arpeggio/vibrato/duty-cycle tables are fixed ROM data (deterministic); portamento's glide is a deterministic function of old/new frequency and glide-frame-count — none of this introduces new non-determinism beyond what the existing `DIV`-seeded LFSR (`R213`, `IP-0007`) already does. |
| **Acceptance Criteria** | (1) With arpeggio active, a pitched channel's frequency-register-write pattern shows at least 2 distinct frequency values within a single note's duration (not just at onset), each corresponding to a scale-degree offset from the note's root. (2) With vibrato active, a channel's written frequency oscillates in a small bounded range around its base value across consecutive frames, while `CUR_DEGREE_*` (the dissonance-scoring input) stays constant for that note's duration. (3) With portamento active, on a degree-changing onset, the written frequency sequence between the old and new note spans more than one frame and each written value lies between the old and new frequency (monotonic toward the target). (4) Pulse A's `NR11` duty bits take at least 2 distinct values across a sustained run. (5) All existing `test_rom.py` suites (T1-T10) remain green — no regression. |
| **Verification Plan** | Test — a new `test_rom.py` suite (T11, or appended to an existing one at the implementing package's discretion) drives a sustained run and asserts on the WRAM-mirrored state each acceptance criterion needs (frequency/duty values aren't independently WRAM-mirrored today for pulse A/B — the implementing package must decide whether to add a WRAM scratch mirror for test visibility, since `NR13`/`NR14`/`NR11` are write-only on real hardware/PyBoy per `R108`/`VR-0001`'s own precedent, or to verify via `run-driftune`'s sound-register read capability instead; named as an Open Question below since it's a real implementation-package-level decision, not fixed here). |
| **Dependencies** | `FEAT-1000`/`IP-0001`-`IP-0003` (the `_emit_channel_gen`/`CHANNELS` machinery this feature extends) — all already `VERIFIED`. No dependency on `IP-9010`/`IP-9020` (the still-gated remediation packages) or `BL-0020`'s `ADS-100` (combinable schemes) — those are independent, unrelated threads. |
| **Risks** | ROM budget (bounded per `NFR-1040`, but not yet measured against actual headroom — the implementing package should confirm). Audible-quality risk: like `BL-0021`'s palette-luminance finding, whether these effects sound good together (all four active on all 3 channels at once could plausibly sound cluttered) is a judgment call for `09-content-review`/listening, not resolvable at the spec stage — flagged so that review knows to specifically listen for it. Interaction risk: arpeggio+vibrato+portamento's combined per-note register-write logic (System Behaviour's "order of operations" note) is the single most implementation-risk-bearing part of this spec — recommend the implementing package build and test one effect at a time (arpeggio first, per R216's own "highest-value" ranking) rather than all four simultaneously. |
| **Open Questions** | (1) Should the implementing package split this into multiple `IP-xxxx` packages (one per effect) or one combined package? `07-implementation-planning`'s call, informed by the Risks section's "build one at a time" recommendation. (2) How should acceptance criteria be verified given `NR11`/`NR13`/`NR14` are write-only registers — a new WRAM test-visibility mirror, or `run-driftune`'s register-read capability? `07-implementation-planning`/the implementing package's call. (3) **Closed 2026-07-26** — GDS-09 (Interface Specification) is now authored with its gate closed, so the contract this feature extends is formally specified. See [GDS-09 §2](../architecture/09-interface-specification.md) (the `ROM` class surface, including the `JR` signed-8-bit range limit this feature's per-channel routines must respect) and §5 (the per-frame call-order contract). |
| **Related ADRs** | None yet specific to this feature. `ADR-0001` (scheme selection rides `CHMIX_IDX`) is unrelated — different feature, noted only to confirm no conflict (this feature doesn't touch `CHMIX_IDX`). |
