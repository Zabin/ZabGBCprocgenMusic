# FS-107 — Combinable Generation Schemes

| Field | Content |
|---|---|
| **Feature ID** | `FS-107` / `FEAT-1070` |
| **Title** | Combinable Generation Schemes (Scheme W / Scheme E) |
| **Purpose** | Give each pitched channel a second, contrasting note-selection strategy (Scheme E — Euclidean-gated onset timing + fixed-motif pitch selection) alongside the shipped Scheme W (LFSR-driven scale-constrained walk), selectable per channel via the existing `CHMIX_IDX` preset space — so a mix preset audibly changes *how* the music is generated, not just which channels are active, per `BL-0020`'s "solo or in combination" ask and `ADS-100`'s concrete design. |
| **Scope** | The note-*selection* step of all 3 pitched channels' generation (pulse A, pulse B, wave). Which channels are *active* (`FEAT-1030`'s remediation, `IP-9010`) and every other per-frame behavior (timer countdown, register write mechanics, bad-zone bookkeeping, `FEAT-1060`'s arpeggio/vibrato/portamento/duty-cycle modulations) are explicitly out of scope and unchanged — this feature only changes *which scale degree is picked next* and *when the next onset happens*, nothing else in the onset pipeline. The noise channel (no pitch, `FEAT-1000`'s existing Euclidean-density mechanism) is unaffected — Scheme E *reuses* that same mechanism for pitched channels, it does not modify it. |
| **Requirements Implemented** | FR-1180 (scheme-select bit determines strategy), FR-1190 (scheme switch takes effect at next onset), FR-1200 (Scheme E onset timing reuses the Euclidean-pattern mechanism), FR-1210 (Scheme E pitch selection via a fixed motif), FR-1220 (bad-zone detection/recovery is scheme-agnostic), NFR-1060 (ROM/WRAM budget), NFR-1070 (no new WRAM control byte/input control) |
| **User Workflows** | 1. Listener presses Start to step `CHMIX_IDX` to a preset that assigns Scheme E to one or more pitched channels → from that channel's next note onset, it stops drifting freely (Scheme W) and instead plays a short, recognizable repeating melodic/rhythmic fragment gated by the same density-driven Euclidean pattern the noise channel already uses — audible as a clear textural contrast against any channel still running Scheme W. 2. Listener steps back to a Scheme-W-only preset (e.g. the boot preset) → the same channel resumes its free-drifting walk from its next onset. 3. Developer/coding agent adding a third scheme later reads Module Responsibilities/Interfaces Used to find the one branch point both schemes share. |
| **System Behaviour** | **Scheme selection** (FR-1180): each pitched channel's current scheme is read from a scheme-select bit in the active `CHMIX_IDX` preset's mask data (the specific bit position within `CHMIX_MASKS`'s spare bits 4-6, per `ADS-100` §2, is an implementation-package-level data decision, not fixed here). **Switch timing** (FR-1190): a channel already mid-note when `CHMIX_IDX` changes finishes that note under its old scheme; the new scheme takes over starting with that channel's next onset — identical "takes effect at next onset, not mid-note" contract `IP-9010`'s channel-activity gating already established for the same preset index, so a listener experiences one consistent rule for everything Start controls. **Scheme W** (unchanged): the shipped LFSR-delta walk, `_emit_channel_gen`'s existing note-selection branch — Scheme E is additive, not a replacement. **Scheme E onset timing** (FR-1200): instead of a fixed per-tempo timer reload, the channel's onset is gated by the same Euclidean-pattern lookup the noise channel already uses (`_euclidean_pattern`, keyed by the existing `DENSITY_IDX`) — a Scheme-E channel checks its own position in that pattern each tick and onsets only on a pattern hit, producing a patterned rather than metronomically-regular onset rhythm. **Scheme E pitch selection** (FR-1210): on an onset, instead of an LFSR-picked signed delta from the previous degree, the channel steps to the next entry in a short, fixed, ROM-resident cyclic motif (a precomputed sequence of scale-degree deltas, e.g. 4 motifs of 8 steps each per `ADS-100` §5) and wraps at the motif's end. **Bad-zone interaction** (FR-1220): dissonance/stale/overload detection and `IP-0007`'s autonomous recovery overrides read/write `CUR_DEGREE_*` exactly as they do for Scheme W — a Scheme-E channel's motif-picked degree is just as subject to the dissonant-pull-toward-tonic override as a Scheme-W channel's LFSR-picked one; no scheme-specific bad-zone branch exists. Edge case: a channel switches from Scheme E to Scheme W (or vice versa) with a bad-zone override active mid-transition — the override applies to whichever scheme is live at the next onset, same as any other preset-driven behavior change already handles (no special-casing needed, since the override operates on `CUR_DEGREE_*` after either scheme's own selection step, per `ADS-100` §2's "existing per-frame structure is unchanged" framing). |
| **Module Responsibilities** | Both schemes live in `music_engine.py`, inside `_emit_channel_gen`'s existing note-selection step (GDS-03 §1's "one job per file" — generation strategy, however many schemes exist, stays the engine module's job; no new module, consistent with `ADS-100` §2). `build_rom.py` gains no new responsibility beyond emitting Scheme E's motif table(s), same pattern as every existing preset/data table. `input_map.py` is unaffected — no new control (`FR-1070`/`NFR-1070`). `visuals.py` is unaffected — no new visualizer signal for scheme (not requested by `BL-0020`, not implied by any FR above); an Open Question below flags this as a deliberately unaddressed possibility, not an oversight. |
| **Interfaces Used** | The existing `CHANNELS`-list-driven parameterization of `_emit_channel_gen` (the same informal Python-level contract `FS-106`/`IP-1060`/`IP-1061`/`IP-9010` have each already extended in turn — GDS-09 remains `⛔ Planned`, so no formal interface contract exists to check this feature's extension against; same standing Open Question `FS-106` already named, not repeated as new). The shipped `CHMIX_MASKS` table and `CHMIX_IDX` read path (`IP-9010`) — this feature reads bits from the same byte `IP-9010` already populates, adding no new WRAM read/write path of its own. The shipped `_euclidean_pattern` function and `DENSITY_IDX`/`DENSITY_K` (`IP-0003`) — reused as-is, not modified. |
| **Data Model Changes** | New ROM-resident data (against GDS-07, which does not yet reserve these): one or more motif tables (`ADS-100` §6 estimates ≈32 bytes for 4 motifs × 8 one-byte scale-degree deltas). New WRAM: one small "current motif step" scratch byte per pitched channel running Scheme E (analogous in size and role to the shipped `NOISE_STEP_IDX`) — the exact count (one byte per channel vs. a packed shared byte, following `ARP_STATE_PA`/`PB`'s established packing precedent) is an implementation-package-level sizing decision. No new address is needed for scheme *selection itself* (`NFR-1070`) — it is derived from the already-resident `CHMIX_MASKS` byte each tick, not stored separately. |
| **State Changes** | No new engine *state machine* — scheme is a per-frame *branch* in the existing note-selection step of the existing note-onset/note-timer state machine (GDS-01's loop), not a new state, mirroring `FS-106`'s own "no new state machine" framing for its per-frame modulations. Select-reset (`FR-1070`) must additionally zero each pitched channel's new "current motif step" scratch byte, same audit discipline `IP-0005` already established for every other per-channel field. Scheme *assignment itself* is not reset by Select — it is derived from `CHMIX_IDX`, which Select already resets to the known-good preset (Scheme W for all channels, since the boot preset must not regress `FEAT-1000`'s existing default behavior, per `ADS-100` §3's "preset 0 stays this way" constraint). |
| **Error Handling** | No new failure mode — both schemes are bounded, always-computable (table lookups + wrapping counters), no new external input, no new randomness source (`NFR-1070`'s "no new PRNG" implicit constraint, mirroring `FS-106`'s duty-cycle requirement of the same shape). A motif table with zero entries or a scheme-select bit reading an out-of-range value cannot occur by construction (fixed-size ROM data, a 1-bit-wide select), so no invalid-state recovery path is needed. |
| **Performance Considerations** | NFR-1060 (ROM/WRAM budget): the motif table(s) plus per-channel scratch byte(s) are bounded and small, to be measured against actual headroom by the implementing package (same "not yet measured, confirm at implementation" framing `FS-106`'s own Risks section used for its budget). No dedicated timing NFR was formalized for this feature specifically (unlike `FS-106`'s `NFR-1050`) — Scheme E's added per-frame work (a Euclidean-pattern lookup already paid for by the noise channel's own tick, plus a motif-table index step) is bounded and comparable in cost to Scheme W's existing LFSR-delta step; verified the same way `NFR-1010` already is, via extended headless stress runs, not static cycle analysis. Flagged as an Open Question below (whether a dedicated NFR should be authored) rather than assumed adequate. |
| **Integrity Considerations** | None — no save data, no checksums beyond the existing header (unaffected). Determinism: motif tables are fixed ROM data (deterministic); Scheme E's Euclidean-pattern reuse is already deterministic (`IP-0003`'s shipped noise-channel mechanism). No new non-determinism beyond what the existing `DIV`-seeded LFSR (`R213`, `IP-0007`) already introduces for Scheme W. |
| **Acceptance Criteria** | (1) With a channel assigned Scheme E, its onset events occur on a Euclidean-pattern-gated schedule (matching the pattern the noise channel would produce at the same `DENSITY_IDX`), not at the fixed per-tempo interval Scheme W uses. (2) With a channel assigned Scheme E, its scale-degree sequence across consecutive onsets matches a fixed, repeating motif (the same short cycle recurs), rather than the continuous, non-repeating drift Scheme W produces. (3) Switching `CHMIX_IDX` to reassign a channel's scheme takes effect starting at that channel's next onset, not mid-note (an in-flight note started under the old scheme completes normally). (4) A channel running Scheme E is subject to the same dissonant/stuck/overload bad-zone overrides as a Scheme-W channel — driving the engine into a bad zone while a Scheme-E channel is active shows the same override behavior `T8`/`T10` already assert for Scheme W. (5) Preset 0 (boot/Select default) assigns Scheme W to all 3 pitched channels — no regression to the shipped default listening experience. (6) All existing `test_rom.py` suites (`T1`-`T13`) remain green — no regression. |
| **Verification Plan** | Test — a new `test_rom.py` suite drives `CHMIX_IDX` to a preset assigning Scheme E to at least one pitched channel and asserts on the WRAM-mirrored motif-step/degree state each acceptance criterion needs (the same "WRAM mirror, not raw PSG readback" convention every prior suite already uses, per `R108`/`VR-0001`'s write-only-register precedent) — exact preset assignment and WRAM mirror layout are implementation-package-level decisions, not fixed here (see Open Questions). Acceptance criterion (4) rides the existing `T8`/`T10` bad-zone assertions, re-driven with a Scheme-E channel active rather than a new mechanism. |
| **Dependencies** | `FEAT-1000`/`IP-0001`-`IP-0003` (`_emit_channel_gen`, `_euclidean_pattern`, `DENSITY_IDX` — all `VERIFIED`). `IP-9010` (`CHMIX_MASKS`, the shipped bit layout this feature's scheme-select bits ride, per `ADR-0001` — confirmed shipped with bits 0-3 as `ADR-0001` assumed, `VERIFIED`). No dependency on `FEAT-1060`/`IP-1060`/`IP-1061` — functionally independent, touches adjacent code only. |
| **Risks** | ROM/WRAM budget not yet measured against actual headroom (`NFR-1060`) — implementing package should confirm. Audible-contrast risk (`ADS-100` §8, carried forward): a 4-motif/8-step table is a small vocabulary — if Scheme E doesn't read as clearly distinct from Scheme W in practice, `BL-0020`'s "solo vs. combination" value proposition weakens; a judgment call for `09-content-review`, not resolvable at the spec stage, flagged so that review knows to specifically listen for it (same pattern `ADS-100` itself already named). Coupling risk (`ADS-100` §8, carried forward): packing scheme-selection into `CHMIX_MASKS`'s spare bits couples two independent concerns (channel activity, scheme) into one preset index — a future third `CHMIX_IDX`-adjacent concern would need to renegotiate this packing; accepted per `ADR-0001`, not re-litigated here. |
| **Open Questions** | (1) Exact motif-table contents/count and the scheme-select bit's precise position within bits 4-6 are data/preset decisions deferred to `07-implementation-planning`/the implementing package, per `ADS-100`'s own "shape, not values" framing — consistent with every prior preset-table deferral in this project. (2) Should a dedicated timing NFR (mirroring `FS-106`'s `NFR-1050`) be authored for Scheme E's per-frame cost, or is the existing `NFR-1010`/extended-stress-run verification method sufficient without a new ID? `04-requirements-engineering`'s call if the implementing package's own stress testing surfaces a reason to formalize one. (3) Should the visualizer (`FEAT-1040`) ever gain a scheme-reactive signal (e.g. a distinct tile/palette cue for a Scheme-E channel)? Not requested by `BL-0020`/`ADS-100`, not implied by any FR above — named here only so a future intake request for "show which scheme is playing" has a clear place to land (`00-intake` → likely `03-architecture-design-synthesis`, since it would extend GDS-08's still-`⛔ Planned` visualizer architecture level). (4) GDS-09 (Interface Specification) remains `⛔ Planned` — same standing gap `FS-106` already flagged, not blocking (every prior feature has extended the informal `CHANNELS` contract without it). |
| **Related ADRs** | `ADR-0001` (scheme selection rides the existing `CHMIX_IDX` preset space) — this feature's entire selection mechanism is that ADR's direct consequence; its stated contingency (bit layout matching `IP-9010`'s shipped `CHMIX_MASKS`) is confirmed satisfied (`04-requirements-engineering`'s delta review, 2026-07-25). |
