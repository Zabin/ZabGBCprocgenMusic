# FS-108 — Genre-Aware Style Presets

| Field | Content |
|---|---|
| **Feature ID** | `FS-108` / `FEAT-1080` |
| **Title** | Genre-Aware Style Presets |
| **Purpose** | Turn `R219`'s genre-feasibility tiering into real, selectable parameter regions — pressing Start now cycles through presets that shift the *whole musical character* (tempo, density, scale, timbre brightness) together, reading as a recognizable style change, per `docs/roadmap/04-release-roadmap.md`'s R5 and `ADS-101`'s concrete design. |
| **Scope** | A new, parallel `STYLE_TABLE` data table keyed by the existing `CHMIX_IDX` preset index, and the routine that applies a style row's values to `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX`/a new `DUTY_BIAS` byte when `CHMIX_IDX` changes. Which channels are *active* and which generation *scheme* each runs (`FEAT-1030`'s `CHMIX_MASKS`, `FEAT-1070`'s scheme-select bits) are explicitly out of scope and unchanged — this feature only changes the *target values* four existing tracked parameters hold, never how they're consumed by `_emit_channel_gen`/`_emit_noise_gen`/`_emit_badzone_tick`, all of which remain unmodified. Naming/authoring which specific `CHMIX_IDX` preset indices map to which style, and the exact per-style numeric values, are implementation-package-level data decisions (consistent with this project's standing preset-table deferral convention), not fixed here beyond the 3 named v1 styles' qualitative targets. |
| **Requirements Implemented** | FR-1230 (`CHMIX_IDX` preset maps to a style data row), FR-1240 (style values applied immediately, not gated to next onset), FR-1250 (at least 3 audibly-distinct styles), FR-1260 (preset-0 style matches shipped default, no regression), NFR-1080 (ROM/WRAM budget), NFR-1090 (no new input control) |
| **User Workflows** | 1. Listener presses Start to step `CHMIX_IDX` → the new preset's style row is applied immediately (same frame as the press, not waiting for a note onset): `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX`/`DUTY_BIAS` all jump to that style's target values, audible as an immediate, coordinated shift in speed, busyness, tonality, and brightness. 2. Listener who has been independently steering tempo/scale/density with the D-pad/A/B presses Start → those manually-drifted values are overwritten to the new style's targets; the listener can immediately resume independent steering from the new starting point (nothing is locked). 3. Listener cycles back to preset 0 → the engine returns to exactly the shipped default combination, with no audible discontinuity from "no style feature at all." 4. Developer/coding agent adding a 4th+ style later reads Module Responsibilities/Data Model Changes to find the one table to extend. |
| **System Behaviour** | **Style mapping** (FR-1230): each `CHMIX_IDX` value (0-7) indexes a `STYLE_TABLE` row holding 4 target values — `tempo_idx`, `density_idx`, `scale_idx`, `duty_bias`. **Application timing** (FR-1240): unlike `CHMIX_MASKS`'s channel-activity/scheme-select half (`FEAT-1030`/`FEAT-1070`, both "next onset" per `FR-1190`), style application is immediate — the same Start press that steps `CHMIX_IDX` also writes the new row's 4 values into `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX`/`DUTY_BIAS` on that frame, since these are parameters the D-pad/A/B already write directly and immediately today (a manual tempo/scale/density change has never been "next onset" gated); style application is simply a 4-way version of that same already-immediate write, not a new timing rule. **3 v1 styles** (FR-1250, per `ADS-101` §3): *Techno/Chiptune-Driving* (fast tempo, dense Euclidean percussion, minor/dorian mode, bright duty bias); *Ambient/Lo-Fi* (slow tempo, sparse density, major/pentatonic mode, soft duty bias — deliberately the style closest to the shipped default, the "anchor" the other two contrast against); *Holiday* (major mode, moderate tempo, moderate-steady density, bright duty bias, per `R219` §8's addendum). **Preset-0 non-regression** (FR-1260): `STYLE_TABLE[0]` holds exactly the values `PRESET_TEMPO_IDX`/`PRESET_OCTAVE_IDX`(unaffected, style doesn't touch octave)/`PRESET_SCALE_IDX`/`PRESET_DENSITY_IDX` already boot to, plus a neutral (zero) `DUTY_BIAS` — selecting preset 0 is indistinguishable from the pre-`FS-108` shipped behavior. **Edge case**: pressing Start rapidly through several presets in succession applies each style's values in turn, immediately, exactly as rapid D-pad presses already immediately re-write `TEMPO_IDX` today — no debouncing/coalescing beyond the joypad's own existing edge-detection (`FEAT-1010`), no new edge case introduced. **Edge case**: a style change mid-bad-zone-recovery — `DISSONANCE_SCORE`/`BAD_ZONE_FLAGS`/`STALE_COUNT_*`/`ONSET_WINDOW_COUNT` are untouched by a style change (only `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX`/`DUTY_BIAS` are written), so bad-zone state carries through a style change exactly as it already does through any other independent parameter change (e.g. a manual D-pad tempo nudge mid-bad-zone) — no special-casing needed. |
| **Module Responsibilities** | `music_engine.py` gains the new `STYLE_TABLE` data (alongside `CHMIX_MASKS`, `TEMPO_TABLE`, etc. — GDS-03 §1's "one job per file," data/generation logic stays the engine module's job) and the read-and-apply routine, called from the same Start-press handling site `input_map.py`'s `_step_on_bit` already triggers for `CHMIX_IDX` (an added step in that existing call chain, not a new call site or a change to `input_map.py`'s own code — `FEAT-1010` is unaffected). `build_rom.py` gains no new responsibility beyond emitting `STYLE_TABLE`, same pattern as every existing data table. `visuals.py` is unaffected — no new visualizer signal for style (not requested by any FR above; an Open Question below flags this as deliberately unaddressed, not an oversight). |
| **Interfaces Used** | The existing `CHMIX_IDX` WRAM read/write path (`FEAT-1010`/`FEAT-1030`/`FEAT-1070`) — this feature adds a read of a new, parallel table keyed by the same index, no new WRAM control byte and no change to how `CHMIX_IDX` itself is stepped. The existing `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX` WRAM addresses (`FEAT-1000`) — written by this feature exactly as `input_map.py`'s D-pad/A/B handlers already write them, reusing the identical write path/semantics, not a new one. GDS-09 (Interface Specification) remains `⛔ Planned`, same standing gap `FS-106`/`FS-107` already flagged — not blocking, since every prior feature has extended the informal module contracts without it. |
| **Data Model Changes** | New ROM-resident data (against GDS-07, which does not yet reserve this): `STYLE_TABLE`, 8 rows × 4 bytes (`tempo_idx`, `density_idx`, `scale_idx`, `duty_bias`) = 32 bytes (`ADS-101` §6's own estimate). New WRAM: one byte, `DUTY_BIAS` (a per-style timbre offset consumed by `IP-1060`'s existing duty-cycle write site — the exact add-vs-override combination rule with `DUTY_BY_DEGREE` is an implementation-package-level decision, `BL-0038`). No new address is needed for style *selection itself* — it is derived from the already-resident `CHMIX_IDX` each Start press, not stored separately. |
| **State Changes** | No new engine state machine — style application is a coordinated *write* to 4 already-existing tracked-parameter WRAM addresses (plus the 1 new `DUTY_BIAS` byte) triggered by an existing input edge (Start), not a new state or a new transition in GDS-01's loop. Select-reset (`FR-1070`) must additionally zero `DUTY_BIAS` to `STYLE_TABLE[0]`'s value (0, per FR-1260), same audit discipline `IP-0005`/`IP-9010` already established for every other per-preset field reset by Select. |
| **Error Handling** | No new failure mode — `STYLE_TABLE` is fixed-size ROM data indexed by an already-range-checked `CHMIX_IDX` (wrapped mod 8 by the existing `_step_on_bit` mask, `FEAT-1010`), so an out-of-range row read cannot occur by construction. No new external input, no new randomness source. |
| **Performance Considerations** | NFR-1080 (ROM/WRAM budget): 32 bytes of ROM data plus 1 WRAM byte, negligible against the measured 29349 free ROM bytes (`ADR-0002`'s own instrumentation, re-confirmed by the implementing package per that same method). No dedicated timing NFR needed — applying 4 byte-writes on a Start press is bounded, comparable in cost to the existing per-button parameter writes `input_map.py` already performs every frame; no new per-tick generation-routine work is added (`_emit_channel_gen`/`_emit_noise_gen` read `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX` exactly as they already do today, unaware a style feature exists). |
| **Integrity Considerations** | None — no save data, no checksums beyond the existing header (unaffected). Determinism: `STYLE_TABLE` is fixed ROM data (deterministic); no new non-determinism is introduced (style values are a direct table lookup, no PRNG involvement). |
| **Acceptance Criteria** | (1) Selecting a `CHMIX_IDX` preset mapped to a named style immediately (same frame as the Start press) sets `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX`/`DUTY_BIAS` to that style's documented target values. (2) Each of the 3 v1 styles' resulting parameter combination is distinguishable, by content review, from the other 2 styles and from preset 0's combination. (3) Selecting `CHMIX_IDX` preset 0 produces exactly the shipped default `TEMPO_IDX`/`OCTAVE_IDX`/`SCALE_IDX`/`DENSITY_IDX` combination with `DUTY_BIAS` = 0 — no change from pre-`FS-108` boot/Select-reset behavior. (4) A style change does not alter `DISSONANCE_SCORE`/`BAD_ZONE_FLAGS`/`STALE_COUNT_*`/`ONSET_WINDOW_COUNT` — bad-zone state is unaffected by a style change, verified by driving a style change mid-bad-zone and confirming those WRAM fields are untouched by the change itself. (5) Select still resets `DUTY_BIAS` to 0 alongside every other per-preset field it already resets. (6) All existing `test_rom.py` suites (`T1`-`T14`) remain green — no regression. |
| **Verification Plan** | Test — a new `test_rom.py` suite steps `CHMIX_IDX` through each style-mapped preset and asserts `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX`/`DUTY_BIAS` read the documented target values on the same frame as the Start press (verifying FR-1240's "immediate," not "next onset," timing directly — a different assertion shape than `FS-107`'s own next-onset-gated tests). Acceptance criterion (2)'s audible-distinctness judgment is a `09-content-review` task, not an automated assertion (same "judgment call, not resolvable by test alone" pattern `FS-107`'s Risks section already used for Scheme E's audible contrast). Acceptance criterion (4) drives a style change during an active bad-zone state and confirms bad-zone WRAM fields are unchanged by the style-change frame itself, reusing the existing `T8`/`T10` bad-zone assertion style. |
| **Dependencies** | `FEAT-1000`/`IP-0001`-`IP-0003` (`TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX`, all `VERIFIED`). `FEAT-1010`/`IP-0001` (`CHMIX_IDX`'s existing Start-stepped read/write path, `VERIFIED`). `IP-1060` (`DUTY_BY_DEGREE`'s existing duty-cycle write site, which `DUTY_BIAS` composes with — `VERIFIED`). No dependency on `FEAT-1060`'s arpeggio/vibrato/portamento logic beyond the shared duty-cycle write site, and no dependency on `FEAT-1070`'s scheme-select bits — `STYLE_TABLE` is read independently of `CHMIX_MASKS`, per `ADS-101` §2's "two tables stay independent" design. |
| **Risks** | Overwriting manually-steered parameters on every Start press could read as the engine "fighting" the listener's own tuning if styles are stepped through idly (`ADS-101` §8, carried forward) — a `09-content-review` judgment call, not resolvable at the spec stage, flagged so review specifically listens for whether the overwrite reads as intentional/legible. Genre-fidelity risk (`ADS-101` §8, carried forward): parameter-preset-only genre signaling (no new timbral/percussive mechanism) may not read as *recognizably* the named genre without a listener already primed by the reference — named for `09-content-review` against `R219`'s own genre-fidelity framing, not asserted as solved here. `DUTY_BIAS` combination-rule risk (`BL-0038`, carried forward): the exact add-vs-override rule with `IP-1060`'s existing duty selection needs prototyping before `08-code-implementation` can finalize it. |
| **Open Questions** | (1) Exact `CHMIX_IDX`-to-style preset assignment (which of the 8 index values map to which of the 3 v1 styles, and what the remaining unassigned indices default to) is a data/preset decision deferred to `07-implementation-planning`/the implementing package, per `ADS-101`'s own "shape, not values" framing — consistent with every prior preset-table deferral in this project. (2) `DUTY_BIAS`'s exact combination rule with `IP-1060`'s existing per-degree duty selection (`BL-0038`) — a `07-implementation-planning`/`08-code-implementation`-level detail once prototyped and listened to. (3) Should the visualizer (`FEAT-1040`) ever gain a style-reactive signal? Not requested by any FR above, not implied by `ADS-101` — named here only so a future intake request has a clear place to land (`00-intake` → likely `03-architecture-design-synthesis`, extending GDS-08's still-`⛔ Planned` visualizer architecture level), same pattern `FS-107`'s own Open Question (3) already used for a scheme-reactive signal. (4) Celtic (a 4th style, per `R219` §8/`BL-0039`) and Holiday's own stepwise-motion-bias refinement are deliberately deferred past this spec's 3-style scope — real, grounded follow-on candidates once v1 styles ship and their listening character is known, not addressed here. (5) GDS-09 (Interface Specification) remains `⛔ Planned` — same standing gap `FS-106`/`FS-107` already flagged, not blocking. |
| **Related ADRs** | None directly — `ADS-101`'s Decision Log carries this feature's binding decisions (no dedicated ADR was needed, unlike `FS-107`'s `ADR-0001`, since `ADS-101` itself is the authoritative decision record for this feature's mechanism). |
