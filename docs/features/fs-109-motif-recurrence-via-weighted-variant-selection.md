# FS-109 — Motif Recurrence via Weighted Variant Selection

| Field | Content |
|---|---|
| **Feature ID** | `FS-109` / `FEAT-1090` |
| **Title** | Motif Recurrence via Weighted Variant Selection |
| **Purpose** | Close `BL-0010`'s motif-recurrence gap (R211/R212/R214 §8): give Scheme E's existing fixed 8-step `MOTIF_TABLE` genuine development over time — occasional, bounded variation on top of clear recurrence — rather than looping one fixed sequence forever, per `docs/architecture/ADS-102-motif-recurrence-via-weighted-variant-selection.md`'s concrete design. |
| **Scope** | Extending `IP-1070`'s existing single-row `MOTIF_TABLE` into a small fixed set of pre-composed motif variants, and the weighted-selection routine that autonomously picks the active variant at each motif-cycle boundary. The existing motif-step counter's packing/advance logic (`scheme_state` bits4-6), Scheme E's onset-timing mechanism (`FEAT-1070`'s Euclidean-gated onsets), and Scheme W (the LFSR walk) are all explicitly out of scope and unchanged — this feature only changes *which row* of motif data the existing per-step lookup reads from, never *how* or *when* that lookup runs. Choosing the exact `N_VARIANTS` count and the weighting table's precise numeric values are implementation-package-level data decisions (`BL-0042`, consistent with this project's standing preset-table deferral convention), not fixed here beyond `ADS-102` §3's proposed starting shape. |
| **Requirements Implemented** | FR-1270 (motif data is a small fixed variant set, variant 0 matches shipped), FR-1280 (weighted variant selection at cycle boundaries, no input required), FR-1290 (weighting favors retaining the current variant), FR-1300 (variant 0 held throughout reproduces pre-change behavior exactly, no regression), NFR-1100 (ROM/WRAM budget), NFR-1110 (no new input control/WRAM control byte beyond the variant-index field) |
| **User Workflows** | 1. Listener with a Scheme-E channel active hears the channel's core motif shape recur clearly cycle to cycle (recognizable, "short but interesting," per R214 §8) while occasionally shifting to a related variant at a cycle boundary — audible development without losing the sense of recurrence, with no button involved. 2. Listener who never touches any control still experiences this — the selection is fully autonomous, the same class of no-input-required behavior as bad-zone recovery (`FEAT-1030`). 3. Listener switching `CHMIX_IDX` (Start, `FEAT-1080`/`FEAT-1070`) to a different preset that also assigns Scheme E to a channel experiences the same variant-selection behavior on that channel, unaffected by which preset triggered it. 4. Developer/coding agent verifying no regression forces/seeds `MOTIF_VARIANT_IDX` to 0 for an entire run and confirms the channel's onset-by-onset pitch sequence is byte-identical to the pre-`FS-109` shipped behavior. |
| **System Behaviour** | **Variant data shape** (FR-1270): `MOTIF_TABLE` becomes `N_VARIANTS` rows (proposed 4, `ADS-102` §3) of 8 bytes each, indexed first by variant then by motif-step (0-7); variant row 0 is byte-identical to the currently shipped single sequence (`[0, 2, 4, 5, 4, 2, 0, 7]`). **Selection timing** (FR-1280): on the exact frame a Scheme-E channel's motif-step counter completes a full cycle (wraps from its final step back to its first — the same wrap-detection the existing step-advance arithmetic already produces), the engine draws a new `MOTIF_VARIANT_IDX` via a weighted lookup (`MOTIF_VARIANT_SELECTOR`) and holds it for the following full cycle; this happens autonomously, with no button input, identically whether or not the listener has pressed anything. **Weighting** (FR-1290): the selector's entries are not a uniform draw across all variants — most cycle-boundary draws retain the currently-active variant, with only occasional switches to a different one, directly implementing R214 §8's "short melody, still interesting" constraint (variation is occasional and whole-cycle-grain, never per-note). **Non-regression** (FR-1300): with `MOTIF_VARIANT_IDX` held at 0 (e.g. a test-only seed disabling the weighted draw), the per-step lookup reads exactly variant row 0 every cycle — identical output to `IP-1070`'s shipped behavior, byte for byte. **Edge case**: a `CHMIX_IDX` preset change (`FEAT-1080`'s style application, or `FEAT-1070`/`FEAT-1030`'s scheme/channel-mix reassignment) landing on the exact frame a motif cycle would otherwise complete — this feature's own cycle-boundary detection and the existing motif-step counter are unaffected by any of those other mechanisms' writes (none of them touch `scheme_state`'s motif-step bits or the new `MOTIF_VARIANT_IDX` byte), so the variant draw proceeds on schedule regardless; named as a combination `09-package-verification`/`10-integration-review` should explicitly exercise (per `ADS-102` §8's own flagged risk), not asserted as solved by inspection alone. **Edge case**: bad-zone state (`FEAT-1030`) during a variant-boundary draw — `DISSONANCE_SCORE`/`BAD_ZONE_FLAGS`/`STALE_COUNT_*`/`ONSET_WINDOW_COUNT` are untouched by variant selection (only `MOTIF_VARIANT_IDX` is written), so bad-zone state carries through a variant change exactly as it already does through any other independent per-frame mechanism. |
| **Module Responsibilities** | `music_engine.py` gains the extended `MOTIF_TABLE` data, the new `MOTIF_VARIANT_SELECTOR` weighting table, and the cycle-boundary-detection-plus-selection logic, all inside `_emit_channel_gen`'s existing Scheme-E branch (the same `gt_e_*` label family `FEAT-1070` already owns — GDS-03 §1's "one job per file" is preserved, no new module). `input_map.py` is entirely unaffected — this feature has no input-mapping component (`NFR-1110`). `build_rom.py` gains no new responsibility beyond emitting the extended `MOTIF_TABLE` and the new selector table, same pattern as every existing data table. `visuals.py` is unaffected — no new visualizer signal for motif-variant state (not requested by any FR above; flagged as an Open Question, same pattern `FS-107`/`FS-108` already used for their own scheme/style-reactive-visualizer questions). |
| **Interfaces Used** | The existing motif-step counter's read/advance path inside `_emit_channel_gen`'s `gt_e_*` branch (`FEAT-1070`) — this feature adds a read (at cycle-boundary frames only) of a new `MOTIF_VARIANT_IDX` byte to select which table row the existing per-step lookup uses, with no change to the counter's own packing (`scheme_state` bits4-6) or advance logic. The existing `MOTIF_TABLE` lookup site itself (`FEAT-1070`) — extended to be variant-relative (`motif_table_base + variant_idx * 8 + step`) rather than a single fixed base, per `ADS-102` §2. GDS-09 (Interface Specification) remains `⛔ Planned`, same standing gap `FS-106`/`FS-107`/`FS-108` already flagged — not blocking. |
| **Data Model Changes** | New ROM-resident data (against GDS-07, which does not yet reserve this): `MOTIF_TABLE` extended from 8 bytes (1 row) to `N_VARIANTS × 8` bytes (proposed 4 rows = 32 bytes, `ADS-102` §6's own estimate — net +24 over the currently shipped table), plus a new `MOTIF_VARIANT_SELECTOR` weighting table (comparable in size to `DELTA_TABLE`'s existing 4 bytes, likely 8-16 bytes to encode a real retention-biased weighting curve). New WRAM: one byte, `MOTIF_VARIANT_IDX` (a single shared field for v1, since today's only shipped Scheme-E-assigning preset activates the scheme on exactly one channel at a time — a future multi-channel-Scheme-E preset would need this revisited, per `ADS-102`'s own Open Question, not addressed here). No new address is needed for the *selection event itself* — it is derived from the existing motif-step counter's wrap condition each frame, not stored separately. |
| **State Changes** | No new engine state machine — variant selection is a small, bounded update to the existing per-channel motif mechanism (a new WRAM byte, written only at cycle-boundary frames), not a new state or a new transition in GDS-01's loop. No Select-reset interaction is required beyond what already happens: `MOTIF_VARIANT_IDX` is not part of any preset's reset semantics (unlike `FS-108`'s `DUTY_BIAS`), since it is a Scheme-E-internal scratch value the mechanism reseeds naturally at the next cycle boundary regardless of Select — flagged in Open Questions for `07-implementation-planning` to confirm this reasoning holds once prototyped, not asserted as final here. |
| **Error Handling** | No new failure mode — `MOTIF_TABLE`/`MOTIF_VARIANT_SELECTOR` are fixed-size ROM data indexed by values produced entirely by existing, already-bounded arithmetic (the motif-step counter's own wrap-masking, and an LFSR-bit-derived selector index, the same class of index `DELTA_TABLE` already uses safely), so an out-of-range row read cannot occur by construction. No new external input, no new randomness source beyond the LFSR state the engine already maintains. |
| **Performance Considerations** | NFR-1100 (ROM/WRAM budget): roughly 24-40 bytes of additional ROM data plus 1 WRAM byte, negligible against the measured free-ROM headroom (`ADR-0002`'s own instrumentation — `IP-1080` alone used only 78 of 29349 free bytes, so a comparably-sized addition here is not a budget concern; re-confirmed by the implementing package per that same method). No dedicated timing NFR needed — the cycle-boundary check and weighted draw happen at most once per 8-onset cycle, not every frame or every onset, so the added per-tick work is strictly less frequent than `FEAT-1070`'s own existing per-onset motif-step lookup it sits alongside. |
| **Integrity Considerations** | None — no save data, no checksums beyond the existing header (unaffected). Determinism: `MOTIF_TABLE`/`MOTIF_VARIANT_SELECTOR` are fixed ROM data (deterministic); the LFSR-driven selection draw uses the same existing pseudo-random state the engine already relies on for other weighted choices (`DELTA_TABLE`), introducing no new non-determinism source. |
| **Acceptance Criteria** | (1) A Scheme-E channel's motif data comprises at least the shipped default variant (row 0, byte-identical to the pre-`FS-109` sequence) plus at least one additional variant. (2) On the frame a channel's motif-step counter wraps to its first step, `MOTIF_VARIANT_IDX` is drawn via the weighted selector, autonomously, with no button input in the preceding frames required to trigger it. (3) Across a sufficiently long randomized run, the selector's draws measurably favor retaining the current variant over switching (a majority of cycle-boundary draws are retentions, not switches) — verified statistically, not per-draw. (4) With `MOTIF_VARIANT_IDX` held at 0 for an entire run, the channel's onset-by-onset pitch sequence is byte-identical to the pre-`FS-109` shipped sequence — no regression. (5) All existing `test_rom.py` suites (`T1`-`T15`) remain green — no regression. |
| **Verification Plan** | Test — a new `test_rom.py` suite (a) confirms `MOTIF_TABLE`'s variant-0 row matches the pre-`FS-109` shipped sequence exactly (acceptance criterion 1/4, reusing the existing Scheme-E onset-sequence assertion pattern `VR-1070`/`T14` already established, with `MOTIF_VARIANT_IDX` held at a fixed seed); (b) drives a run long enough to observe multiple full motif cycles and asserts `MOTIF_VARIANT_IDX` changes only on cycle-boundary frames, never mid-cycle (acceptance criterion 2); (c) drives a longer randomized run and asserts the empirical retention-vs-switch ratio favors retention (acceptance criterion 3 — a statistical assertion over many draws, the same class of "measured over a run, not a single sample" test `VR-1080`'s own randomized stress-run methodology already used). Acceptance criterion 5 is the standing full-suite regression gate every feature already carries. |
| **Dependencies** | `FEAT-1070`/`IP-1070` (Scheme E's existing `MOTIF_TABLE`/motif-step mechanism, `VERIFIED`) — this feature is a genuine extension of that shipped code, not merely a sibling reader of shared state (the first such dependency this project's feature catalog has recorded, per `05-feature-decomposition`'s own dependency-graph note). No dependency on `FEAT-1080`'s `STYLE_TABLE`/`_emit_apply_style` path — the two features touch disjoint code (this feature's cycle-boundary logic lives entirely inside `_emit_channel_gen`'s Scheme-E branch; `FEAT-1080` touches the Start-press handler in `input_map.py` and a sibling data table) — but see the mid-cycle-interaction edge case above, named for verification, not a code dependency. |
| **Risks** | Variant transitions could read as a discontinuity/jump rather than "development" if a new variant's degree sequence doesn't share enough contour with the outgoing one (`ADS-102` §8, carried forward) — a `09-content-review` judgment call, not resolvable at the spec stage; mitigated at the data-authoring stage by composing variants for family resemblance to variant 0, not independently. Tuning risk (`BL-0042`, carried forward): the exact `N_VARIANTS` count and the selector's weighting curve are real tuning decisions with no single objectively-correct answer from the research alone — needs prototyping/listening before `08-code-implementation` can finalize the data. Interaction risk (`ADS-102` §8, carried forward): the `FEAT-1080`/style-change mid-cycle interaction named in System Behaviour above needs explicit verification, not just code-level reasoning, given `BL-0040`'s prior finding that a superficially-similar "these fields are independent" claim for style presets needed a wording caveat once adversarially stress-tested. |
| **Open Questions** | (1) The concrete `N_VARIANTS` count and `MOTIF_VARIANT_SELECTOR` weighting curve (`BL-0042`) are data/implementation decisions deferred to `07-implementation-planning`/the implementing package, per `ADS-102`'s own "shape, not values" framing — consistent with every prior preset/table-value deferral in this project. (2) Whether `MOTIF_VARIANT_IDX` needs to be per-channel once a future preset assigns Scheme E to more than one channel simultaneously (`BL-0043`) — not yet shipped, so v1 uses a single shared byte; deferred until that case is actually proposed. (3) Whether variant rows should be authored via an offline L-system rewrite step or simply hand-composed (`BL-0043`) — either satisfies R214 §8's framing; left to `08-content-authoring` to decide pragmatically. (4) Does `MOTIF_VARIANT_IDX` need any Select-reset handling, or does the mechanism's own natural cycle-boundary reseeding make that unnecessary (see State Changes)? A `07-implementation-planning`/`08-code-implementation`-level detail once prototyped. (5) Should the visualizer (`FEAT-1040`) ever gain a motif-variant-reactive signal? Not requested by any FR above, not implied by `ADS-102` — named here only so a future intake request has a clear place to land, same pattern `FS-107`/`FS-108`'s own analogous Open Questions already used. (6) GDS-09 (Interface Specification) remains `⛔ Planned` — same standing gap every prior FS has flagged, not blocking. |
| **Related ADRs** | None directly — `ADS-102`'s Decision Log carries this feature's binding decisions (no dedicated ADR was needed, same pattern `FS-108`/`ADS-101` already established). |
