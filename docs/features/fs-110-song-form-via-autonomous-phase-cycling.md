# FS-110 — Song-Form via Autonomous Phase Cycling

| Field | Content |
|---|---|
| **Feature ID** | `FS-110` / `FEAT-1100` |
| **Title** | Song-Form via Autonomous Phase Cycling |
| **Purpose** | Give a listening session a shape over time, per `docs/roadmap/04-release-roadmap.md`'s R6 and R220's parameter-envelope finding — a recognizable intro→build→peak→breakdown arc audible over a multi-minute session, not flat continuous texture, per `ADS-103`'s concrete design. Closes `BL-0010`'s song-form half (the motif-recurrence half already closed via `IP-1090`/`ADS-102`). |
| **Scope** | A new, independent state machine (`SONG_STATE`/`SONG_STATE_TIMER`) that autonomously cycles 4 named phases and, on each transition, overwrites `TEMPO_IDX`/`DENSITY_IDX` to that phase's target values. Which specific tempo/density values each phase targets, and each phase's duration, are implementation-package-level data decisions (consistent with this project's standing preset-table deferral convention), not fixed here beyond the 4 named phases' qualitative shape (calm → rising → dense/fast → settling). Style-drift (R220's slower-cadence half of the same underlying mechanism) is explicitly out of scope for this spec — a named future extension (`ADS-103` §9), not built here. Whether `SCALE_IDX`/`DUTY_BIAS` also join the envelope (a fuller "style" move per phase) is likewise out of scope — v1 targets only `TEMPO_IDX`/`DENSITY_IDX`, per R6's own "recognizable arc" completion criteria. |
| **Requirements Implemented** | FR-1310 (autonomous 4-phase cycle, no input required), FR-1320 (phase transition overwrites tempo/density immediately), FR-1330 (bad-zone/motif-variant mechanisms phase-agnostic), FR-1340 (all 4 phases occur in cyclic order over a long run), NFR-1120 (ROM/WRAM budget), NFR-1130 (no new input control) |
| **User Workflows** | 1. Listener lets a session run uninterrupted with no input — the engine autonomously cycles through INTRO (calm) → BUILD (rising) → PEAK (dense/fast) → BREAKDOWN (settling) → back to INTRO, looping indefinitely, tempo and density visibly/audibly shifting at each transition. 2. Listener who has been manually steering tempo/density with the D-pad/B experiences the next phase transition **overwriting** those manually-drifted values to the phase's target — the same "honest big jump" precedent Select's full-reset and `IP-1080`'s style application already establish, just autonomously triggered. 3. Listener who separately presses Start mid-session (`IP-1080`'s style trigger) sees that style's values apply immediately as always; the next scheduled song-state transition then overwrites `TEMPO_IDX`/`DENSITY_IDX` again on its own independent schedule — two independent autonomous/triggered writers to the same two fields, last write wins, no special-casing (same contract `FR-1240` already established for D-pad/B vs. style). 4. Developer/coding agent verifying no regression confirms bad-zone detection/recovery and Scheme-E motif-variant selection both behave identically regardless of which song-form phase is currently active. |
| **System Behaviour** | **Autonomous cycling** (FR-1310): `SONG_STATE` (0-3) advances INTRO→BUILD→PEAK→BREAKDOWN→INTRO (wrap mod 4) each time `SONG_STATE_TIMER` counts down to 0, with no button input required — the same fully-autonomous, no-input-required class of behavior `IP-0007`'s bad-zone recovery and `IP-1090`'s motif-variant selection already established. **Immediate overwrite** (FR-1320): on the exact tick a phase transition occurs, `TEMPO_IDX`/`DENSITY_IDX` are overwritten to the new phase's target values — the same coordinated-overwrite contract `FR-1240`/`IP-1080` already established for style application, just autonomously triggered by the countdown rather than a Start press. **Phase-agnostic bad-zone/motif-variant behavior** (FR-1330): `_emit_badzone_tick`'s dissonant/stuck/overload detection and recovery, and `IP-1090`'s Scheme-E motif-variant cycle-boundary draws, are both entirely unaffected by which song-form phase is active — neither mechanism reads `SONG_STATE`/`SONG_STATE_TIMER`, and the song-form tick never reads or writes `BAD_ZONE_FLAGS`/`CUR_DEGREE_*`/`MOTIF_VARIANT_IDX`/`scheme_state`. **Long-run cyclic-order demonstration** (FR-1340): over an 8000+ frame headless run, all 4 phases occur in their defined order with no hang or stall — the same "extended stress run" methodology every prior autonomous mechanism (`IP-0007`, `IP-1070`, `IP-1090`) was already demonstrated with. **Edge case**: a phase transition landing on the same frame as an `IP-1080` style-triggered overwrite (a Start press) — both writers independently overwrite `TEMPO_IDX`/`DENSITY_IDX` on that frame; whichever code runs later in `engine_tick`'s existing call order wins for that frame, with no corruption of either mechanism's own bookkeeping (`SONG_STATE`/`CHMIX_IDX` are unaffected by either write) — named for explicit verification (`ADS-103` §8), not merely reasoned safe by analogy, given `VR-1090`'s own prior finding that a superficially-similar independence claim needed adversarial-test confirmation to be trusted. **Edge case**: a BUILD-phase target `DENSITY_IDX` high enough to itself trigger `OVERLOAD` — bad-zone recovery proceeds exactly as it would for any other high-density state (no special-casing), a real musical-tuning question (`ADS-103` §9's own Open Question) rather than a defined edge-case contract, named for `09-content-review` judgment once phase values are chosen. |
| **Module Responsibilities** | `music_engine.py` gains the new `SONG_TABLE` data (alongside `STYLE_TABLE`, `MOTIF_TABLE`, etc. — GDS-03 §1's "one job per file," data/generation logic stays the engine module's job) and a new `_emit_song_tick` routine, called once per frame from `engine_tick` — the same call site `_emit_badzone_tick` and each channel's `gen_tick` already run from (an added call in that existing per-frame sequence, not a new call site pattern). `input_map.py` is entirely unaffected — this feature has no input-mapping component (`NFR-1130`). `build_rom.py` gains no new responsibility beyond emitting `SONG_TABLE`, same pattern as every existing data table. `visuals.py` is unaffected — no new visualizer signal for song-form phase (not requested by any FR above; an Open Question below flags this as deliberately unaddressed, same pattern `FS-107`/`FS-108`/`FS-109` already used for their own reactive-visualizer questions). |
| **Interfaces Used** | The existing `TEMPO_IDX`/`DENSITY_IDX` WRAM addresses (`FEAT-1000`) — written by this feature exactly as `IP-1080`'s `_emit_apply_style` and the D-pad/B handlers already write them, reusing the identical write path/semantics, not a new one. The existing `engine_tick` per-frame call sequence (`FEAT-1000`/`IP-0007`) — this feature adds one new call alongside the existing `_emit_badzone_tick`/`gen_tick` calls, not a new dispatch mechanism. GDS-09 (Interface Specification) remains `⛔ Planned`, same standing gap every prior FS has flagged — not blocking. |
| **Data Model Changes** | New ROM-resident data (against GDS-07, which does not yet reserve this): `SONG_TABLE`, 4 rows × 3 bytes (`tempo_idx`, `density_idx`, `duration`) = 12 bytes (`ADS-103` §6's own estimate). New WRAM: two bytes, `SONG_STATE` (0-3, which phase is active) and `SONG_STATE_TIMER` (ticks remaining in the current phase). No new address is needed for phase *duration* tracking beyond the timer itself — reload value comes directly from the phase's own `SONG_TABLE` row. |
| **State Changes** | A new, fully autonomous state machine — `SONG_STATE` transitions on a fixed per-phase schedule (its own `SONG_STATE_TIMER` reaching 0), independent of any button input, bad-zone state, or Scheme-E motif-variant state. Select-reset (`FR-1070`) must additionally reset `SONG_STATE` to 0 (`INTRO`) and `SONG_STATE_TIMER` to `INTRO`'s own duration, and re-apply `SONG_TABLE[0]`'s `TEMPO_IDX`/`DENSITY_IDX` targets — the same per-preset-field reset discipline `IP-0005`/`IP-9010`/`IP-1080` already established for every other Select-reset field, so a reset always returns to a deterministic, known-good starting phase rather than an arbitrary mid-cycle one. |
| **Error Handling** | No new failure mode — `SONG_TABLE` is fixed-size ROM data indexed by an already-range-checked `SONG_STATE` (wrapped mod 4 by the same wrap-on-increment idiom every other cyclic index in this codebase already uses), so an out-of-range row read cannot occur by construction. No new external input, no new randomness source (the state machine is a deterministic countdown-and-cycle, not a weighted draw like `IP-1090`'s motif-variant selection). |
| **Performance Considerations** | NFR-1120 (ROM/WRAM budget): 12 bytes of ROM data plus 2 WRAM bytes, negligible against the measured free-ROM headroom (`ADR-0002`'s own instrumentation; re-confirmed by the implementing package per that same method). No dedicated timing NFR needed beyond the existing per-frame budget — `_emit_song_tick`'s per-frame cost (a countdown-and-compare, with a 2-byte overwrite only on transition frames) is comparable to `_emit_badzone_tick`'s own existing per-frame cost, per `ADS-103` §6's own "no new arithmetic complexity class" framing. |
| **Integrity Considerations** | None — no save data, no checksums beyond the existing header (unaffected). Determinism: `SONG_TABLE` is fixed ROM data (deterministic); the phase cycle itself is a deterministic countdown, not a randomized draw, so this feature introduces strictly less non-determinism than `IP-1090`'s own motif-variant selection did. |
| **Acceptance Criteria** | (1) With no button input, the engine autonomously cycles through all 4 named phases in their defined order (INTRO→BUILD→PEAK→BREAKDOWN→INTRO), confirmed over a long (8000+ frame) run. (2) On each phase transition, `TEMPO_IDX`/`DENSITY_IDX` read exactly that phase's documented target values on the same frame as the transition. (3) Bad-zone detection/recovery (`BAD_ZONE_FLAGS`/`DISSONANCE_SCORE`/`STALE_COUNT_*`/`ONSET_WINDOW_COUNT`) and Scheme-E motif-variant selection (`MOTIF_VARIANT_IDX`) are both unaffected by song-form phase transitions — verified by driving a phase transition and confirming those WRAM fields are untouched by the transition itself (same "this package's own writes never touch those addresses" framing `IP-1080`'s own acceptance criterion (4) used, with the same `BL-0040`-informed narrow wording, not a broader same-frame guarantee). (4) A phase transition landing on the same frame as an `IP-1080` style-triggered overwrite corrupts neither mechanism's own state (`SONG_STATE`/`CHMIX_IDX` unaffected by either write). (5) Select resets `SONG_STATE`/`SONG_STATE_TIMER` to phase 0 (`INTRO`) and re-applies its target values. (6) All existing `test_rom.py` suites (`T1`-`T16`) remain green — no regression. |
| **Verification Plan** | Test — a new `test_rom.py` suite drives a long run and asserts all 4 phases occur in cyclic order with the documented `TEMPO_IDX`/`DENSITY_IDX` values applied on each transition frame (acceptance criteria 1-2); confirms bad-zone/motif-variant WRAM fields are unchanged by a transition frame specifically (acceptance criterion 3, same assertion shape `IP-1080`'s own `T15.5` already established); drives a Start press timed near a phase-transition boundary and confirms neither mechanism's state is corrupted (acceptance criterion 4, same dedicated-interaction-test discipline `IP-1090`'s own `T16.8`/`VR-1090` established, this time verified with a genuinely forced collision rather than an untested-in-practice interval, per `BL-0045`'s own lesson); confirms Select resets phase/timer/target values (acceptance criterion 5). Acceptance criterion 6 is the standing full-suite regression gate every feature already carries. Whether the 4-phase arc reads as musically "natural, not mechanical" (`ADS-103` §8's own risk) is a `09-content-review` judgment call, not an automated assertion. |
| **Dependencies** | `FEAT-1000`/`IP-0001`-`IP-0003` (`TEMPO_IDX`/`DENSITY_IDX`, all `VERIFIED`). No dependency on `FEAT-1080`/`FEAT-1090` — both are confirmed independent by `ADS-103` §2 (disjoint WRAM fields from bad-zone/motif-variant; independent-but-coexisting writers with `FEAT-1080`'s own `TEMPO_IDX`/`DENSITY_IDX` fields, same "last write wins" contract) — sequencing relative to either is unconstrained, but the `FEAT-1080` interaction needs dedicated verification per Acceptance Criterion 4. |
| **Risks** | Musical-naturalness risk (`ADS-103` §8, carried forward): 4 fixed phase durations may not read as a natural, non-mechanical arc — a `09-content-review` judgment call, not resolvable at the spec stage. BUILD/`OVERLOAD` interaction risk (`ADS-103` §8/§9, carried forward): a BUILD-phase density target high enough to itself trigger overload is a real tuning question, not a defined contract — needs empirical checking once phase values are chosen. `FEAT-1080` mid-transition-collision risk (`ADS-103` §8, carried forward): reasoned safe by design (disjoint bookkeeping fields) but needs the same class of adversarial-test confirmation `VR-1090` already demonstrated is necessary before trusting an "independent, no interaction" claim at face value. |
| **Open Questions** | (1) Exact phase target `TEMPO_IDX`/`DENSITY_IDX` values and durations — data/implementation decisions deferred to `07-implementation-planning`/the implementing package, per `ADS-103`'s own "shape, not values" framing, consistent with every prior preset-table deferral. (2) Should BUILD's density target be tuned to deliberately stay below `OVERLOAD_THRESHOLD`'s reachable range, or is an occasional overload during BUILD a *desirable* dramatic moment? Genuinely open, a `09-content-review` musical judgment call (`ADS-103` §9). (3) Should style-drift (R220's slower-cadence half of the same finding) eventually reuse this exact state machine, or a separate mechanism? Deliberately deferred past this v1 (`ADS-103` §9) — a future `03-architecture-design-synthesis` pass once v1's own timing/tuning is known from real content-review data. (4) Should `SCALE_IDX`/`DUTY_BIAS` eventually join the phase envelope (a fuller "style" move per phase)? Not requested by any FR above — a natural v1.1 extension, not addressed here. (5) Should the visualizer (`FEAT-1040`) ever gain a song-form-phase-reactive signal? Not requested by any FR above, named here only so a future intake request has a clear place to land, same pattern every prior FS's own analogous Open Question already used. (6) GDS-09 (Interface Specification) remains `⛔ Planned` — same standing gap every prior FS has flagged, not blocking. |
| **Related ADRs** | None directly — `ADS-103`'s Decision Log carries this feature's binding decisions (no dedicated ADR was needed, same pattern `ADS-101`/`ADS-102` already established). |
