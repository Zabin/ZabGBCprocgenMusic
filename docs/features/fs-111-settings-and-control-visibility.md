# FS-111 — Settings & Control Visibility

| Field | Content |
|---|---|
| **Feature ID** | `FS-111` / `FEAT-1110` |
| **Title** | Settings & Control Visibility |
| **Purpose** | Close the long-standing gap where the shipped visualizer (`IP-0006`/`FEAT-1040`) shows only per-channel activity and a calm/bad-zone palette swap, never the *value* of any tracked parameter or which button edits which parameter — a listener currently discovers what the D-pad/A/B/Start do only by trial and error. Directly answers the user's own request (`BL-0051`, "visuals that indicate the different settings in place and what the buttons influence (eg octave and tempo)"), per `ADS-104`'s design. |
| **Scope** | 5 new bar-height indicator tiles, one per base control (`TEMPO_IDX`, `OCTAVE_IDX`, `SCALE_IDX`, `DENSITY_IDX`, `CHMIX_IDX`), each showing that parameter's current index as a filled-bar-height glyph (0 to N-1 rows filled, bottom-up), reusing the existing BG palette — no new palette, no font/text rendering. Purely additive to the existing channel-activity tiles and calm/bad-zone palette swap, which are unchanged. The static control legend (which on-screen bar corresponds to which button) is explicitly out of scope for this spec — an off-ROM/external concern (manual, box art), per `ADS-104` §3/§7, not an in-ROM feature. The four newer per-feature reactive signals (Scheme-select identity, `STYLE_TABLE`'s implicit style identity, `MOTIF_VARIANT_IDX`, `SONG_STATE`) are explicitly out of scope — named, deferred follow-on work using the same reusable bar-tile mechanism (`ADS-104` §9), not built here. |
| **Requirements Implemented** | FR-1350 (5 indicators, one per base control, bar-height glyph), FR-1360 (same-frame update as the underlying parameter), FR-1370 (purely additive, no change to existing channel-activity/palette behavior), FR-1380 (at least one indicator demonstrably live-reflects a manual button change), NFR-1140 (ROM/VRAM budget), NFR-1150 (VBlank-gated, comparable per-frame cost), NFR-1160 (no new input control) |
| **User Workflows** | 1. Listener glances at the screen and sees 5 small bar-height indicators alongside the existing 4 channel-activity tiles, each showing how "full" its parameter currently is. 2. Listener presses D-pad Up (steps `TEMPO_IDX`, `FR-1020`) and sees the tempo indicator's fill level visibly change on the same frame — the same immediacy already established for the existing channel-activity tiles' own per-frame reaction. 3. Listener presses D-pad Left/Right (`OCTAVE_IDX`, `FR-1030`), A (`SCALE_IDX`, `FR-1040`), B (`DENSITY_IDX`, `FR-1050`), or Start (`CHMIX_IDX`, `FR-1060`) and sees that control's own indicator update the same way. 4. Listener presses Select (`FR-1070`, full reset) and sees all 5 indicators immediately reflect the restored preset values, the same frame as every other reset field. 5. Developer/coding agent verifying no regression confirms the existing channel-activity tiles and calm/bad-zone palette swap behave identically with the new indicators present. |
| **System Behaviour** | **5 indicators, one per base control** (FR-1350): a new per-frame routine reads `TEMPO_IDX`/`OCTAVE_IDX`/`SCALE_IDX`/`DENSITY_IDX`/`CHMIX_IDX` (`music_engine.py`, `FEAT-1000`/`FEAT-1010`/`FEAT-1070`) and, for each, writes one of 8 new tile-pattern indices (fill levels 0-7) to one of 5 new fixed BG tilemap cells — the same "index selects which of N pre-rendered patterns to show" idiom the existing `CHANNEL_CELLS`/`TILE_OFF`/`TILE_ON` mechanism already uses, extended from 2 patterns to 8. **Same-frame update** (FR-1360): this routine runs from the same per-frame `update_visuals` call site the existing channel-activity/palette logic already runs from, so an indicator's fill level is never more than one frame stale relative to its parameter — no new latency beyond the existing per-frame visualizer cadence. **Purely additive** (FR-1370): the new routine only ever writes to its own 5 new tilemap cells; it never touches `CHANNEL_CELLS`, `TILE_OFF`/`TILE_ON`, or the `CALM_PALETTE`/`BAD_PALETTE` write path — verified by inspection that the new code and the existing code touch disjoint tilemap addresses and call no shared mutating routine. **Live reflection of a manual change** (FR-1380): pressing any of D-pad Up/Down/Left/Right, A, B, or Start changes the corresponding WRAM field the same frame (per `FR-1020`-`FR-1060`'s existing edge-triggered contract); the next `update_visuals` call (already running every frame) picks up the new value and writes the corresponding new tile-pattern index — no additional trigger or hook is needed beyond the existing per-frame read. **Edge case — index range narrower than 8 fill levels**: `OCTAVE_IDX` (4 possible values, `OCTAVE_ROOT_HZ` has 4 entries) and `SCALE_IDX` (4 possible values, `SCALES` has 4 entries) each only ever produce fill levels 0-3 out of the tile set's full 0-7 range, unlike `TEMPO_IDX`/`DENSITY_IDX`/`CHMIX_IDX` (8 possible values each) which use the full range — this is a legitimate difference in effective glyph resolution per control, not a defect (each indicator still shows its own parameter's actual current index; a 4-value control simply never lights more than half the bar), named explicitly rather than silently assumed uniform (Open Question 1). **Edge case — Select reset**: on a Select press (`FR-1070`), all 5 underlying WRAM fields are reloaded to their preset values on that same frame; the existing per-frame `update_visuals` call (already running unconditionally every frame, before or after the reset write depending on call order) reflects the restored values within one frame, the same latency bound as any other manual change — no special-case handling is needed since this feature reads, never writes, the reset fields. |
| **Module Responsibilities** | `visuals.py` gains the new tile-pattern data (8 new 8×8 2bpp bar-height patterns, alongside the existing `_tile_off_bytes()`/`_tile_on_bytes()` — GDS-03 §1's "one job per file," visualizer data/rendering logic stays this module's job) and a new per-frame routine (`_emit_update_settings_row` or equivalent), called from `build_visuals_update_asm` alongside the existing channel-activity/palette logic — the same call site, not a new dispatch mechanism. `music_engine.py` is entirely unaffected — this feature only reads `TEMPO_IDX`/`OCTAVE_IDX`/`SCALE_IDX`/`DENSITY_IDX`/`CHMIX_IDX`, writes nothing, adds no new WRAM field or table (`NFR-1160`). `input_map.py` is entirely unaffected — no new input control (`NFR-1160`). `build_rom.py` gains no new responsibility beyond the existing tile-data/tilemap-init emission `build_visuals_init_asm` already performs, extended to 8 new patterns and 5 new tilemap-cell initializations. |
| **Interfaces Used** | The existing `TEMPO_IDX`/`OCTAVE_IDX`/`SCALE_IDX`/`DENSITY_IDX` WRAM addresses (`0xC000`-`0xC003`, `FEAT-1000`/`FEAT-1010`) and `CHMIX_IDX` (`0xC004`, `FEAT-1070`) — read only, the same read-only access pattern `update_visuals` already uses for `NR52`/`BAD_ZONE_FLAGS`. The existing `update_visuals`/`build_visuals_update_asm` per-frame call site (`FEAT-1040`/`IP-0006`) — this feature adds new tile-pattern-index writes alongside the existing channel-activity/palette writes, not a new dispatch mechanism. The existing tile-pattern/tilemap-cell idiom `CHANNEL_CELLS`/`TILE_OFF`/`TILE_ON` already establishes (`visuals.py`) — extended from a 2-pattern/4-cell shape to an 8-pattern/5-cell shape, the same mechanism, not a new one. GDS-09 (Interface Specification) remains `⛔ Planned`, same standing gap every prior FS has flagged — not blocking. |
| **Data Model Changes** | New ROM-resident data (against GDS-07, which does not yet reserve this): 8 new tile patterns, 16 bytes each (8×8, 2bpp) = 128 bytes (`ADS-104` §6's own estimate), alongside the existing `TILE_OFF`/`TILE_ON` pattern pair. New tilemap-cell reservations (existing tilemap address space, no new VRAM region): 5 new fixed BG tilemap cells, analogous to the existing `CHANNEL_CELLS` list — their exact tilemap addresses are an implementation-package-level layout decision (`ADS-104` §8's own flagged risk: whether free tilemap cells actually exist without crowding `CHANNEL_CELLS`, to be confirmed against the actual shipped tilemap arrangement, not assumed here). No new WRAM address — this feature reads existing fields only. |
| **State Changes** | None — this feature introduces no new engine state, persistent state, or state machine. It is a pure read-and-render function of 5 already-existing WRAM fields, recomputed fresh every frame (the same "no state of its own" characterization already true of the existing channel-activity/palette-swap logic it sits alongside). |
| **Error Handling** | No new failure mode — the 5 source fields are already range-checked/wrapped by their own existing edge-triggered handlers (`FR-1020`-`FR-1060`), so an out-of-range tile-pattern-index lookup cannot occur by construction (Open Question 1 notes that `OCTAVE_IDX`/`SCALE_IDX`'s narrower 0-3 range simply means those two indicators never select pattern indices 4-7, not an error condition). No new external input, no new randomness source. |
| **Performance Considerations** | NFR-1140 (ROM/VRAM budget): 128 bytes of new ROM tile-pattern data plus 5 new tilemap-cell writes (existing tilemap space, no new VRAM region), negligible against the measured ~254/256-free tile-slot headroom (`R104` §7-8) and free-ROM headroom (`ADR-0002`'s own instrumentation; re-confirmed by the implementing package per that same method). NFR-1150 (per-frame cost): the new routine performs 5 reads + 5 tilemap-byte writes per frame, VBlank-gated the same way every existing visualizer write already is (GDS-03's own timing-discipline invariant, unchanged) — comparable cost to the existing 4-cell channel-activity update, verified against the existing VBlank-timing budget (`NFR-1010`), not by static cycle analysis alone. |
| **Integrity Considerations** | None — no save data, no checksums beyond the existing header (unaffected). This feature is a deterministic function of already-deterministic WRAM state; it introduces no new non-determinism of its own. |
| **Acceptance Criteria** | (1) The visualizer displays 5 distinct indicator tiles, each showing the current index (0-7, per each control's own actual range) of `TEMPO_IDX`, `OCTAVE_IDX`, `SCALE_IDX`, `DENSITY_IDX`, and `CHMIX_IDX` respectively, as a filled-bar-height glyph. (2) Each indicator's displayed fill level matches its underlying parameter's actual current value on every frame sampled, with no more than one frame of staleness after a change. (3) The existing 4 channel-activity tiles and calm/bad-zone palette swap behave identically with the 5 new indicators present — verified by confirming this feature's own code never writes `CHANNEL_CELLS`, `TILE_OFF`/`TILE_ON`, or the palette-write routine (same "this package's own writes never touch those addresses" framing `IP-1080`'s own acceptance criterion (4) used). (4) At least one indicator (any) demonstrably reflects a manual D-pad/A/B/Start-driven parameter change, confirmed by reading the relevant tilemap cell's pattern index immediately after the corresponding button press. (5) Select resets all 5 indicators to reflect the restored preset values, the same frame class as every other reset field. (6) All existing `test_rom.py` suites (`T1`-`T17`) remain green — no regression. |
| **Verification Plan** | Test — a new `test_rom.py` suite reads the 5 new tilemap cells' pattern indices directly and asserts each matches its source WRAM field's current value across a range of manually-driven button presses (acceptance criteria 1-2, 4); confirms the existing `CHANNEL_CELLS`/palette-swap tilemap cells are unaffected by this feature's own writes over the same run (acceptance criterion 3, same assertion shape `IP-1080`'s own `T15.5`/`FS-110`'s own acceptance criterion (3) already established); drives a Select press and confirms all 5 indicators immediately reflect the restored preset (acceptance criterion 5). Acceptance criterion 6 is the standing full-suite regression gate every feature already carries. Whether 5 unlabeled bars are actually legible/useful without the external static legend (`ADS-104` §8's own risk) is a `09-content-review` judgment call, not an automated assertion. |
| **Dependencies** | `FEAT-1040`/`IP-0006` (`VERIFIED`) — extends its existing `update_visuals` call site and tile-pattern/tilemap-cell idiom. `FEAT-1000`/`FEAT-1010` (`TEMPO_IDX`/`OCTAVE_IDX`/`SCALE_IDX`/`DENSITY_IDX`, all `VERIFIED`) and `FEAT-1070` (`CHMIX_IDX`, `VERIFIED`) — read only. No dependency on `FEAT-1080`/`FEAT-1090`/`FEAT-1100` (style/motif-variant/song-form) — this feature's v1 scope reads only the 5 pre-existing base-control fields, per `ADS-104` §4/§7's explicit v1-scope boundary; their own reactive signals are a named, deferred v1.1+ extension (Open Question 5), not a dependency incurred now. |
| **Risks** | Tilemap-layout risk (`ADS-104` §8, carried forward): whether the actual shipped tilemap arrangement has free cells for 5 more indicators without crowding the existing 4 channel-activity cells is not re-verified here — flagged for `07-implementation-planning`/`08-code-implementation` to confirm directly against `visuals.py`'s current tilemap layout, not assumed. Legibility risk (`ADS-104` §8, carried forward): a bar-height glyph alone, without the external static legend, may not read as useful to a first-time listener — a `09-content-review` judgment call, not resolvable at the spec stage. `CHMIX_IDX` ambiguity risk (`ADS-104` §8, carried forward): the `CHMIX_IDX` bar shows which preset is active, not what each preset means (it drives channel-mix, scheme-select, and style simultaneously per `ADS-100`/`ADS-101`) — an accepted v1 limitation, not a defect, since decoding preset meaning already requires the same external legend the base controls do. |
| **Open Questions** | (1) Should `OCTAVE_IDX`/`SCALE_IDX`'s indicators use a narrower 4-level tile set (matching their actual 0-3 range) instead of sharing the same 8-level tile set as `TEMPO_IDX`/`DENSITY_IDX`/`CHMIX_IDX`, for a more legible "how full is this, relative to its own range" reading? Not decided here — an implementation-package-level content/legibility decision, same `BL-0005`-class deferral as every other visual-tuning question in this project. (2) Exact tilemap cell placement for the 5 new indicators (which screen positions, relative to the existing 4 channel-activity cells) — flagged in Risks, a `07-implementation-planning`/`08-code-implementation` decision against the actual shipped tilemap layout, not fixed here. (3) Exact bar-tile pixel design (which fill pattern reads most clearly at GBC's actual screen size/viewing distance) — a content-authoring/tuning decision, not fixed here, same `BL-0005`-class deferral as every other visual/preset-value decision in this project. (4) Should the static control legend (which bar = which button) ever be represented in-ROM (e.g. a help/pause screen)? Genuinely open (`ADS-104` §9) — deliberately out of this spec's scope; this design's v1 assumes external-only. (5) Should Scheme-select identity, style identity, `MOTIF_VARIANT_IDX`, and `SONG_STATE` each eventually get their own indicator too, using the same 8-level bar-tile mechanism this feature establishes? Deliberately deferred past v1 (`ADS-104` §9) — a natural v1.1+ extension once this feature ships and is content-reviewed, not built here. (6) GDS-09 (Interface Specification) remains `⛔ Planned` — same standing gap every prior FS has flagged, not blocking. |
| **Related ADRs** | None directly — `ADS-104`'s Decision Log carries this feature's binding decisions (no dedicated ADR was needed, same pattern `ADS-101`/`ADS-102`/`ADS-103` already established). |
