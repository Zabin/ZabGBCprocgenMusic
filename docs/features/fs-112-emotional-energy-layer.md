# FS-112 — Emotional/Energy Layer

| Field | Content |
|---|---|
| **Feature ID** | `FS-112` · Catalog source: `FEAT-1120` (roadmap R7) |
| **Title** | Emotional/Energy Layer |
| **Purpose** | Make the engine's already-tracked internal state legible as mood (valence-arousal), per `R221`'s circumplex model, as a read/interpret layer laying groundwork for roadmap R9's future mood-reactive visualizer work. Not a player-facing feature in itself — carried forward verbatim from `FEAT-1120`'s own catalog entry. |
| **Scope** | Two new derived WRAM bytes, `AROUSAL` and `VALENCE`, computed from `TEMPO_IDX`/`DENSITY_IDX` and `SCALE_IDX` respectively, recomputed **only** at the write sites that can change those inputs. No new player control, no visualizer change, no new PSG register write. Consistent with `FEAT-1120`'s stated boundary — `visuals.py` and `input_map.py`'s control mapping are explicitly out of scope. |
| **Requirements Implemented** | `FR-1390`, `FR-1400`, `FR-1410`, `FR-1420`, `NFR-1170`, `NFR-1180`. **`CR-0002` (`CHMIX_IDX`-derived active-channel count in `AROUSAL`) is explicitly excluded** — it is a Candidate Requirement, not baselined, per `docs/requirements/01-functional-requirements.md`'s own disposition. |
| **User Workflows** | None — this is not a listener/player-facing feature. The relevant "workflow" is a build-pipeline one: (1) the engine boots, `AROUSAL`/`VALENCE` are computed from the boot-preset indices before the first frame is observed; (2) the listener presses D-pad Up/Down/A/B, changing `TEMPO_IDX`/`SCALE_IDX`/`DENSITY_IDX` — `AROUSAL`/`VALENCE` are recomputed within the same frame; (3) the engine autonomously transitions song-form phases (`FEAT-1100`), overwriting `TEMPO_IDX`/`DENSITY_IDX` — `AROUSAL` is recomputed on the same tick; (4) the listener presses Select — all steering indices reset to boot-preset values, and `AROUSAL`/`VALENCE` are recomputed to match on the same frame. No step in any of these workflows produces an observable change to sound or the visualizer; a future `FS` for roadmap R9 is what will give this state a workflow a listener actually experiences. |
| **System Behaviour** | **Normal path**: `AROUSAL` (0-15) increases or stays the same as `TEMPO_IDX` and/or `DENSITY_IDX` increase, and never decreases when either increases while the other is held constant (`FR-1390`'s monotonicity requirement) — verified per input-step direction below. `VALENCE` (0-15) is a fixed function of `SCALE_IDX`'s 4 possible values (`FR-1400`) — each of the 4 scale/mode selections maps to exactly one `VALENCE` output, and switching `SCALE_IDX` always produces the same `VALENCE` output for the same input, run to run. **Edge case — simultaneous input**: if a song-form phase transition (`FEAT-1100`) and a manual D-pad edge land on the same frame, both write `TEMPO_IDX`/`DENSITY_IDX` through the existing "last write wins" call-order contract (`GDS-09` §5 — `apply_input` runs before `engine_tick`, so `engine_tick`'s own `_emit_song_tick` write wins if both land the same frame); this feature's recompute call, wherever it is placed relative to that write, must read the *final* post-both-writes value, not an intermediate one — see Interfaces Used for exactly where the recompute call must sit in the per-frame order to guarantee this. **Edge case — Select-reset mid-drift**: if `TEMPO_IDX`/`SCALE_IDX`/`DENSITY_IDX` have drifted away from the boot preset via button presses, a Select press resets all three and `AROUSAL`/`VALENCE` must reflect the *restored preset* values on the reset frame itself, not the pre-reset drifted values (`FR-1420`) — same "no stale read on the reset frame" discipline every other reset-to-preset field already follows (`GDS-03` §5). **Edge case — boot**: `AROUSAL`/`VALENCE` must not read `0x00` (an uninitialized WRAM byte's likely value) on the very first frame; they must already reflect the boot-preset `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX` values before any test or future consumer reads them (`FR-1420`). |
| **Module Responsibilities** | `music_engine.py` owns the derivation routine and both new WRAM bytes' only writer — consistent with `GDS-03`'s module boundaries: `music_engine.py` already owns every other derived-from-steering-state computation (`_emit_badzone_tick` is the direct precedent — also a derived summary of engine state, also WRAM-resident, also computed by this module, not by `input_map.py` or `visuals.py`). `input_map.py` is a **caller** of the new recompute routine at its own edge-triggered call sites (see Interfaces Used) but does not own the derivation logic itself — the same relationship it already has with `music_engine.py`'s `init_engine` (which `input_map.py` already calls on a Select edge, per `GDS-09`'s label-namespace contract). `visuals.py` has **no role in this feature** — confirmed against `ADS-105` §2's own explicit statement that `visuals.py` is untouched. |
| **Interfaces Used** | **Confirmed against the current tree, not trusted from `ADS-105`'s own citations alone** — one correction found in this pass (see Risks). The new derivation routine (name TBD at implementation time, e.g. `_emit_mood_update`) is called from: (1) `input_map.py`'s `_step_on_bit(rom, J_UP, TEMPO_IDX, +1, 0x07, 'ai_up')` (`input_map.py:54`); (2) `_step_on_bit(rom, J_DOWN, TEMPO_IDX, -1, 0x07, 'ai_down')` (`input_map.py:55`); (3) `_step_on_bit(rom, J_A, SCALE_IDX, +1, 0x03, 'ai_a')` (`input_map.py:58`); (4) `_step_on_bit(rom, J_B, DENSITY_IDX, +1, 0x07, 'ai_b')` (`input_map.py:59`) — **all four verified present at these exact lines**, called from `build_input_asm`'s `apply_input` body; (5) `music_engine.py`'s `_emit_song_tick` (`music_engine.py:1067`) — verified present; (6) `music_engine.py`'s `build_engine_asm`, at the `init_engine` label (`music_engine.py:1120`) — verified present, serving both the boot path and the Select-reset path (the same label is both, per `GDS-03`'s existing reset-to-preset design). Per `GDS-09` §5's per-frame call-order contract (`apply_input` → `engine_tick`, and within `apply_input`'s own body, each `_step_on_bit` call runs and returns before the next), the recompute call at each `_step_on_bit` site must be placed **after** that call's own `LD_nn_A` write completes (so it reads the post-write value, not the pre-write one) — a detail for `07-implementation-planning`'s Implementation Tasks, not decided here, but the ordering constraint itself is a real interface contract this spec is recording. |
| **Data Model Changes** | Two new WRAM bytes: `AROUSAL` and `VALENCE` (exact addresses per `GDS-07`'s next-free-pair convention, `0xC068`-`0xC069` as of this writing — confirm against `GDS-07`'s live headroom figure at implementation time, since other features may have claimed addresses in between). Both are read-only from every module's perspective except the one new derivation routine in `music_engine.py`, which is their sole writer — no other module writes these bytes, ever. |
| **State Changes** | `AROUSAL`/`VALENCE` are not independent state machines — they have no transitions of their own beyond "recomputed from current inputs." They are created (given a correct value) at boot, and updated (never "transitioned" in the state-machine sense) at each of the six trigger call sites in Interfaces Used. They are never retired — they exist for the life of a running session. |
| **Error Handling** | None applicable — there is no failure mode a derived, always-recomputed value can enter that isn't already covered by its own recompute guarantee (`FR-1410`). If a future trigger site is added to the tree without a corresponding recompute call (the risk `ADS-105`'s own Risks field names), the failure mode is silent staleness, not a crash — no error-handling contract is needed for this, only the test coverage named in Verification Plan. |
| **Performance Considerations** | `NFR-1170` (zero unconditional per-frame CPU cost — this feature's binding, load-bearing constraint, cited directly to `IP-9030`'s VBlank-budget measurement earlier this session) and `NFR-1180` (bounded WRAM: 2 bytes; bounded per-trigger-site cost). Neither of the six trigger sites in Interfaces Used runs inside the exhausted VBlank window `IP-9030` measured (`read_joypad`→`apply_input`→`engine_tick`, i.e. these routines already execute inside it every frame regardless of this feature) — so this feature's cost is "how much heavier does an already-executing routine get," not "a new addition to an unvisited code path." `07-implementation-planning`'s own package must state the actual cycle cost once real opcodes are chosen, per `NFR-1180`'s own wording. |
| **Integrity Considerations** | None — no save data, no checksum, no persisted state beyond ordinary WRAM (`MSTR-001` C2, no SRAM/battery commitment, unaffected by this feature). |
| **Acceptance Criteria** | (1) `AROUSAL` read after driving `TEMPO_IDX` to its minimum and maximum (holding `DENSITY_IDX` fixed) never decreases as `TEMPO_IDX` increases; same check with `DENSITY_IDX` varied and `TEMPO_IDX` fixed. (2) `VALENCE` read at each of `SCALE_IDX`'s 4 values is a fixed, distinct-or-repeatable mapping — the same `SCALE_IDX` value always produces the same `VALENCE` output within a run. (3) `AROUSAL`/`VALENCE` are recomputed within the same frame as a write to any of `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX`, checked independently at each of the six trigger sites named in Interfaces Used (not merely "at least one," given `ADS-105`'s own named risk of a missed site). (4) `AROUSAL`/`VALENCE` hold correct boot-preset-derived values on the first frame after boot, before any input. (5) `AROUSAL`/`VALENCE` hold correct restored-preset-derived values on the exact frame a Select-reset completes, even when read immediately (no settling-frame grace period). **On exact formulas**: this spec deliberately does **not** pin down literal lookup-table byte values, matching `04-requirements-engineering`'s own judgment call that `FR-1390`/`FR-1400`'s acceptance criteria stay at the behavioral level (monotonicity, fixed mapping) rather than implementation-grade tables — a specific formula is `07-implementation-planning`'s to propose against these behavioral criteria, and pinning it here would cross into implementation detail this stage's own scope boundary excludes. |
| **Verification Plan** | New `test_rom.py` suite **`T20`** (next free suite number after `T19`, `IP-9030`'s VBlank budget assertion). Per acceptance criterion: (1)/(2) **Test** — drive the relevant control to each value, read `AROUSAL`/`VALENCE`, assert monotonicity/fixed-mapping directly. (3) **Test** — for each of the six trigger sites independently, drive it and assert the derived value changed (or, for song-tick/reset, drive to a known transition and assert on that exact frame). (4)/(5) **Test** — read immediately after `fresh_boot()`/immediately after a Select-reset frame. **Named risk, stated honestly rather than glossed** (per `ADS-105`'s own Risks field): this feature has **no consumer yet** — `visuals.py` doesn't read `AROUSAL`/`VALENCE` (roadmap R9, separately blocked, is the eventual consumer), so `T20`'s checks can only assert the derived value against the *same formula* the implementation itself uses. This is inherently weaker than an independent behavioral assertion (the kind `test_rom.py` prefers project-wide, per `R305`) — a bug in both the check's expected-value calculation and the implementation's own formula, made the same way, would not be caught. Named explicitly so `09-package-verification`/`10-integration-review` know the coverage limit up front, not discover it. |
| **Dependencies** | `FEAT-1010` (Input Steering — this feature's four input-step trigger sites) and `FEAT-1020` (Reset-to-Preset — the shared reset/boot-init trigger site), both `VERIFIED` and shipped. No dependency on `FEAT-1080`/`FEAT-1090`/`FEAT-1100`/`FEAT-1110` despite reading adjacent WRAM territory — confirmed by `05-feature-decomposition`'s own Feature Review, not re-derived here. |
| **Risks** | **A real drift found and corrected in this pass, not merely inherited from `ADS-105`.** `ADS-105` §2 describes "3 input-step routines" as trigger sites; the actual tree has **4** — `TEMPO_IDX` has two writers (D-pad Up *and* Down), not one, so the correct trigger-site count is **6 total** (4 input-step calls + song-tick + reset/boot-init), not 5. This spec's Interfaces Used field states the corrected count and the exact 4 input-step call sites by line number; `07-implementation-planning` should cite this spec's corrected count, not `ADS-105`'s original 5, when scoping Implementation Tasks. **The missed-trigger-site risk `ADS-105` itself named is real and now slightly sharper**: if the count was wrong once (5 vs. 6) before any code existed, a future package adding a seventh way to write `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX` without adding a recompute call is a plausible, not merely theoretical, failure mode — `T20`'s per-site checks (Verification Plan) are this feature's only defense against it, and they must be updated if a future trigger site is ever added. **No-consumer-yet risk** (see Verification Plan) is inherited from `ADS-105` and restated here rather than resolved — it is a property of this feature's own scope, not a defect to fix. |
| **Open Questions** | (1) **Exact `AROUSAL`/`VALENCE` derivation formulas** — deliberately left open by both `ADS-105` §9 OQ1 and `04-requirements-engineering`'s own delta pass; resolved at `07-implementation-planning` grain, not here (see Acceptance Criteria's own note). (2) **New module name for the derivation routine** — not decided (`ADS-105` §9 OQ4 leaves naming to the implementer); a minor detail, `07`'s to pick. Neither question blocks implementation-readiness — both are ordinary planning-grain decisions, not design ambiguities. |
| **Related ADRs** | None directly binding — `ADR-0002`'s single-32KB-bank/no-bank-switching constraint applies generally (unaffected here, 2 bytes against ample WRAM headroom) but this feature makes no new ADR-level commitment. |
