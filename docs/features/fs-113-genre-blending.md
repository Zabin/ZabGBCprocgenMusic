# FS-113 — Genre Blending

| Field | Content |
|---|---|
| **Feature ID** | `FS-113`, source `FEAT-1130` (roadmap R8, Genre Blending) |
| **Title** | Genre Blending |
| **Purpose** | A session can audibly drift from one shipped genre style toward another over a few frames, rather than only hard-cutting between `STYLE_TABLE` presets on a Start press — per `BL-0020`'s "solo or in combination" framing and `R220`'s style-drift finding (`FEAT-1130`'s Purpose, carried forward verbatim). |
| **Scope** | Interpolating `TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS` between the current and newly-selected `STYLE_TABLE` rows over 4 discrete steps, triggered by the Start press that already changes `CHMIX_IDX`. **Excludes**: `SCALE_IDX` interpolation (categorical, hard-switches — owned by the unchanged half of `FR-1240`), any new physical input, continuous/fine-grained interpolation, and the exact tuned blend duration (deferred to content review, `ADS-107` §9 OQ1). |
| **Requirements Implemented** | `FR-1470`, `FR-1480`, `FR-1490`, `NFR-1210`, `NFR-1220`, `NFR-1230`. **`FR-1240` is AMENDED by this feature, not implemented fresh** — it predates `FEAT-1130` (shipped under `FEAT-1080`/R5); this feature changes 3 of its 4 fields' guarantee (`TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS` no longer land the same frame) while leaving `SCALE_IDX`'s guarantee untouched. Listed separately from the six "Implemented" IDs above for exactly this reason. |
| **User Workflows** | (1) Listener presses Start → `CHMIX_IDX` steps by 1 (always changes, see System Behaviour) → the newly selected style's `SCALE_IDX` is audible on the very next note-onset; `TEMPO_IDX`/`DENSITY_IDX`/timbre glide toward the new style's values over the following frames, reaching the target exactly. (2) Listener presses Start again before the glide finishes → the glide restarts from wherever it currently is, toward the second new selection; the first target is abandoned, never reached. (3) Listener presses Start exactly once and waits → after the blend completes, engine state is bit-for-bit identical to what `FR-1240`'s original instant-apply would have produced — no side effect distinguishes "blended slowly" from "applied instantly," once done. |
| **System Behaviour** | **Trigger — confirmed unconditional on every Start press.** `CHMIX_IDX` is stepped by `INC_A` then masked `AND 0x07` (`input_map.py:70-72`) — a pure mod-8 increment. Because the step is always exactly `+1 mod 8`, `CHMIX_IDX` **never lands on its own pre-press value**; every Start press is a real preset change and therefore always begins a blend. There is no "Start pressed but nothing changed" case to specify — confirmed by inspection of the increment, not assumed. **Normal path:** on the Start edge, before `CHMIX_IDX`'s new value is used to look up the target row: capture `TEMPO_IDX`→`BLEND_SRC_TEMPO`, `DENSITY_IDX`→`BLEND_SRC_DENSITY`, `DUTY_BIAS`→`BLEND_SRC_DUTY`; write `STYLE_TABLE[CHMIX_IDX].scale_idx`→`SCALE_IDX` immediately (same frame, unconditionally); set `BLEND_STEP`←0. Every subsequent frame's `_emit_blend_tick`, while `BLEND_STEP`<4: increment `BLEND_STEP`, recompute `TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS` as `BLEND_SRC_* + (STYLE_TABLE[CHMIX_IDX].* − BLEND_SRC_*) × BLEND_STEP / 4` (integer, exact at `BLEND_STEP`=4). Once `BLEND_STEP`=4, `_emit_blend_tick` is a comparison and a return every frame — no further writes. **Edge case — mid-blend restart (`FR-1490`), stated precisely so `07` need not re-derive it:** if a second Start press lands while `1 ≤ BLEND_STEP ≤ 3` (blend in progress, not yet complete), the *same* begin-blend sequence above runs again, using `TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS`'s **current, partially-interpolated** values (not the original `BLEND_SRC_*`, and not the abandoned first target) as the new `BLEND_SRC_*`. `SCALE_IDX` applies immediately for the *second* press's target exactly as it does for any press — **this holds even when a press restarts an in-progress blend; `SCALE_IDX` is never itself "mid-blend," it simply re-fires its own always-immediate rule on every press, independent of `BLEND_STEP`'s value at press time.** `BLEND_STEP` resets to 0 for the new blend; the value it held from the interrupted blend is discarded, never read again. **Edge case — Start press exactly on `BLEND_STEP`=4 (blend just completed, or long since idle):** behaves identically to the normal path — there is no distinct "resume" state, since a complete blend and an idle engine are the same state (`BLEND_STEP`=4 in both). |
| **Module Responsibilities** | `music_engine.py` owns: the 4 new WRAM constants; a new `_emit_begin_blend(rom)` routine (replacing the direct `_emit_apply_style` call at the Start handler, or called from within it — `07`'s exact call-site choice, not decided here) implementing the capture-and-immediate-`SCALE_IDX` step above; a new `_emit_blend_tick(rom)` routine implementing the per-frame step, called from `engine_tick` alongside the existing `rom.CALL('song_tick')` (`music_engine.py:1255`, verified present at this exact line against the current tree). `input_map.py` owns: the Start-press handler (`input_map.py:64-74`, verified present) — its `CHMIX_IDX` step is unchanged; its call to apply the style changes from `_emit_apply_style` to `_emit_begin_blend`. Neither `visuals.py` nor any input control mapping changes. |
| **Interfaces Used** | `music_engine.py`'s `STYLE_TABLE` (read-only, `FEAT-1080`'s existing ROM table — this feature never writes it); `input_map.py`'s existing Start-edge detection (`GDS-03` §3, no new control, per `R217`'s no-free-input finding, confirmed by `ADS-107` §1); `GDS-09` §5's per-frame call-order contract (`_emit_blend_tick`'s call site relative to `song_tick`, `badzone_tick`, `gen_tick_*` — order among these three is not specified as load-bearing by `ADS-107`; confirmed no ordering dependency exists, since all three read/write disjoint fields, same reasoning `ADS-103`'s own independence argument used). |
| **Data Model Changes** | 4 new WRAM bytes (`GDS-07` §6, next free address `0xC070` at authoring time, re-confirm at implementation time per standing discipline): `BLEND_SRC_TEMPO`, `BLEND_SRC_DENSITY`, `BLEND_SRC_DUTY` (each 1 byte, snapshot of the blend's starting values), `BLEND_STEP` (1 byte, 0-4, doubles as progress index and completion flag). No SRAM. No change to any existing WRAM field's meaning — `TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS`/`SCALE_IDX` keep their existing addresses and existing readers; only *when* the first three are written changes. |
| **State Changes** | New transient state: a **Blend**, existing only while `0 < BLEND_STEP < 4`; created on a Start-press edge, advanced once per frame, retired (implicitly — no explicit "not blending" flag beyond `BLEND_STEP`=4) when it reaches its terminal step. Never persists across a Select-reset in a special way — `ADS-107` names no interaction with `IP-0007`'s reset path; a Select-reset's own existing full-state reinitialization (`FR-1070`) is unaffected by this feature and this feature does not need to special-case it, since Select's reset writes `TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS`/`SCALE_IDX` directly and unconditionally regardless of `BLEND_STEP`'s value — **flagged here as a confirmed non-interaction, not left implicit**: if a blend is mid-flight when Select is pressed, the reset's own writes simply overwrite whatever the blend had reached, and `BLEND_STEP` is left however it was (stale, but harmless, since the next Start press's begin-blend sequence resets it to 0 unconditionally before any read of it matters again). |
| **Error Handling** | None applicable — no invalid input state exists (Start always changes `CHMIX_IDX`, per System Behaviour); no data-integrity concern (no SRAM); a corrupted `BLEND_STEP` value (e.g. somehow >4, not reachable via this feature's own logic) would simply cause `_emit_blend_tick`'s `>=4` guard to treat it as already-complete — a safe, non-crashing degenerate case, not a scenario requiring dedicated handling. |
| **Performance Considerations** | `NFR-1210`: steady-state cost (the vast majority of frames, blend complete) is one comparison and a return — negligible against `engine_tick`'s existing cost. Active-blend cost (at most 4 frames per Start press, a rare event at 60fps) performs 3 small interpolation computations, each a subtraction, a multiply by a value 0-4, and a shift-by-2 — no SM83 division anywhere. Must be costed at implementation time against `IP-9030`'s measured VBlank margin (`GDS-06` §2.2a), same discipline `ADS-105`/`FS-112` already applied. |
| **Integrity Considerations** | None — no SRAM, no checksum, no save format. Determinism: the blend is a pure function of `BLEND_SRC_*`/`BLEND_STEP`/`STYLE_TABLE`, no RNG involvement, so a given input sequence always produces the same interpolated trajectory — relevant to `09-package-verification`'s eventual reproducibility check, not a new integrity risk. |
| **Acceptance Criteria** | (1) On a Start press, `SCALE_IDX` reads the newly selected style's value on the same frame the press is processed. (2) `BLEND_SRC_TEMPO`/`DENSITY`/`DUTY` read the pre-press `TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS` values, captured on that same frame. (3) `BLEND_STEP` reaches exactly 4 within **N frames** of the press, where **N is a first-guess constant fixed at implementation time** (`BL-0005`-class deferral, tuned later by `09-content-review` — the exact frame count is deliberately not specified here, the same judgment call `04` made keeping `AROUSAL`'s formula out of the requirements baseline; the criterion is testable regardless of N's eventual value). (4) At `BLEND_STEP`=4, `TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS` exactly equal `STYLE_TABLE[CHMIX_IDX]`'s corresponding values — no rounding-short defect. (5) A second Start press while `1 ≤ BLEND_STEP ≤ 3` causes `BLEND_SRC_*` to be overwritten with the engine's then-current `TEMPO_IDX`/`DENSITY_IDX`/`DUTY_BIAS` (not the original pre-first-press values), `SCALE_IDX` to apply the second press's target immediately, and `BLEND_STEP` to reset to 0. (6) At `CHMIX_IDX`=0 (default preset), a full blend cycle lands on exactly the values `FR-1240`'s original instant-apply already produced for the default preset — no regression to the shipped default's own character. |
| **Verification Plan** | New `test_rom.py` suite **`T21`** (next free number after `T20`). Per acceptance criterion: (1)/(2) same-frame WRAM read after a Start press (Test). (3) frame-count-to-completion assertion against the implementation's own fixed N (Test). (4) exact-value assertion at `BLEND_STEP`=4 across at least 2 non-default style pairs (Test). (5) forced mid-blend Start press (drive to a known `BLEND_STEP` in `{1,2,3}`, press Start again, assert the restart contract) — same "force the exact collision frame" methodology `T17.6`/`T19` already established (Test). (6) default-preset regression check, reusing `T15`'s own existing default-value fixture (Test). **`T15`'s existing same-frame-landing checks must be updated in the same package that builds this feature** (`BL-0099`) — not a separate follow-up, since shipping this feature without updating them would leave `T15` asserting a contract this feature deliberately breaks. Named explicitly so `07-implementation-planning` schedules it as one Implementation Task, not an afterthought. |
| **Dependencies** | `FEAT-1080` (`STYLE_TABLE`, `VERIFIED`, shipped — the rows this feature interpolates between; read-only dependency, no modification). `FEAT-1100` at the design-pattern level only (reuses the countdown-then-overwrite *shape*, not its WRAM or its `SONG_STATE`/`SONG_STATE_TIMER` fields — `ADS-107`'s own explicit decision, carried forward, not re-litigated here). No dependency on `FEAT-1090`/`FEAT-1110`/`FEAT-1120`. |
| **Risks** | The roadmap's own named risk (`04-release-roadmap.md` R8) — interpolation producing an audibly "in-between-and-bad" state — is not resolved by this spec; it is explicitly a `09-content-review` judgment, per `NFR-1230`. `ADS-107` §9 OQ3 (interaction between this feature's `TEMPO_IDX`/`DENSITY_IDX` writes and `FEAT-1100`'s own song-form-phase writes to the same two fields) remains genuinely open — both mechanisms exist and both can write the same addresses on different triggers (a Start press vs. an autonomous song-phase transition); this spec does not add a precedence rule beyond `GDS-09` §5's existing per-frame call-order contract (whichever call in `engine_tick` runs later that frame wins, the same "last write wins, no special-casing" contract `FR-1240`/`FR-1320` already established for their own trigger pair) — carried forward as an Open Question below rather than silently assumed safe. |
| **Open Questions** | (1) **Exact blend duration N** — first-guess placeholder at implementation time, resolved by content review post-shipping, not by this spec (`ADS-107` §9 OQ1). (2) **Should blend duration vary by style-pair distance** — explicitly deferred past v1 by `ADS-107` §9 OQ2; this spec assumes fixed N regardless of distance, consistent with that deferral. (3) **`TEMPO_IDX`/`DENSITY_IDX` dual-writer interaction with `FEAT-1100`'s song-form ticks** (Risks, above) — `ADS-107` §9 OQ3 names this as needing empirical confirmation at implementation/verification time, not an architectural rule; carried forward unresolved, to `07-implementation-planning`/`09-package-verification`, matching `ADS-107`'s own explicit non-resolution. |
| **Related ADRs** | None directly — `ADS-107`'s own Decision Log carries every binding decision this spec is grounded in; no ADR was needed for this feature (same as `FEAT-1080`/`FEAT-1100` before it). |
