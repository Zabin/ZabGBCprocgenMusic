# FS-114 — Harmonic Coordination via a Shared Chord Context

| Field | Content |
|---|---|
| **Feature ID** | `FS-114`, source `FEAT-1150` (`BL-0119` remediation; `ADS-108` as amended by its own §11/D13, and `ADR-0004`) |
| **Title** | Harmonic Coordination via a Shared Chord Context |
| **Purpose** | The three pitched channels stop being three independent random walks that happen to share a scale, and start playing the same music. `BL-0119` measured the defect on the shipped ROM — a near-uniform vertical-interval distribution (the signature of independent random processes) and **36.1 % harsh pairs** (m2, M2, tritone, m7, M7) — and identified it as the direct, measured cause of the project owner's own verdict that the music doesn't sound good. `R211` §5's prior "chord-progression harmony is out of scope" position was formally withdrawn in `R211` §9; `R225` grounds the replacement mechanism. This feature builds it, **on the default boot path**, per the owner's 2026-08-20 release of the preset-0 no-regression standard. |
| **Scope** | A single shared current-chord index in WRAM that every pitched channel reads at its own onset; a hand-authored per-scale chord table; a weighted 4-chord tonic-biased progression; an onset-counted harmonic clock; and three per-voice note-selection rules (bass = root/fifth, melody = chord tone on strong onsets / ±1 step on weak, harmony = chord tone an octave below). This **replaces** the default scheme's LFSR-delta note selection rather than sitting beside it. **Excludes**: phrase structure, rests and cadence (`CR-0003`); harmonizing Scheme E's motif (`CR-0004`); re-rooting the `IP-1060` arpeggio (`CR-0006`); any `SCHEME_TABLE`/`CHMIX_MASKS` migration (`FR-1570`, withdrawn — `ADR-0004`); any new input control; any `visuals.py` change; any retuning of `DISSONANCE_THRESHOLD` (`ADS-108` §9 OQ1, left to measurement). |
| **Requirements Implemented** | `FR-1500`, `FR-1510`, `FR-1520`, `FR-1530`, `FR-1540`, `FR-1550`, `FR-1560`, `FR-1580` (**as amended 2026-08-20 — reversed in place; this feature implements the amended statement, which absorbs the former `CR-0005`**), `FR-1590`, `NFR-1240`, `NFR-1250`, `NFR-1260`, `NFR-1270`. **`FR-1570` is NOT implemented and must not be claimed** — it was withdrawn unimplemented by `ADR-0004`. **`FR-1180` is unchanged and still in force**: scheme selection remains one bit per pitched channel in `CHMIX_MASKS` bits 4-6; only the *meaning of the `0` value* changes, from "unharmonized LFSR walk" to "chord-derived selection." |
| **User Workflows** | (1) Listener powers on → within the usual ~90 boot frames, all three pitched channels sound notes drawn from one shared chord that changes roughly every two seconds, the wave channel alternating that chord's root and fifth underneath. There is no control to press and nothing to discover; this is simply what the ROM now sounds like. (2) Listener presses A (next scale) → the chord vocabulary follows the scale, because chords are stored as scale *degrees*, not pitches; `OCTAVE_IDX` changes flow through unchanged for the same reason. (3) Listener presses Start onto preset 6 → the wave channel switches to Scheme E's unharmonized motif while pulse A/B stay harmonized; the two voices are deliberately not coordinated (`ADS-108` §8 R3, disclosed, increment 2's problem). (4) Listener presses Select → full reset, including the chord context, back to the boot chord with re-randomized LFSR seeds. |
| **System Behaviour** | **The shared context.** Three WRAM bytes: `CHORD_IDX` (0-3, which chord is sounding), `CHORD_ONSET_CTR` (onsets remaining before the chord advances), `CHORD_TOGGLE` (bit0 = bass root/fifth alternation, bit1 = melody strong/weak onset parity). Every pitched channel reads `CHORD_IDX` at its own onset; **no pitched channel reads any other channel's generation state** (`FR-1500`), which is what keeps cost linear in voices and every rule local. <br><br>**The harmonic clock (pulse A's onset branch only).** On each pulse-A onset: decrement `CHORD_ONSET_CTR`. If it reaches zero → step pulse A's own LFSR, index `CHORD_TRANSITION[CHORD_IDX*4 + (lfsr & 3)]`, write the result to `CHORD_IDX`, reload `CHORD_ONSET_CTR` to **N=4**, and **set** `CHORD_TOGGLE` bit1 (so the onset on which the chord changes is always a strong one). Otherwise → **toggle** `CHORD_TOGGLE` bit1. Because N is even and the parity is forced on every chord change, the phase is stable and cannot drift: strong onsets are the 1st and 3rd of each four-onset group, weak onsets the 2nd and 4th. Pulse A is the driver because it is the fastest pitched onset (30 frames at boot defaults vs. the wave channel's 60, so the clock never starves) and because its onset bookkeeping runs even when the channel is mix-excluded (`IP-9010` gates only the register writes) — so a preset that mutes pulse A still advances the harmony. The clock is **not** coupled to `SONG_STATE`'s timer (different cadence; `IP-1100`'s disjointness is preserved). <br><br>**Per-voice note selection**, each replacing the LFSR-delta step at that channel's onset: <br>• **Wave (bass)** — degree = `CHORD_TABLE[SCALE_IDX][CHORD_IDX][0]` (root) or `[2]` (fifth), chosen by `CHORD_TOGGLE` bit0, which is then toggled. No LFSR step at all; strictly cheaper than what it replaces. <br>• **Pulse A (melody)** — on a **strong** onset (bit1 set): step its LFSR, take 2 bits, index `MELODY_PICK` (a 4-entry table of chord-tone slots, `[0,1,2,1]` — root/third/fifth/third, third-weighted) and read `CHORD_TABLE[SCALE_IDX][CHORD_IDX][that slot]`. On a **weak** onset: the existing LFSR → `DELTA_TABLE` ±1 walk, **byte-for-byte the shipped code path**, which supplies the passing/neighbour tone between chord tones. <br>• **Pulse B (harmony)** — always a chord tone, picked from its own LFSR through a *differently weighted* 4-entry table `HARMONY_PICK` = `[2,0,2,1]` (fifth-weighted), and placed an **octave** below pulse A by setting pulse B's build-time `octave_delta` from `0` to `-1`. <br><br>**Why a table and not arithmetic** (`FR-1510`): the obvious "chord tones are root, root+2, root+4 in scale degrees" is *incorrect* on this project's data. `SCALE_SEMITONES` rows are 8 entries whose 8th duplicates the 1st, and every degree is masked `AND 0x07`, so third-stacking across the octave seam lands a scale step wrong — the V chord's fifth computes as degree 8 → masks to 0 (C) where the correct pitch is D. A hand-authored table takes the octave decision at authoring time for free. <br><br>**Bad-zone reconciliation** (`FR-1590`, `ADS-108` D8). The harmonized path **skips** the dissonance tonic-pull override — a deliberate strong-onset chord tone must not be silently un-harmonized by the very mechanism the harmony makes unnecessary — and **keeps** stuck-note and overload recovery unchanged, since both are orthogonal to harmony. Implementation-wise this is a jump past the dissonance block into the stuck block, not a new flag. Scheme E's path is unaffected and still receives the dissonance override exactly as it does today. Dissonance *scoring* itself is untouched: it still runs every frame over all three pitched channels and still drives the visualizer palette. |
| **Module Responsibilities** | `music_engine.py` (`08-code-implementation`) owns: the three new WRAM constants; the harmonic-clock block inside `gen_tick_pa`'s existing onset branch; the three per-voice note-selection blocks replacing the LFSR-delta block in `_emit_channel_gen`'s fall-through (non-Scheme-E) path; the `FR-1590` dissonance-skip jump; pulse B's `octave_delta` change in the `CHANNELS` table; the new tables' emission into the ROM's data section; and `init_engine`'s initialization of all three new bytes on boot **and** Select-reset. `music_data.py` (`08-content-authoring` surface, but authored in the same package — see Risks) owns `CHORD_TABLE`, `CHORD_TRANSITION`, `MELODY_PICK`, `HARMONY_PICK` as pure data. `test_rom.py` owns the new `T22` suite and the re-authoring of `T5`/`T6`-class assertions. **`visuals.py`, `input_map.py`, `patterns.py`, `tiles.py`, `gbc_lib.py` are untouched.** |
| **Interfaces Used** | `_emit_channel_gen`'s existing `gt_delta_ready_{suffix}` convergence point and its `SUB_D` target-degree→signed-delta idiom (already used by Scheme E's motif lookup) — chord-derived selection produces a *target degree* and reuses that idiom verbatim, so the entire downstream path (bad-zone stuck/overload, `STALE_COUNT` bookkeeping, onset-window counting, `CHMIX_MASKS` mute gating, note-table addressing, duty selection, timer reload) is reused unchanged. `_ld_hl_label` for forward table references. `SCALE_IDX`/`OCTAVE_IDX`/`CHMIX_IDX` read-only. `GDS-09` §5's per-frame call-order contract — **no new call is added to `engine_tick`**, which is the load-bearing property of this design. |
| **Data Model Changes** | **3 new WRAM bytes** (`GDS-07` §6; `0xC077` recorded as next free — re-confirm at implementation time per standing discipline): `CHORD_IDX` `0xC077`, `CHORD_ONSET_CTR` `0xC078`, `CHORD_TOGGLE` `0xC079`. `0xC020`-`0xC037` is **not** reclaimed (reserved `HIST_*`, `BL-0013`). **4 new ROM tables**: `CHORD_TABLE` 4 scales × 4 chords × 3 tones = **48 B**, `CHORD_TRANSITION` 4 × 4 = **16 B**, `MELODY_PICK` **4 B**, `HARMONY_PICK` **4 B** — 72 B of data plus emitted code, inside `NFR-1250`'s ~100 B table budget. No SRAM. **No existing WRAM field changes meaning or address.** `CUR_DEGREE_*` keeps its exact semantics (a 0-7 scale degree) — only how the next value is *chosen* changes, which is why every existing reader keeps working. |
| **State Changes** | New persistent engine state: the **chord context**, live from boot to power-off, advancing autonomously. `init_engine` must set `CHORD_IDX`←0 (tonic), `CHORD_ONSET_CTR`←N, `CHORD_TOGGLE`←`0b10` (bass takes the root first, melody's first onset is strong) on **both** boot and Select-reset — the same explicit-initialization discipline `VR-1130`'s `BLEND_STEP` defect established as non-optional (an uninitialized counter there let a stale blend corrupt a fresh reset). **Retired state**: the unharmonized independent walk is no longer reachable on any preset. `GDS-04` §4.1's fixed-point rule still holds — preset 0 and the boot preset remain the same thing — under that section's own 2026-08-20 amendment separating it from the released historical-no-regression reading. |
| **Error Handling** | No invalid input state exists — every field is bounded by construction: `CHORD_IDX` only ever receives a `CHORD_TRANSITION` entry (all in 0-3), `CHORD_ONSET_CTR` is reloaded from a constant and only decremented, and the chord-tone slot index comes from a 4-entry table of values 0-2. A corrupted `CHORD_IDX` >3 would index past `CHORD_TABLE`'s row into adjacent ROM and produce a wrong-but-in-range degree after the existing `AND 0x07` mask — audible as a wrong note, never a crash or a hang. No masking-off or clamping code is spent defending against a state this feature cannot reach. |
| **Performance Considerations** | **The hardest constraint in the project, and the one that shapes the whole design.** `R101` §8.5 measured `read_joypad`+`apply_input`+`engine_tick` consuming ~9 of VBlank's 10 scanlines *on every frame*, and `IP-9040` was abandoned (`BL-0113`) for adding a handful of unconditional per-frame instructions. `R225` §3h measured the escape route: **95.1 % of frames execute no pitched-onset branch at all**, pulse A and pulse B are phase-locked so the worst case is 2 coincident onsets rather than 3, and a chord change at N=4 lands on **~0.8 % of frames**. Every instruction this feature adds therefore lives inside an onset branch that already exists — **`NFR-1240`: no unconditional per-frame work, zero new `engine_tick` calls.** Two further properties make the onset-path cost itself favourable rather than merely acceptable: the wave channel's rule *removes* an LFSR step and a `DELTA_TABLE` read, and the melody's weak-onset limb *is* the existing code, so only the strong limb (half of pulse A's onsets) is new work. `VIS_ENTRY_LY` must be measured on a chord-transition frame specifically (`NFR-1260`), and a regression there is **blocking, not absorbable**. |
| **Integrity Considerations** | None — no SRAM, no checksum, no save format. Determinism: the chord walk is driven by pulse A's existing LFSR, which `IP-0007` seeds from `DIV` on boot/Select, so runs differ from each other exactly as much as they already do — this feature adds no new randomness source (`NFR-1110`'s established principle) and removes none. |
| **Acceptance Criteria** | (1) `CHORD_IDX` changes value over a run and only ever holds 0-3. (2) `CHORD_IDX` changes on exactly every 4th pulse-A onset, and on no other frame. (3) On every wave-channel onset, `CUR_DEGREE_WV` equals `CHORD_TABLE[SCALE_IDX][CHORD_IDX][0]` or `[2]`, alternating between them across successive onsets. (4) On a strong pulse-A onset, `CUR_DEGREE_PA` equals one of the three tones of `CHORD_TABLE[SCALE_IDX][CHORD_IDX]`. (5) On a weak pulse-A onset, `CUR_DEGREE_PA` differs from its previous value by at most 1 (mod 8). (6) On every pulse-B onset, `CUR_DEGREE_PB` equals one of the current chord's three tones. (7) All three new WRAM bytes hold their specified initial values immediately after boot **and** immediately after a Select press. (8) `VIS_ENTRY_LY` stays within `144`-`153` on a chord-transition frame, in addition to `T19`'s existing five frame classes (`NFR-1260`). (9) **The acceptance measurement** (`NFR-1270`): vertical-interval statistics captured live from the built ROM, **partitioned by metric strength**, show harsh intervals (m2, M2, tritone, m7, M7) materially reduced on **strong-beat sonorities** against the immediately-preceding commit's ROM measured identically. `R225` §5f's simulation predicts 32.6 % → ~14.9 %; the aggregate figure is expected to improve far less (~28.5 %) and **is not the acceptance instrument** (`BL-0122`). (10) ROM still builds to exactly 32768 bytes with a valid header; full `test_rom.py` suite green (G5). (11) Criteria (3)-(6) are asserted only on frames where `BAD_ZONE_FLAGS`'s stuck bit is clear — stuck recovery deliberately forces a step and may move a degree off its chord tone (`FR-1590` keeps that path), the same exclusion `T14.3`/`T16` already apply for `IP-1090`'s motif assertions. |
| **Verification Plan** | New `test_rom.py` suite **`T22`** (next free after `T21`), one check per acceptance criterion (1)-(8), all Test method. **`T19` gains a sixth frame class** (chord transition) rather than a new suite. **Re-authoring, not addition, is the load-bearing half of this plan**: every existing check that asserts the old unharmonized contract must be re-authored *in the same package*, because shipping this feature without touching them leaves the suite asserting behavior the feature deliberately removes. Named explicitly so `07` schedules it as an Implementation Task and not an afterthought: `T5`/`T6`-class per-channel degree-walk assertions (they currently assert a ±1 stepwise walk for pulse A/B/wave — pulse A's weak onsets still satisfy this, pulse B and wave no longer do), and any check asserting pulse B's register placement now that its `octave_delta` moves. Criterion (9) is **not** a `test_rom.py` check — it is a measurement driver written in a scratchpad and reported in the package's own evidence (a `test_rom.py` assertion on a statistical distribution would be flaky and would not carry the before/after comparison that gives the number meaning). Criterion (9) plus `09-content-review`'s holistic dimension (`R224` §7a — is there a melodic idea you could hum back; does it go somewhere; would you leave it on) together constitute the real acceptance gate; **a green suite is explicitly not sufficient**, which is the precise failure mode `BL-0097` and `BL-0120` both record. |
| **Dependencies** | `FEAT-1000` (core generation, `_emit_channel_gen`'s structure). `FEAT-1070` (`VERIFIED`, shipped — its `gt_delta_ready` convergence point and `SUB_D` idiom are reused verbatim; its Scheme-E path is left untouched). `FEAT-1030`/`IP-0007` (bad-zone detection and recovery — reconciled with, per `FR-1590`, not modified). No dependency on `FEAT-1080`/`1090`/`1100`/`1110`/`1120`/`1130`. **No dependency on any `SCHEME_TABLE` migration** — that work was obviated, not deferred (`ADR-0004`). |
| **Risks** | (1) **The boot sound changes and a body of shipped tests stops describing the engine.** Authorized and expected, but it means a regression in this package cannot be distinguished from the intended change by "did tests break" alone — which is exactly why criterion (9)'s before/after measurement, not the suite, is the acceptance instrument. (2) **VBlank budget.** `IP-9040` died here. Mitigated structurally (nothing unconditional per frame; the bass rule is net cheaper than what it replaces) and measured explicitly by criterion (8) on the chord-transition frame class. Treat a `VIS_ENTRY_LY` regression as blocking. (3) **The bad-zone detector may still fight the generator numerically.** `FR-1590` removes the structural conflict, but `DISSONANCE_THRESHOLD` was never tuned by ear (`BL-0005`) and `BL-0102` already reports a bad-zone-at-boot condition; a deliberate weak-beat passing tone is by construction the thing the detector flees. Left to measurement (`ADS-108` §9 OQ1) — if the engine sits in a bad zone at boot after this change, that is a finding to diagnose, not a reason to lower criterion (9)'s bar. (4) **This package writes both `music_engine.py` and `music_data.py`**, crossing the stage-08 code/content peer seam (`G1`). The data is meaningless without the mechanism and vice versa; splitting them would produce two packages neither of which is independently verifiable, which is the opposite of the seam's purpose. Recorded here for `07` to decide and declare rather than for `08` to discover. (5) **`BL-0119`'s other named symptoms are only partly addressed**: static runs of repeated degrees are reduced (chord tones change with the chord) but not eliminated, and **there are still no rests and nothing that formally resolves** — `CR-0003` owns both, deliberately out of scope. If criterion (9) passes but the holistic review still says "wandering," that is the expected next finding and it routes to `CR-0003`, not back to this feature. |
| **Open Questions** | (1) **Is N=4 onsets per chord right?** First-guess, `BL-0005` class (`ADS-108` §9 OQ4) — resolved by listening, not by this spec. (2) **`FR-1560`'s "distinct from the melody role's chord tone" cannot be implemented literally** without pulse B reading pulse A's `CUR_DEGREE`, which `FR-1500` forbids and which would reintroduce exactly the cross-channel coupling this design exists to remove. This spec implements the *operative* half — `R225` §5f's finding that **octave** separation, not degree separation, is what avoids manufactured sevenths — plus a differently-weighted pick table so the two voices differ statistically rather than by construction. Flagged for `04-requirements-engineering` to reword `FR-1560` at its next natural touch; **not** silently reinterpreted. (3) **Pentatonic's four chord rows are idiomatic judgements, not derivable** (`ADS-108` §9 OQ3): pentatonic has no semitones among its first five degrees, so stacked thirds do not yield triads there. Authored as first-guess pentatonic-idiomatic sonorities; excluding pentatonic was rejected because silently losing the feature on one of four user-selectable scales is a worse listener experience than an imperfect chord set. (4) **`DISSONANCE_THRESHOLD`'s correct value** once the interval distribution is deliberately non-uniform — `ADS-108` §9 OQ1, needs the measurement this package produces, and is a candidate follow-on rather than this package's scope. |
