# FS-115 — The Arpeggio Re-rooted, Gated and Varied

| Field | Content |
|---|---|
| **Feature ID** | `FS-115` · catalog source [`FEAT-1160`](../feature-planning/01-feature-catalog.md) · Epic: the harmonic-coordination remediation stream (same stream as `FEAT-1150`/`FS-114`) |
| **Title** | The arpeggio re-rooted, gated and varied |
| **Purpose** | Stop the arpeggio from fighting the harmony the engine just built, and stop it from being the same figure forever. `IP-1060` added the arpeggio in 2026-07 to *fake* harmony in its absence (`R216`: "implying a chord on a single channel"); `FS-114` then supplied real harmony and the arpeggio was never revisited, so it now stacks a second, differently-rooted triad on the ensemble's own chord — in a 24-frame figure that repeats ~2.5×/second on every note of both pulse channels, forever, with no mechanism by which it could ever vary. The project owner heard this before any document noticed it: **"constant repeated arpeggios."** |
| **Scope** | **In:** what the two pulse channels sound *between* their onsets — which pitches the per-frame frequency rewrite selects, whether it selects any at all on a given note, and how much per-frame work it costs. **Out:** note selection *at* onsets (unchanged, `FS-114`); the wave and noise channels (neither arpeggiates and neither gains the ability here); vibrato's depth/rate and portamento's glide behavior (both must be *preserved* — see Risks — but neither is redesigned); Scheme E (untouched and still unharmonized, `CR-0004`); rests and phrase structure (`CR-0003`); any new input control. |
| **Requirements Implemented** | `FR-1130` (as amended 2026-08-21), `FR-1600`, `FR-1610`, `FR-1620`, `FR-1630`, `NFR-1280`. Acceptance is additionally governed by `NFR-1260` and `NFR-1270` (as amended 2026-08-21 — **sounding-pitch basis**), which this feature does not implement but must satisfy. **`FR-1140` and `FR-1150` are explicitly *not* implemented here and must not regress** — they are shipped, verified behaviors that this feature's own routine produces (see Risks R1). |
| **User Workflows** | **W1 — Boot and listen (the default path).** Player powers on → engine initializes (`FR-1630`) → pulse A/B begin generating. At each pulse-channel onset the channel selects its note per `FS-114`'s unchanged rules, then selects how that note will be articulated for its duration. Over the following seconds the listener hears: chord tones spelled out as figures against the ensemble's own chord; some notes not arpeggiated at all; the two pulse channels not moving in lockstep; and the figure changing from note to note rather than looping.<br>**W2 — A strong melody onset.** Pulse A takes a chord tone (`FR-1550`) → that note is a chord tone → an arpeggio figure is drawn → the note is articulated as a figure over tones of the currently-sounding chord (`FR-1130`, `FR-1610`).<br>**W3 — A weak melody onset (the passing tone).** Pulse A takes a ±1 passing step (`FR-1550`) → that note is **not** a chord tone → the note sustains at its own pitch for its whole duration (`FR-1600`). Vibrato and portamento remain audible on it.<br>**W4 — The chord changes under a sounding note.** The harmonic clock advances `CHORD_IDX` at a pulse-A onset (`FR-1530`). Channels whose notes were selected against the previous chord continue articulating what they were already articulating; each picks up the new chord at its own next onset — the same next-onset granularity `FR-1190` already establishes.<br>**W5 — The player changes scale or octave mid-note.** A/D-pad press updates the parameter. The change lands audibly on each pitched channel from **its next onset** rather than mid-note (`FR-1620`); the onset write itself uses the values current at that onset, so nothing feels unresponsive beyond one note duration.<br>**W6 — Select reset.** Every pitched channel's arpeggio state is re-established, so nothing sounding after the reset derives from pitch material chosen before it (`FR-1630`). |
| **System Behaviour** | **B1 (`FR-1130`).** While a pulse channel is arpeggiating, the pitches it cycles through are tones of the **currently-sounding shared chord** (`FR-1500`'s `CHORD_IDX`, through the existing per-scale chord table), never offsets applied to the channel's own scale degree. Consequence: every arpeggiated pitch is a chord tone by construction, and the octave-seam wrap that degree-offset arithmetic produced (`ADS-108` D3, `R225` §3g) cannot arise, because the chord table already resolved it at authoring time.<br>**B2 (`FR-1600`).** A channel arpeggiates only while the note it holds is itself a tone of the current chord. A non-chord tone sustains. **Sustaining means the channel's frequency register continues to be written every frame with that note's own pitch** — it never means the per-frame write stops. This sentence is the whole of Risk R1's mitigation and is normative.<br>**B3 (`FR-1610`).** The figure is chosen **per onset** from a set of alternatives, drawn from that channel's own randomness source. The set contains at least one member under which the note does not arpeggiate at all, so `FR-1600`'s gate is expressible as a member of the same set rather than as a separate branch. Members differ in **how many of the note's frames sound a pitch other than the onset pitch**, not merely in the order of pitches. Pulse A and pulse B draw independently and neither reads the other's private state.<br>**B4 (edge — chord change mid-note, W4).** A note articulated against a chord that has since advanced is not re-derived mid-note. This is deliberate: re-deriving would require per-frame chord reads (forbidden by `NFR-1240`/`NFR-1280`) and would make an already-sounding note lurch. Worst case is one note's articulation trailing the chord by up to its own remaining duration, which is bounded by the note rate.<br>**B5 (edge — `FR-1620`).** A `SCALE_IDX`/`OCTAVE_IDX` change during a sounding note does not alter that note's pitch mid-flight. Both the arpeggio's pitches and the sustained pitch follow from the resolution taken at that channel's most recent onset.<br>**B6 (edge — mute/unmute).** A channel excluded by `CHMIX_MASKS` (`FR-1000`) continues its internal bookkeeping exactly as today (`IP-9010`'s established contract), so it resumes musically current rather than frozen; nothing in this feature changes that.<br>**B7 (edge — bad zone).** Bad-zone recovery acts on note *selection* at onsets (`FR-1590`, `IP-0007`), which this feature does not touch. A stuck-flag-forced step that lands on a non-chord tone therefore sustains rather than arpeggiating, by B2 — which is correct: recovery's job is to move the note, not to decorate it. |
| **Module Responsibilities** | **`music_engine.py`** (GDS-03 §1: all sound-channel generation logic) — the per-frame articulation routine and the per-onset resolution/draw that feeds it, both inside routines that already exist. **`music_data.py`** (GDS-03 §1: curated musical building blocks) — the figure-alternatives table replacing the current fixed offset table, and any weighting data it carries. **`test_rom.py`** — the new and re-authored checks named under Verification Plan. **Untouched:** `visuals.py`, `input_map.py`, `patterns.py`, `tiles.py`, `gbc_lib.py`, `build_rom.py`, `wram_constants.py`. No new module (GDS-03's one-job-per-file inventory is unchanged). |
| **Interfaces Used** | Existing only. The per-frame articulation routine keeps its current call site and its current position in `engine_tick`'s call order — **that ordering is load-bearing for `FR-1150`'s portamento and must not change** (`Claude.md`'s sound-design section states this explicitly). The per-onset work extends branches that already exist in the per-channel generation routine, the same convergence discipline `FS-114` used. `build_rom.py`'s existing ROM-table emission path carries the new data table with no new mechanism. No `build_engine_asm` patch-point key is added or changed (GDS-09). |
| **Data Model Changes** | **ROM:** the fixed arpeggio-offset table is replaced by a figure-alternatives table; net ROM change is expected to be small and is bounded by `NFR-1250`-class discipline (`R104` §7's measured headroom). The existing per-scale chord table is **read, not modified** — this feature adds no chord data. **WRAM:** per-channel state is added to hold what the per-frame routine must no longer recompute (`NFR-1280`) plus which figure the current note drew. GDS-07 records the next free address as `0xC07A` with ample headroom; exact addresses and packing are `07`/`08`'s to fix against GDS-07, not this spec's. **SRAM:** none — this project persists nothing (`MSTR-001` C2). |
| **State Changes** | Created at each pulse-channel onset: that note's resolved articulation state (which figure, and whatever the per-frame routine needs to sound it). Consumed every frame by the articulation routine. Retired implicitly at the next onset of the same channel. Re-established on **both** boot and Select (`FR-1630`) — this is stated as a requirement rather than left implicit precisely because `VR-1130` already found this defect class once (`BLEND_STEP` left uninitialized, letting a stale mechanism corrupt a fresh reset). |
| **Error Handling** | The mechanism has no failure mode that can halt or silence the engine: every path writes a frequency every frame, and the only inputs are a chord index already constrained to 0-3 (`FR-1500`) and a drawn figure index bounded by its own table. The two states that would be *wrong* rather than *failed* are both covered above: stale post-reset state (prevented by `FR-1630`) and an articulation trailing a chord change (bounded and accepted, B4). A channel muted by `CHMIX_MASKS` follows `IP-9010`'s existing contract unchanged. |
| **Performance Considerations** | **This is the feature's hardest constraint and one of its deliverables.** `NFR-1280`: the unconditional per-frame cost must **strictly decrease**. Today the routine costs roughly 60 emitted instructions per channel per frame on its common path — ~120 per frame across both pulse channels — of which ~32 re-derive a note-table address from `SCALE_IDX`/`OCTAVE_IDX`, values that change only at onsets and input presses. `R101` §8.5 / `GDS-06` §2.2a record the VBlank budget as already exhausted (`VIS_ENTRY_LY` 152-153 of a 144-153 window), and `IP-9040` is `BLOCKED` over three instructions (`BL-0113`). The design therefore moves resolution to the onset (conditional work, `NFR-1240`'s existing allowance) and leaves the per-frame path doing strictly less. `NFR-1260`: `VIS_ENTRY_LY` must stay within 144-153 on every frame class `T19` covers; **a regression is blocking, not absorbable.** |
| **Integrity Considerations** | Determinism is preserved (`MSTR-001` C6): the figure draw uses each channel's existing LFSR, introducing no new randomness source, so a fixed seed still yields a fixed sequence and headless verification stays byte-reproducible. No persisted state, no checksum surface. Build reproducibility is unaffected — the new table is build-time data like every other. |
| **Acceptance Criteria** | **A1.** Over a long headless run at boot defaults, **every** pitch sounded by a pulse channel while that channel is arpeggiating is a tone of the chord `CHORD_IDX` names at that moment (`FR-1130`). Measured on **sounding** pitch. Baseline for comparison: 46.4 %.<br>**A2.** On weak pulse-A onsets (the passing tones), the channel's sounding pitch is constant for the note's duration apart from vibrato (`FR-1600`, `FR-1550`).<br>**A3.** Across a long run, more than one distinct figure is observed on each pulse channel, and at least one note per channel is observed not arpeggiating at all (`FR-1610`).<br>**A4.** The two pulse channels are observed articulating differently as the same time (`FR-1610`, independent draws).<br>**A5.** `FR-1140`'s vibrato and `FR-1150`'s portamento remain observable **on a sustained, non-arpeggiating note** — the check that does not exist today and that Risk R1 exists to force.<br>**A6.** A scale or octave change during a sounding note changes that channel's pitch from its next onset, not mid-note (`FR-1620`).<br>**A7.** After boot and after Select, arpeggio state holds defined values and no pre-reset pitch material sounds (`FR-1630`).<br>**A8.** `VIS_ENTRY_LY` stays within 144-153 on every frame class `T19` covers (`NFR-1260`), **and** the measured per-frame cost is lower than the pre-change build's (`NFR-1280`).<br>**A9.** `NFR-1270`'s strong-beat-partitioned harsh-interval rate, **measured on sounding pitch**, improves against the immediately-preceding commit's ROM under identical conditions. Baselines to beat, on that basis: strong 25.7 %, weak 36.1 %, aggregate 30.9 %.<br>**A10.** ROM still builds to exactly 32768 bytes with a valid header; full suite green (G5). |
| **Verification Plan** | A1-A4, A6, A7 — **Test**, a new `test_rom.py` suite (`T23`), driving the ROM headlessly and asserting on WRAM articulation state plus sounding pitch reconstructed at the same instant (never from `SEMI_*`, per `BL-0124`). A5 — **Test**, and it must be a *new* check: no existing check asserts a glide occurred, which is exactly why R1 is survivable-but-invisible today. A8 — **Test** via `T19`'s existing frame classes, plus **Analysis** (instruction-count comparison of the emitted routine, before vs after) for the strictly-decreased half, since `VIS_ENTRY_LY` alone proves "within budget," not "cheaper." A9 — **Demonstration**, an out-of-suite measurement driver run against both commits' ROMs under identical conditions, reported in the implementing package's evidence whatever it says. A10 — the standing G5 gates. **Re-authored, not added:** any existing check that asserts the shipped fixed arpeggio pattern (`T`-checks referencing the offset table or a 4-step cycle) must be **re-derived against the new contract**, never loosened until it stops failing — `FS-114`'s implementation record shows a loosened check is how a real off-by-one nearly shipped. |
| **Dependencies** | [`FS-114`](fs-114-harmonic-coordination.md) / `FEAT-1150` — `COMPLETE`, and its chord table plus `CHORD_IDX` broadcast field are exactly what this feature reads. `FEAT-1060`/`IP-1060`+`IP-1061` (shipped, `VERIFIED`) — this feature modifies their routine and must preserve two of its four effects. `IP-9010`'s mute contract and `IP-0007`'s bad-zone paths are consumed unchanged. No dependency on R8 or R9 in either direction. |
| **Risks** | **R1 (High, `BL-0130`) — implementing the gate as "skip the per-frame write" would silently delete portamento and vibrato.** `FR-1150`'s glide is not produced by a glide routine: it is produced *by this very routine's* per-frame frequency rewrite carrying the pitch from the outgoing note to the new one, which is why `engine_tick` calls it *before* the generation tick. `FR-1140`'s vibrato rides the same write. The natural reading of "a non-chord tone does not arpeggiate" is "don't write" — and that reading removes both effects **on every weak melody onset, which is where portamento matters most**, while every existing test still passes because nothing asserts a glide occurred. Mitigations: B2's normative sentence; A5's new check; and this risk restated in the implementing package.<br>**R2 (High) — the VBlank budget.** The single most likely reason this feature fails, exactly as it was for `FS-114`. Mitigated structurally (all new work at onsets; the per-frame path required to shrink) and measured explicitly; blocking if regressed.<br>**R3 (Medium) — this changes the boot sound again**, so "did tests break" no longer distinguishes a regression from the intended change. The before/after sounding-pitch measurement and the listening pass are the acceptance instruments, not the suite. Same posture `FS-114` took, and for the same reason.<br>**R4 (Medium) — the fix may not answer the complaint.** The complaint is qualitative. Chord-correctness is measurable and variation is countable, but "does it still read as a constant looping figure" is not, and a green suite has never predicted it (`BL-0097`/`BL-0120`). `ADR-0005` names the bounded fallback: an all-sustain figure table *is* retirement, a data edit rather than a redesign.<br>**R5 (Low-Medium) — this feature spans the stage-08 code/content peer seam** (`music_engine.py` + `music_data.py`), as `FS-114` did. Declared here rather than discovered at execution: the table is meaningless without the mechanism and the mechanism cannot be tested without the table, so splitting yields two packages neither independently verifiable. |
| **Open Questions** | **OQ1 — the contents and size of the figure-alternatives table.** `FR-1610` fixes its two structural constraints (a no-arpeggio member; members differing in rhythmic surface, not only pitch order) and deliberately not its contents, which are first-guess placeholder data of the same `BL-0005` class as every other untuned table here. Matters because it is what the listener actually hears; resolved by `09-content-review`'s ear, not by this document. **OQ2 — whether the sub-tick rate should also vary.** Weighed and deferred at `03` (`BL-0129`, `ADS-108` §12.5) with a named trigger: a listening pass reporting the result *varied in pitch but monotonous in pulse*. Matters only if that trigger fires; resolved by `03-architecture-design-synthesis` re-opening D14. **OQ3 — whether pulse B should now take a different octave.** `ADS-108` §12.4 records that this feature *unblocks* `BL-0125`/`FR-1560`'s withheld octave half at no per-frame cost, and explicitly does **not** exercise it. Matters because `FS-114` withheld it for a reason that this feature removes; resolved by `04`/`03` deciding whether anything now demands it — deliberately not taken here, to keep this feature's before/after attributable to one change. |
