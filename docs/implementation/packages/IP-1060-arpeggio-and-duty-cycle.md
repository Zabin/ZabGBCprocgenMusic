# IP-1060 — Arpeggio + Duty-Cycle Variation

| Field | Content |
|---|---|
| **Package ID** | `IP-1060` |
| **Objective** | Add arpeggio-as-polyphony (rapid chord-implying frequency cycling within a held note) and per-onset duty-cycle variation to the pitched channels, per `FS-106`/`R216`. |
| **Requirements Covered** | `FR-1130` (arpeggio), `FR-1160` (duty-cycle variation), `NFR-1040` (ROM/WRAM budget), `NFR-1050` (per-frame timing budget) |
| **Architecture Components** | GDS-03 §1 (module ownership — stays in `music_engine.py`, no new module), `FS-106` (System Behaviour, Module Responsibilities) |
| **Interfaces** | Extends the existing `CHANNELS`-list parameterization of `_emit_channel_gen` (`music_engine.py:128-136`) with new per-channel fields: an arpeggio sub-tick WRAM address and (for pulse A/B only — the wave channel keeps its existing role, R207's bass/timbre framing doesn't call for arpeggiating the bass voice) a duty-cycle register address (`NR11`/`NR21`). |
| **Files to Create/Modify** | `music_engine.py` only: (1) new `ARPEGGIO_OFFSETS` ROM table (3 entries, scale-degree deltas from the root — e.g. `[0, 2, 4]`, chosen to land on scale-relative approximations of a root/third/fifth without a full chord-theory table); (2) new `DUTY_BY_DEGREE` ROM table (4 entries, one per `NR11`/`NR21` duty-bits value, indexed by `CUR_DEGREE mod 4`); (3) new per-pitched-channel WRAM: an arpeggio sub-tick counter + step index (may be packed into one byte — implementation's choice, document whichever layout is chosen); (4) `_emit_channel_gen` (`music_engine.py:196-328`) extended: a new sub-tick block (runs every frame, independent of the existing note-timer countdown) that decrements the arpeggio counter, and on expiry reloads it and advances the step index (mod 3), then recomputes the *effective* degree as `(CUR_DEGREE + ARPEGGIO_OFFSETS[step]) mod 8` and rewrites only the frequency registers (`NR13` plain write, `NR14` written with bit7 clear — no retrigger, so the existing decreasing envelope continues decaying naturally across the arpeggiated note, the standard chiptune arpeggio technique per `R216`); the existing per-onset register-write block additionally writes the channel's duty register (`NR11`/`NR21`) from `DUTY_BY_DEGREE[CUR_DEGREE mod 4]` (pulse A/B only — wave/noise channels have no duty concept, skip). (5) `init_engine` (`music_engine.py:503-539`): zero the new arpeggio counters/step indices for pulse A/B (and wave, if wave also gets arpeggio — see Implementation Tasks) on both boot and Select-reset, same pattern `IP-0005` already audited every other per-channel field against. |
| **Implementation Tasks** | (1) Decide whether wave gets arpeggio too, or stays arpeggio-free (its existing half-rate/bass role, `IP-0002`, may read better *without* fast pitch cycling — a judgment call `FS-106` left to this package; default recommendation: pulse A/B only, wave excluded, document the choice either way). (2) Add `ARPEGGIO_OFFSETS`/`DUTY_BY_DEGREE` tables. (3) Add the new WRAM fields to `CHANNELS` (or a parallel small table, whichever keeps the existing tuple shape from getting unwieldy — implementation's call, document it). (4) Implement the sub-tick arpeggio block — pick a sub-tick reload value (a few frames, e.g. 4-8) fast enough to read as an arpeggio, slow enough to stay musically legible; not tuned by ear here (same "first-guess placeholder" convention as `BL-0005`'s other tunables — flag it the same way). (5) Implement the duty-cycle write in the existing onset block. (6) Zero all new WRAM in `init_engine`, both boot and Select paths. |
| **Tests to Add** | New `test_rom.py` suite (e.g. `T11`, coordinate the exact number with whatever `IP-1061` lands on if built in the same session): (a) boot, run enough frames to cover several arpeggio sub-ticks within one note's duration, assert the frequency-register-value-implied degree (via a WRAM mirror if one is added per `FS-106`'s Open Question, or via `run-driftune`'s register-read capability) takes at least 2 distinct values within a single note (confirming sub-tick cycling is live, not just onset-time); (b) assert `NR11` (or `NR21`) takes at least 2 distinct values across a sustained run (duty-cycle variation live); (c) full regression — all pre-existing suites (T1-T10) still green. |
| **Documentation Updates** | `Claude.md` (new "Arpeggio + duty-cycle" bullet under Known Good Behavior, or a new subsection matching `IP-0007`'s "Autonomous bad-zone avoidance" precedent), `memory.md` (WRAM quick-reference gains the new arpeggio-counter/step-index addresses), GDS-07 (the new WRAM addresses are a real data-model addition — extend GDS-07 §3 the same way `BL-0018`'s reconciliation just did, in-place, not deferred). |
| **Definition of Done** | Arpeggio audibly/measurably cycles frequency within a note's duration on at least pulse A; duty-cycle varies across onsets on at least pulse A; Select-reset zeroes all new state; every pre-existing test still passes; ROM still builds to 32768 bytes with a valid header. |
| **Verification Checklist** | ROM builds, exactly 32768 bytes, valid header (G5). Full `test_rom.py` suite passes, including the new suite (G5). `09-package-verification` independently drives a non-default scale/octave (per this project's tunable-parameter standard, `VR-0002`-`VR-0004`'s precedent) and confirms arpeggio/duty-cycle behavior holds off the default preset too. |
| **Dependencies** | `IP-0001`-`IP-0003` (`_emit_channel_gen`/`CHANNELS`, all `VERIFIED`). No dependency on `IP-9010`/`IP-9020`/`IP-1061` (sequencing-only, per the TWBS). |
| **Risks** | ROM budget: 2 new small tables (≤8 bytes total) + a handful of new WRAM bytes — negligible per `NFR-1040`. Musical-quality risk: the arpeggio sub-tick rate and offset table are first-guess placeholders, same as every other untuned constant in this project (`BL-0005`'s existing disposition covers this — fold in, don't file a new entry). Interaction risk with bad-zone scoring: arpeggio's sub-tick frequency rewrites must NOT touch `CUR_DEGREE_*`/`STALE_COUNT_*`/dissonance scoring — those stay driven by the note-onset degree only, per `FR-1130`'s "for the duration of that note" framing; the implementing package must not accidentally wire the sub-tick block into the onset-only bookkeeping. |
| **Rollback Considerations** | Fully additive (new tables, new WRAM, a new sub-tick code block, one new register write in the existing onset block) — reverting is a straightforward commit revert; no WRAM address reused from elsewhere, no existing behavior removed. |
