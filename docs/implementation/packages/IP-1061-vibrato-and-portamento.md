# IP-1061 — Vibrato + Portamento

| Field | Content |
|---|---|
| **Package ID** | `IP-1061` |
| **Objective** | Add periodic pitch vibrato and multi-frame portamento glide to the pitched channels, per `FS-106`/`R216`. Builds on `IP-1060`'s arpeggio sub-tick pattern for its own per-frame frequency-write hook, but is a functionally independent addition (sequencing dependency only, per the TWBS). |
| **Requirements Covered** | `FR-1140` (vibrato), `FR-1150` (portamento), `NFR-1040` (ROM/WRAM budget), `NFR-1050` (per-frame timing budget) |
| **Architecture Components** | GDS-03 §1 (module ownership), `FS-106` (System Behaviour's "order of operations" note — portamento determines the base frequency, vibrato perturbs it last) |
| **Interfaces** | Extends `_emit_channel_gen` (`music_engine.py:196-328`) and, if `IP-1060` shipped first in the same session, composes with its sub-tick arpeggio block per `FS-106`'s specified write order: portamento (glide) → arpeggio (chord-tone select, if `IP-1060` built) → vibrato (offset) → one register write. If `IP-1060` has not shipped yet when this package is built, the order simplifies to portamento → vibrato → one write. |
| **Files to Create/Modify** | `music_engine.py` only: (1) new `VIBRATO_OFFSETS` ROM table (small, e.g. 4-8 signed entries forming one LFO cycle); (2) new per-pitched-channel WRAM: a vibrato phase counter, a portamento glide-remaining counter, and a portamento "current interpolated frequency" scratch pair (lo/hi) — or equivalent, implementation's choice on exact layout, documented either way; (3) `_emit_channel_gen`'s onset block: when the new degree differs from the previous one, instead of writing the target frequency immediately, initialize the glide-remaining counter and let the per-frame block step the held frequency toward the target over N frames (N a first-guess placeholder constant, same convention as `IP-1060`'s arpeggio sub-tick rate); when the degree repeats, skip the glide (already at target, matching `FS-106`'s explicit edge case). (4) A new always-runs-every-frame block: if a glide is in progress, step the held frequency one increment toward the target; then add the current `VIBRATO_OFFSETS` entry (phase-counter-indexed, advancing every frame or every few frames) to the held frequency; write the result to the frequency registers, no retrigger (same non-retriggering technique `IP-1060` uses for arpeggio, for the same reason — envelope continuity). (5) `init_engine`: zero all new WRAM on both boot and Select paths. |
| **Implementation Tasks** | (1) Design the glide-step algorithm: linear interpolation over N frames is the simplest correct approach (`old + (target - old) * (1 - remaining/N)`, computed incrementally frame-by-frame rather than via division — an 8-bit-friendly accumulator approach, e.g. precompute a per-frame delta at glide start and add it each frame) — exact arithmetic approach is this package's own implementation decision, not fixed here, but must avoid a hardware division (SM83 has none) and stay within the per-frame budget (`NFR-1050`). (2) Design the vibrato table/phase-advance rate — same "first-guess placeholder, not tuned by ear" status as every other untuned constant. (3) Implement the write-order composition with `IP-1060` (if present) exactly as `FS-106` specifies. (4) Confirm `CUR_DEGREE_*`/dissonance/stale scoring reads the *target* degree at onset, unaffected by the glide-in-progress frequency value — same non-interference requirement `IP-1060` has for arpeggio (`FR-1140` states this explicitly for vibrato; the same logic applies to portamento even though no FR states it as explicitly — flag this as confirmed-by-inspection in the Implementation Summary, not assumed). |
| **Tests to Add** | New `test_rom.py` suite (or extends `IP-1060`'s, coordinate the numbering): (a) drive a sustained run, sample the written frequency across consecutive frames while vibrato is active, assert it oscillates in a bounded range around a stable center (not monotonically drifting) while `CUR_DEGREE_*` stays constant for that note's duration; (b) force a degree-changing onset, sample the written frequency sequence between the old and new note, assert it spans more than one frame and each sampled value lies between the old and new target (monotonic progression, not an instant jump); (c) force a same-degree repeat onset, assert no glide occurs (frequency reaches target within one frame, as before this package); (d) full regression — all pre-existing suites plus `IP-1060`'s (if built first) still green. |
| **Documentation Updates** | `Claude.md`/`memory.md` (new WRAM addresses, new Known-Good-Behavior bullets), GDS-07 (extend §3 with the new addresses, same in-place-correction discipline as `IP-1060`/`BL-0018`). |
| **Definition of Done** | Vibrato is measurably active (bounded oscillation) without disturbing bad-zone scoring inputs; portamento measurably glides over more than one frame on a degree change and skips the glide on a repeat; every pre-existing test (including `IP-1060`'s, if built first) still passes; ROM still builds to 32768 bytes with a valid header. |
| **Verification Checklist** | ROM builds, exactly 32768 bytes, valid header (G5). Full `test_rom.py` suite passes, including the new suite (G5). `09-package-verification` independently drives a non-default tempo/octave and confirms vibrato/portamento behavior holds off the default preset. |
| **Dependencies** | `IP-0001`-`IP-0003` (`VERIFIED`). Sequencing-only dependency on `IP-1060` per the TWBS (same file, built second to avoid conflating two packages' test additions in one diff) — no functional dependency; this package's own logic does not require `IP-1060`'s arpeggio code to exist, only composes with it if present. |
| **Risks** | ROM budget: one small vibrato table + a handful of new WRAM bytes — negligible per `NFR-1040`. Arithmetic risk: the glide-step computation is the most implementation-risk-bearing part of this package (SM83 has no division) — recommend a simple accumulator/pre-computed-per-frame-delta approach over anything requiring real division. Interaction risk: composing with `IP-1060`'s arpeggio write order incorrectly (e.g. vibrato added before arpeggio's chord-tone selection instead of after) would produce audibly wrong results without necessarily failing a register-value test that only checks "is it varying" — the implementing package should specifically verify the write-order sequence against `FS-106`'s explicit spec, not just that some variation exists. |
| **Rollback Considerations** | Fully additive — reverting is a straightforward commit revert; no existing behavior removed, no WRAM address reused. |
