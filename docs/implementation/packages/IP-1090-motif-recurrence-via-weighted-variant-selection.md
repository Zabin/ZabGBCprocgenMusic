# IP-1090 — Motif Recurrence via Weighted Variant Selection

| Field | Content |
|---|---|
| **Package ID** | `IP-1090` |
| **Objective** | Extend Scheme E's existing single-row `MOTIF_TABLE` into 4 pre-composed motif variants, and add the routine that autonomously selects (at each motif-cycle boundary) which variant is active via a weighted lookup, per `FS-109`/`ADS-102`. |
| **Requirements Covered** | `FR-1270` (motif data is a small fixed variant set, variant 0 matches shipped), `FR-1280` (weighted variant selection at cycle boundaries, autonomous), `FR-1290` (weighting favors retaining the current variant), `FR-1300` (variant 0 held throughout reproduces pre-change behavior exactly, no regression), `NFR-1100` (ROM/WRAM budget), `NFR-1110` (no new input control/WRAM control byte beyond the variant-index field) |
| **Architecture Components** | `ADS-102` (full design), GDS-03 §1 (module ownership — stays in `music_engine.py`, no new module), `FS-109` (System Behaviour, Module Responsibilities) |
| **Interfaces** | Extends the existing motif-step lookup inside `_emit_channel_gen`'s `gt_e_*` Scheme-E branch (`music_engine.py:449-472`) — no new call site, an added read/branch inside that existing block. Reuses the exact indexed-table-read idiom (`_ld_hl_label` + `ADD_HL_BC` + `LD_A_HL`) every other `CHMIX_IDX`/`DENSITY_IDX`-keyed table lookup in this file already uses. Reuses the per-channel LFSR-step idiom (`SRL_A`/`JR_NC`/`XOR_n(LFSR_POLY)`, `music_engine.py:403-408`) already used for Scheme W's own delta draw — that channel's `lfsr_state` is otherwise idle while running Scheme E (the code path that steps it is skipped entirely when `scheme_bit` routes to `gt_schemee_`), so stepping it once at the cycle-boundary event introduces no new randomness source, only a new use of the existing one (`NFR-1110`/no-new-mechanism framing). |
| **Files to Create/Modify** | `music_engine.py` only — (1) add a new `MOTIF_VARIANT_IDX` WRAM constant at `0xC03C` (confirmed free against `docs/architecture/07-data-model.md`: `0xC038`-`0xC03A` is `IP-1070`'s `MOTIF_STEP_PA`/`PB`/`WV`, `0xC03B` is `IP-1080`'s `DUTY_BIAS`, `0xC03C`-`0xC04F` remains genuine unused headroom before `JOY_PREV` at `0xC050`); (2) extend `MOTIF_TABLE` from 8 bytes (1 row) to 32 bytes (`N_VARIANTS=4` rows × 8 bytes) — row 0 unchanged (`[0, 2, 4, 5, 4, 2, 0, 7]`), rows 1-3 new hand-composed variants sharing row 0's start/end degree with differing middle contour (per `FS-109` Open Question 3's resolution: hand-composed, matching row 0's own origin, not an offline L-system tool — pragmatic, no new tooling needed); (3) add a new `MOTIF_VARIANT_SELECTOR` ROM data block, 4 bytes, shaped exactly like the existing `DELTA_TABLE` (`[0x00, 0x00, 0x00, 0x01]` — signed deltas *relative to the current variant index*, 3-of-4 entries `0` (retain), 1-of-4 entry `+1` (advance to the next variant, wrapped mod `N_VARIANTS`), indexed by 2 LFSR-derived bits exactly the way `DELTA_TABLE` is indexed by 2 LFSR bits today — resolves `BL-0042`'s open tuning question with a concrete, cheap starting point reusing an already-shipped shape rather than inventing a new one); (4) in `_emit_channel_gen`'s Scheme-E branch, right after the existing motif-step-advance code computes the new motif-step bits (`music_engine.py:451-455`, the `AND_n(0x70)` that yields the new step bits still shifted into position), add a check: if those bits are zero (the step just wrapped from 7 back to 0 — a full cycle just completed), step this channel's own `lfsr_state` once (reusing the existing per-channel LFSR-step idiom, otherwise unused on this code path), mask to 2 bits, look up `MOTIF_VARIANT_SELECTOR`, add the resulting signed delta to `MOTIF_VARIANT_IDX`, and re-mask `AND 0x03` (wrap mod `N_VARIANTS=4`) — writing the result back to `MOTIF_VARIANT_IDX`; (5) change the existing motif-table lookup (`music_engine.py:462-467`, computing `motif_table_base + motif_step`) to first add `MOTIF_VARIANT_IDX * 8` to the base offset before adding the motif-step offset, making the lookup variant-relative; (6) `init_engine`: zero `MOTIF_VARIANT_IDX` alongside the existing `scheme_state` zeroing in the per-channel reset loop (`music_engine.py:1014`, same loop iteration, same reset trigger — boot and Select both already zero `scheme_state`, which resets the motif-step counter to 0 too, so zeroing `MOTIF_VARIANT_IDX` in the same place keeps a reset fully deterministic: variant 0, step 0, resolving `FS-109` Open Question 4). |
| **Implementation Tasks** | (1) Add `MOTIF_VARIANT_IDX` WRAM constant at `0xC03C`. (2) Extend `MOTIF_TABLE` to 4 rows (32 bytes); row 0 unchanged, rows 1-3 new hand-composed variants. (3) Add `MOTIF_VARIANT_SELECTOR` (4 bytes, `[0x00, 0x00, 0x00, 0x01]`). (4) In the Scheme-E branch, after the existing motif-step-advance arithmetic, detect the cycle-boundary condition (new motif-step bits == 0) and, only on that condition, step the channel's own LFSR once, index `MOTIF_VARIANT_SELECTOR`, apply the signed delta to `MOTIF_VARIANT_IDX` with `AND 0x03` wrap. (5) Make the existing motif-table lookup variant-relative (`variant_idx * 8 + motif_step` offset instead of just `motif_step`). (6) Zero `MOTIF_VARIANT_IDX` in `init_engine`'s per-channel reset loop, same iteration as `scheme_state`'s existing zeroing. (7) Confirm (by code-reading, not new logic) that this package's writes to `MOTIF_VARIANT_IDX`/the LFSR step never touch `BAD_ZONE_FLAGS`/`DISSONANCE_SCORE`/`STALE_COUNT_*`/`ONSET_WINDOW_COUNT`, so no ordering conflict with `_emit_badzone_tick`/`IP-0007`'s bad-zone overrides is possible by construction — document this confirmation rather than leaving it assumed, same discipline `IP-1080` already used for its own bad-zone-independence claim (and the caveat `BL-0040` found: state this narrowly — "this package's own writes never touch those addresses" — not as a broader same-frame guarantee, since `engine_tick` runs unconditionally regardless of this package's own logic). (8) Verify the mid-cycle interaction with `IP-1080`'s style-application path (`FS-109`'s own flagged risk): confirm by code-reading that `_emit_apply_style` never touches `scheme_state`/`MOTIF_VARIANT_IDX`, so a style change landing on the same frame as a motif-cycle-boundary draw cannot corrupt either mechanism's own state — document this confirmation, and add a dedicated test exercising the combination (Tests to Add, item (e)) rather than relying on code-reading alone, per `BL-0040`'s own lesson that an analogous claim needed adversarial-test confirmation, not just inspection. |
| **Tests to Add** | New `test_rom.py` suite (e.g. `T16`): (a) with `MOTIF_VARIANT_IDX` held at 0 via a test-only seed/override, drive a Scheme-E channel through a full motif cycle and confirm the onset-by-onset degree sequence matches the pre-`IP-1090` shipped sequence exactly — regression guard for `FR-1300`; (b) drive a Scheme-E channel through several full cycles and assert `MOTIF_VARIANT_IDX` only ever changes on the exact frame the motif-step counter wraps to 0, never mid-cycle — confirms `FR-1280`'s cycle-boundary-only timing; (c) drive a long randomized run (thousands of frames, many cycle completions) and assert the empirical ratio of retained-vs-switched draws favors retention (majority retained) — statistical confirmation of `FR-1290`, same "measured over a run" methodology `VR-1080`'s own stress-run test already used; (d) confirm all 4 variant rows are distinct from each other (sanity check on the authored data, `FR-1270`); (e) drive a `CHMIX_IDX` style change (`IP-1080`) on the exact frame a motif-cycle boundary would also complete and confirm both mechanisms' own state (`MOTIF_VARIANT_IDX`/`TEMPO_IDX` etc.) update independently and correctly, with no corruption of either — the dedicated interaction test named in Implementation Task 8; (f) full regression — all pre-existing suites (`T1`-`T15`) still green. |
| **Documentation Updates** | `Claude.md` (new "Motif recurrence via weighted variant selection" Known Good Behavior bullet, test-count update, a new "Change motif variants" dev-guide subsection matching the existing "Change Scheme E's motif table"/"Change style-preset values" precedents), `memory.md` (WRAM quick-reference gains `MOTIF_VARIANT_IDX`), GDS-07 (the new WRAM address and `MOTIF_TABLE`'s expanded shape / new `MOTIF_VARIANT_SELECTOR` table are a real data-model addition — extend GDS-07 §3 in place, same discipline every prior package's WRAM addition used), `docs/pipeline/backlog.md` (`BL-0010` closes once this package is `VERIFIED` — the motif-recurrence half this entry has tracked since run #4; `BL-0042` closes once the concrete `N_VARIANTS`/weighting values this package names are confirmed working by test). |
| **Definition of Done** | A Scheme-E channel's motif data comprises 4 variants (row 0 identical to the pre-`IP-1090` shipped sequence); at each motif-cycle-boundary frame, `MOTIF_VARIANT_IDX` is drawn via the weighted selector with no input required; the draw measurably favors retention over switching across a long run; with `MOTIF_VARIANT_IDX` held at 0, the channel's output is byte-identical to the pre-`IP-1090` shipped behavior; a style change (`IP-1080`) landing on the same frame as a cycle boundary corrupts neither mechanism's state; every pre-existing test still passes; ROM still builds to 32768 bytes with a valid header. |
| **Verification Checklist** | ROM builds, exactly 32768 bytes, valid header (G5). Full `test_rom.py` suite passes, including the new suite (G5). `09-package-verification` independently drives a non-default variant sequence (e.g. forcing several consecutive switch-draws rather than the statistically-more-common retain-draws) live and confirms the DoD holds beyond whatever single fixture the new suite happens to use, per this project's standing tunable-parameter/non-default-combination verification standard (`VR-1070`/`VR-1080`'s own precedent). |
| **Dependencies** | `IP-1070` (Scheme E's existing `MOTIF_TABLE`/motif-step mechanism, `VERIFIED`) — this package is a direct extension of that shipped code, the first such genuine code dependency this project's packages have recorded (per `05-feature-decomposition`'s own dependency-graph note for `FEAT-1090`). No dependency on `IP-1080` (`STYLE_TABLE`) — the two packages touch disjoint code paths, but see the mid-cycle-interaction test (Tests to Add, item (e)), named for verification, not a code dependency. |
| **Risks** | ROM/WRAM budget: `MOTIF_TABLE`'s +24 bytes (8→32) plus `MOTIF_VARIANT_SELECTOR`'s 4 bytes plus 1 new WRAM byte — small, but this package should confirm against the actual printed `build_rom.py` layout / `rom.pos`-instrumentation measurement (`ADR-0002`'s own method), not merely assumed negligible. Variant-contour risk (carried from `ADS-102`/`FS-109`): whether the 3 new hand-composed variants read as "development" of variant 0 rather than a discontinuity is a `09-content-review` judgment call, not resolvable here. Tuning risk (`BL-0042`, carried forward): the specific `MOTIF_VARIANT_SELECTOR` values (`[0x00,0x00,0x00,0x01]`, a 3-in-4 retention rate) are this package's own first-guess placeholder, same "not tuned by ear yet" disposition as every other untuned constant (`BL-0005`). Interaction risk (`BL-0040`'s own lesson, carried forward): the `IP-1080` mid-cycle-interaction claim is verified by a dedicated test in this package (not code-reading alone), precisely because a superficially-similar independence claim needed adversarial-test confirmation once before. |
| **Rollback Considerations** | Fully additive (extended table with the original row preserved as row 0, one new small selector table, one new WRAM byte, an added branch inside an existing block, one changed offset computation at the existing motif lookup site) — reverting is a straightforward commit revert; no existing WRAM address reused, no existing behavior removed. The lookup change reduces to today's exact behavior when `MOTIF_VARIANT_IDX`=0 (which it always is until the first cycle boundary after a reset), so even a partial rollback leaves default (variant-0) behavior unchanged. |
