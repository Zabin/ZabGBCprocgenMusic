# IP-1100 — Song-Form via Autonomous Phase Cycling

| Field | Content |
|---|---|
| **Package ID** | `IP-1100` |
| **Objective** | Add a new, independent state machine (`SONG_STATE`/`SONG_STATE_TIMER_LO`/`SONG_STATE_TIMER_HI`) that autonomously cycles 4 named phases and, on each transition, overwrites `TEMPO_IDX`/`DENSITY_IDX` to that phase's target values, per `FS-110`/`ADS-103`. |
| **Requirements Covered** | `FR-1310` (autonomous 4-phase cycle, no input required), `FR-1320` (phase transition overwrites tempo/density immediately), `FR-1330` (bad-zone/motif-variant mechanisms phase-agnostic), `FR-1340` (all 4 phases occur in cyclic order over a long run), `NFR-1120` (ROM/WRAM budget), `NFR-1130` (no new input control) |
| **Architecture Components** | `ADS-103` (full design), GDS-03 §1 (module ownership — stays in `music_engine.py`, no new module), `FS-110` (System Behaviour, Module Responsibilities) |
| **Interfaces** | Adds a new routine (`_emit_song_tick`), called once per frame from `engine_tick` — the same per-frame call sequence `_emit_badzone_tick` and each channel's `gen_tick` already run from (an added call, not a new dispatch mechanism). Writes `TEMPO_IDX`/`DENSITY_IDX` via the same plain `LD_nn_A` pattern `_emit_apply_style`/the D-pad/B handlers already use — no new write mechanism invented. |
| **Files to Create/Modify** | `music_engine.py` only — (1) add three new WRAM constants: `SONG_STATE` at `0xC03D`, `SONG_STATE_TIMER_LO` at `0xC03E`, `SONG_STATE_TIMER_HI` at `0xC03F` (confirmed free against `docs/architecture/07-data-model.md`: `0xC03C` is `IP-1090`'s `MOTIF_VARIANT_IDX`, `0xC03D`-`0xC04F` genuinely unused headroom before `JOY_PREV` at `0xC050`); (2) add a new `SONG_TABLE` ROM data block — 4 rows × 4 bytes (`tempo_idx`, `density_idx`, `duration_lo`, `duration_hi`), values per the Master Build Plan's own TWBS table (INTRO/BUILD/PEAK/BREAKDOWN, first-guess placeholders per `BL-0005`'s standing disposition); (3) implement `_emit_song_tick(rom)`: decrement the 16-bit `SONG_STATE_TIMER_LO`/`HI` pair (standard decrement-with-borrow: decrement the low byte; if it was already 0 before decrementing, borrow by also decrementing the high byte — the same class of multi-byte arithmetic idiom `gbc_lib.py`'s own 16-bit `ADD_HL_BC`-based table addressing already relies on, applied here to a plain counter instead of an address); if both bytes are now 0, advance `SONG_STATE` (`INC A; AND 0x03` — the same wrap-mod-4 idiom every other cyclic index in this file already uses), look up the new `SONG_TABLE` row (`song_table_base + SONG_STATE*4`), write its `tempo_idx`/`density_idx` bytes into `TEMPO_IDX`/`DENSITY_IDX`, and reload `SONG_STATE_TIMER_LO`/`HI` from that same row's `duration_lo`/`hi` bytes; (4) call `_emit_song_tick(rom)` from `engine_tick`'s existing per-frame sequence, alongside the existing `_emit_badzone_tick`/per-channel `gen_tick` calls — confirmed by reading the current `engine_tick` body that no ordering dependency exists (this tick reads/writes only `SONG_STATE`/`SONG_STATE_TIMER_*`/`TEMPO_IDX`/`DENSITY_IDX`, none of which any other tick routine's own per-frame logic depends on being written before or after it runs); (5) `init_engine`: initialize `SONG_STATE`=0, `SONG_STATE_TIMER_LO`/`HI` = `SONG_TABLE[0]`'s own duration, and `TEMPO_IDX`/`DENSITY_IDX` already boot to `PRESET_TEMPO_IDX`/`PRESET_DENSITY_IDX` via the existing preset writes — confirm (Implementation Task, not assumed) whether `SONG_TABLE[0]`'s own `tempo_idx`/`density_idx` should match those preset values exactly (no regression to current boot audio) or intentionally differ (INTRO's own musical identity) — this package's own concrete choice, to be stated in its Definition of Done once decided; same reset applied on Select. |
| **Implementation Tasks** | (1) Add `SONG_STATE`/`SONG_STATE_TIMER_LO`/`SONG_STATE_TIMER_HI` WRAM constants. (2) Add `SONG_TABLE` (16 bytes) with the 4 defined phase rows. (3) Implement `_emit_song_tick`'s 16-bit countdown-and-transition logic, reusing the existing indexed-table-read idiom (`_ld_hl_label` + `ADD_HL_BC` + `LD_A_HLI` auto-increment reads) already used for `STYLE_TABLE`/`MOTIF_TABLE`. (4) Wire the call into `engine_tick`'s existing per-frame sequence. (5) Initialize `SONG_STATE`/`SONG_STATE_TIMER_*` in `init_engine`'s boot/Select path, deciding explicitly whether `SONG_TABLE[0]` matches the shipped default `TEMPO_IDX`/`DENSITY_IDX` exactly (no regression) or is INTRO's own distinct value (a real product decision this package must state, not leave implicit). (6) Confirm (by code-reading, not new logic) that `_emit_song_tick`'s writes never touch `BAD_ZONE_FLAGS`/`DISSONANCE_SCORE`/`STALE_COUNT_*`/`ONSET_WINDOW_COUNT`/`CUR_DEGREE_*`/`MOTIF_VARIANT_IDX`/`scheme_state`, so no ordering conflict with `_emit_badzone_tick`/`IP-0007`'s overrides or `IP-1090`'s motif-variant draws is possible by construction — document this confirmation, phrased narrowly ("this package's own writes never touch those addresses," not a broader same-frame guarantee, per `BL-0040`'s own lesson about over-claiming independence). (7) Verify the `IP-1080` mid-transition interaction (`FS-110`'s own flagged risk): confirm by code-reading that `_emit_apply_style` never touches `SONG_STATE`/`SONG_STATE_TIMER_*`, then add a dedicated test forcing a Start press onto the exact frame a phase transition also occurs, per `FS-110`'s own Verification Plan and `BL-0045`'s lesson that a merely-plausible interval is not the same as a guaranteed collision. |
| **Tests to Add** | New `test_rom.py` suite (e.g. `T17`): (a) drive a long run (at least one full 4-phase cycle, ~6600+ frames) and assert all 4 phases occur in their defined cyclic order, each transition landing exactly `SONG_TABLE`'s documented `TEMPO_IDX`/`DENSITY_IDX` values on the transition frame itself; (b) assert `SONG_STATE`/`SONG_STATE_TIMER_*` never go out of their defined ranges across the run; (c) drive the engine into a bad-zone state and confirm a phase transition landing during it leaves `BAD_ZONE_FLAGS`/`STALE_COUNT_PA`/`ONSET_WINDOW_COUNT` unchanged on the transition frame itself (same assertion shape `IP-1080`'s own `T15.5` established, same `BL-0040`-informed narrow wording); (d) confirm a Scheme-E channel's `MOTIF_VARIANT_IDX` is unaffected by a phase transition; (e) force a guaranteed same-frame collision between a Start press (`IP-1080`) and a phase transition (by first empirically deriving the real transition frame, the same methodology `VR-1090` used, not a plausible-but-unverified interval) and confirm neither mechanism's state is corrupted; (f) confirm Select resets `SONG_STATE`/`SONG_STATE_TIMER_*` to phase 0 and re-applies its target values; (g) full regression — all pre-existing suites (`T1`-`T16`) still green. |
| **Documentation Updates** | `Claude.md` (new "Song-form via autonomous phase cycling" Known Good Behavior bullet, test-count update, a new "Change song-form phases" dev-guide subsection matching the existing "Change style-preset values"/"Change motif variants" precedents), `memory.md` (WRAM quick-reference gains `SONG_STATE`/`SONG_STATE_TIMER_LO`/`SONG_STATE_TIMER_HI`), GDS-07 (the three new WRAM addresses and `SONG_TABLE`'s ROM section are a real data-model addition — extend GDS-07 §3 in place), `docs/pipeline/backlog.md` (R6 rides the roadmap, not a single `BL-xxxx` — no direct backlog item to close, same pattern `IP-1080`'s own R5 note used). |
| **Definition of Done** | With no button input, the engine autonomously cycles through all 4 named phases in order, each transition overwriting `TEMPO_IDX`/`DENSITY_IDX` to that phase's documented values on the transition frame; bad-zone/motif-variant state is unaffected by any phase transition; a Start press landing on the same frame as a phase transition corrupts neither mechanism; Select resets to phase 0; every pre-existing test still passes; ROM still builds to 32768 bytes with a valid header. |
| **Verification Checklist** | ROM builds, exactly 32768 bytes, valid header (G5). Full `test_rom.py` suite passes, including the new suite (G5). `09-package-verification` independently drives a non-default scenario (e.g. forcing entry mid-cycle at a phase other than INTRO, or the guaranteed Start-press/transition collision) live and confirms the DoD holds beyond whatever single fixture the new suite happens to use, per this project's standing tunable-parameter/non-default-combination verification standard (`VR-1070`/`VR-1080`/`VR-1090`'s own precedent). |
| **Dependencies** | `IP-0001`-`IP-0003` (`TEMPO_IDX`/`DENSITY_IDX`, all `VERIFIED`). No dependency on `IP-1080`/`IP-1090` — both confirmed independent by `ADS-103` §2 (disjoint WRAM fields from bad-zone/motif-variant; independent-but-coexisting writer with `IP-1080`'s own `TEMPO_IDX`/`DENSITY_IDX` fields) — sequencing relative to either is unconstrained, but Implementation Task 7/Tests to Add item (e) name the one combination needing dedicated verification. |
| **Risks** | ROM/WRAM budget: `SONG_TABLE` (16 bytes) + 3 new WRAM bytes — small, but this package should confirm against the actual printed `build_rom.py` layout / `rom.pos`-instrumentation measurement (`ADR-0002`'s own method), not merely assumed negligible; already flagged in the Master Build Plan as a small, disclosed deviation from `ADS-103`'s original 12-byte/2-byte estimate (a 16-bit timer, not 1 byte, was needed for genuinely multi-minute phase durations). Musical-naturalness risk (carried from `ADS-103`/`FS-110`): a `09-content-review` judgment call, not resolvable here. BUILD/`OVERLOAD` interaction risk (carried forward): whether the BUILD phase's `DENSITY_IDX=4` target measurably increases `OVERLOAD` frequency versus the default preset is worth empirically checking (a stress-run comparison), not asserted safe by inspection alone. Boot-behavior risk (Implementation Task 5): whether `SONG_TABLE[0]` matches the shipped default exactly or intentionally differs is a real product decision this package must make explicitly, not leave ambiguous. |
| **Rollback Considerations** | Fully additive (new table, three new WRAM bytes, a new routine, one new call site in `engine_tick`) — reverting is a straightforward commit revert; no existing WRAM address reused, no existing behavior removed, no existing routine modified. |
