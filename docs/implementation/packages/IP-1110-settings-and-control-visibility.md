# IP-1110 — Settings & Control Visibility

| Field | Content |
|---|---|
| **Package ID** | `IP-1110` |
| **Objective** | Add 5 new bar-height indicator tiles to the visualizer, one per base control (`TEMPO_IDX`, `OCTAVE_IDX`, `SCALE_IDX`, `DENSITY_IDX`, `CHMIX_IDX`), each showing that parameter's current index as a filled-bar glyph, updated every frame — per `FS-111`/`ADS-104`. **Disclosed exception found during implementation** (see Risks/Definition of Done): on the exact frame Select is pressed, the display update for that one frame is silently dropped due to a real VRAM-write timing constraint; it self-heals the very next frame. |
| **Requirements Covered** | `FR-1350` (5 indicators, one per base control, bar-height glyph), `FR-1360` (same-frame update), `FR-1370` (purely additive, no change to existing channel-activity/palette behavior), `FR-1380` (at least one indicator demonstrably live-reflects a manual button change), `NFR-1140` (ROM/VRAM budget), `NFR-1150` (VBlank-gated, comparable per-frame cost), `NFR-1160` (no new input control) |
| **Architecture Components** | `ADS-104` (full design), GDS-03 §1 (module ownership — stays in `visuals.py`, no new module, read-only-visualizer invariant preserved), `FS-111` (System Behaviour, Module Responsibilities) |
| **Interfaces** | Extends the existing `build_visuals_update_asm`/`update_visuals` per-frame routine (`visuals.py`) with new tile-pattern-index writes, the same per-frame call site the existing `CHANNEL_CELLS`/palette-swap logic already runs from — no new dispatch mechanism. Extends `build_visuals_init_asm` with new tile-pattern/tilemap-cell initialization, the same init call site `TILE_OFF`/`TILE_ON`/`CHANNEL_CELLS` already use. Reads `TEMPO_IDX`/`OCTAVE_IDX`/`SCALE_IDX`/`DENSITY_IDX` (`music_engine.py`, `0xC000`-`0xC003`) and `CHMIX_IDX` (`0xC004`) via the same plain `LD_A_nn` read pattern `update_visuals` already uses for `BAD_ZONE_FLAGS` — read-only, no new write mechanism. |
| **Files to Create/Modify** | `visuals.py` only — (1) add 8 new tile patterns (fill levels 0-7, indices 2-9 following the existing `TILE_OFF`=0/`TILE_ON`=1 pair), each an 8×8 2bpp glyph with `N` filled rows from the bottom (solid color index 3 for the bottom `N` rows, color index 0 for the remaining `8-N` rows) — a `_bar_tile_bytes(n)` helper generalizing the existing `_tile_off_bytes()`/`_tile_on_bytes()` pattern (which become the `n=0`/`n=8` special cases, though kept as-is to avoid touching working code — the 8 new patterns are added alongside, not by refactoring the existing pair); (2) add a `SETTINGS_CELLS` list of 5 new fixed BG tilemap cells — confirmed against the current tilemap layout that `CHANNEL_CELLS` occupies exactly `TILEMAP_BASE+0`..`TILEMAP_BASE+3` and nothing else in the tree writes or reads any other `0x98xx` address (grepped `build_rom.py`/`music_engine.py`/`gbc_lib.py`, clean) — `SETTINGS_CELLS = [TILEMAP_BASE + 4, TILEMAP_BASE + 5, TILEMAP_BASE + 6, TILEMAP_BASE + 7, TILEMAP_BASE + 8]` (same tilemap row, immediately following the 4 channel-activity cells, well within the 32-wide row `TILEMAP_BASE` starts), one cell per control in the fixed order tempo/octave/scale/density/channel-mix; (3) in `build_visuals_init_asm`, write the 8 new tile patterns to VRAM immediately after the existing `TILE_OFF`/`TILE_ON` pair, and initialize the 5 `SETTINGS_CELLS` to the tile-pattern index matching each control's actual boot-preset value (`PRESET_TEMPO_IDX`/`PRESET_OCTAVE_IDX`/`PRESET_SCALE_IDX`/`PRESET_DENSITY_IDX` from `music_engine.py`, `CHMIX_IDX`'s own boot default of 0) — not left at `TILE_OFF`/an arbitrary pattern, so the very first rendered frame is already correct rather than snapping into place after the first `update_visuals` call; (4) implement a new routine `_emit_update_settings_row(rom)`: for each of the 5 controls, read its WRAM byte, use it directly as the tile-pattern-index offset (2 + index, since patterns 2-9 correspond to fill levels 0-7 and the source value already is the fill level 0-7/0-3 — no scaling needed since `TEMPO_IDX`/`DENSITY_IDX`/`CHMIX_IDX` range 0-7 and `OCTAVE_IDX`/`SCALE_IDX` range 0-3, both naturally within the 0-7 pattern-index space per `FS-111` Open Question 1's resolution below), write that index to the corresponding `SETTINGS_CELLS` entry; (5) call `_emit_update_settings_row(rom)` from `build_visuals_update_asm`, alongside the existing channel-activity/palette-swap logic — confirmed by reading the current function body that this new call touches none of `CHANNEL_CELLS`, `TILE_OFF`/`TILE_ON`, or the palette-write routine (`_emit_write_palette`), so `FR-1370`'s purely-additive requirement holds by construction, not merely by intent. **Call-site position within `update_visuals` (resolved during implementation, not as originally planned)**: this call runs *last*, after the channel-activity/palette writes, not interleaved earlier — an initial attempt to run it first (to give it the same early, historically-safe position the channel-activity writes occupy) instead caused the *channel-activity* writes to intermittently drop on ordinary frames with no button input, a strictly worse regression; last position confines the one disclosed timing exception (see Risks) to this package's own writes only. |
| **Implementation Tasks** | (1) Add `_bar_tile_bytes(n)` and the 8 new tile-pattern byte sequences (fill levels 0-7). (2) Add `SETTINGS_CELLS` (5 tilemap addresses, `TILEMAP_BASE+4`..`+8`). (3) Extend `build_visuals_init_asm` to write the 8 new patterns to VRAM and pre-initialize `SETTINGS_CELLS` to the boot-preset values (not left blank/arbitrary for the first frame). (4) Implement `_emit_update_settings_row`, reading the 5 WRAM fields and writing the corresponding tile-pattern index to each `SETTINGS_CELLS` entry — this package resolves `FS-111` Open Question 1 pragmatically: all 5 indicators share the same 8-level tile set (patterns 2-9) rather than authoring a separate 4-level set for `OCTAVE_IDX`/`SCALE_IDX`; those two controls' bars simply never exceed half-full (index 0-3 of 0-7), a first-guess placeholder decision per this project's standing visual-tuning deferral convention (`BL-0005`), not a functional defect. (5) Wire the call into `build_visuals_update_asm`'s existing body. (6) Confirm (by code-reading, not new logic) that this package's own writes never touch `CHANNEL_CELLS`, `TILE_OFF`/`TILE_ON`, or the palette-write routine — document this confirmation, phrased narrowly ("this package's own writes never touch those addresses," the same `BL-0040`-informed narrow wording every prior package's independence claim has used). |
| **Tests to Add** | New `test_rom.py` suite `T18` (10 checks): (a) at boot, read all 5 `SETTINGS_CELLS` tile-pattern indices and assert each matches the corresponding preset value's expected pattern index (tests Implementation Task 3's pre-initialization, not just steady-state behavior); (b) drive each of D-pad Up/Down/Left/Right, A, B, Start in turn and assert the corresponding `SETTINGS_CELLS` entry's tile-pattern index updates to match the new WRAM value on the same frame (`FR-1360`/`FR-1380`); (c) drive a run exercising several of the above changes and assert `CHANNEL_CELLS`'/`TILE_OFF`/`TILE_ON`'s own existing tile-index values and the calm/bad-zone palette are unaffected by any of this package's writes (`FR-1370`, same assertion shape `IP-1080`'s own `T15.5`/`IP-1100`'s own `T17.5` established); (d) drive a Select press and assert the underlying WRAM fields reset on the exact reset frame (`T18.9`, same guarantee `T5`/`T17.7` already established, unaffected by this package); (e) assert the settings-indicator *display* catches up to the restored preset within one further frame (`T18.10`) — the disclosed, narrower, self-healing exception discovered during implementation (see Risks), not the same-frame guarantee originally assumed; (f) full regression — all pre-existing suites (`T1`-`T17`) still green. |
| **Documentation Updates** | `Claude.md` (new "Change settings-indicator tile patterns" dev-guide subsection matching the existing "Change style-preset values"/"Change motif variants"/"Change song-form phases" precedents, test-count update, a new Known Good Behavior bullet), `memory.md` (no new WRAM addresses — this package adds no WRAM, only ROM tile data and existing-tilemap-space cell assignments; note `SETTINGS_CELLS`' tilemap addresses in the visualizer quick-reference section instead), GDS-07 (the 8 new tile patterns and `SETTINGS_CELLS`' tilemap-cell reservations are a real data-model addition — extend GDS-07's tile/tilemap section in place), `docs/pipeline/backlog.md` (`BL-0051` closes its base-control half on this package's completion — mark accordingly at that time). |
| **Definition of Done** | At boot, all 5 settings indicators already show the correct preset-value fill level (not blank/arbitrary). Each indicator updates to reflect its parameter's new value on the same frame a manual D-pad/A/B/Start press changes it. The existing channel-activity tiles and calm/bad-zone palette swap are unaffected by this package's own writes. Select resets the underlying WRAM fields on the exact reset frame, and the settings-indicator display catches up within one further frame (a disclosed, narrower exception than originally planned — see Risks — self-healing, not a functional defect). Every pre-existing test still passes. ROM still builds to 32768 bytes with a valid header. |
| **Verification Checklist** | ROM builds, exactly 32768 bytes, valid header (G5). Full `test_rom.py` suite passes, including the new suite (G5). `09-package-verification` independently drives a non-default scenario (e.g. a non-boot-default `CHMIX_IDX` preset, or a sequence of several button presses in a row rather than just one of each) live and confirms the DoD holds beyond whatever single fixture the new suite happens to use, per this project's standing tunable-parameter/non-default-combination verification standard (`VR-1070`/`VR-1080`/`VR-1090`/`VR-1100`'s own precedent). |
| **Dependencies** | `IP-0006` (`FEAT-1040`, minimal visualizer, `VERIFIED`) — extends its existing `update_visuals`/tile-pattern/tilemap-cell mechanism directly. `IP-0001`-`IP-0003` (`TEMPO_IDX`/`OCTAVE_IDX`/`SCALE_IDX`/`DENSITY_IDX`, all `VERIFIED`) and `IP-1070`/`IP-9010` (`CHMIX_IDX`, both `VERIFIED`) — read only. No dependency on `IP-1080`/`IP-1090`/`IP-1100` — this package's v1 scope reads only the 5 pre-existing base-control fields, per `ADS-104`/`FS-111`'s explicit v1-scope boundary. |
| **Risks** | **ROM budget (measured, not estimated)**: +449 bytes (28528 free, `ADR-0002`'s own `rom.pos` method) — larger than this package's original 128-byte tile-data-only estimate, since the per-frame update routine's and the init routine's own instruction overhead (5 controls × several opcodes each, twice) wasn't counted in that estimate; disclosed here rather than silently absorbed, still negligible against the ROM's total headroom. Tilemap-layout risk (`FS-111` Open Question 2, resolved by this package's own Files-to-Modify grounding: confirmed `CHANNEL_CELLS` occupies only `TILEMAP_BASE+0`..`+3` and nothing else in the tree touches any other tilemap address — `TILEMAP_BASE+4`..`+8` are genuinely free) — confirmed directly against a live PyBoy tilemap read during implementation, not solely by static grep. **Disclosed Select-frame display-lag finding (found during implementation, not fixed)**: on the exact frame Select is pressed, `apply_input`'s full `init_engine` reset costs enough extra CPU that this package's settings-row VRAM writes for that one frame are silently dropped — confirmed empirically to be independent of where `_emit_update_settings_row`'s call sits within `update_visuals` (moving it earlier did not help, and moving it all the way to the front of the routine instead caused the pre-existing channel-activity writes to intermittently drop on *ordinary* frames with no button input at all, a strictly worse outcome — reverted). This is a pre-existing property of the visualizer's per-frame VRAM-write design (GDS-03's timing-discipline invariant), only made observable by this package since it is the first indicator whose displayed value actually changes across a Select press; the display self-heals the very next frame since `update_visuals` reruns unconditionally every frame against already-reset WRAM. Not fixed in this package (would require reducing `init_engine`'s per-frame cost or restructuring the main loop's call order — out of this package's scope, a `03-architecture-design-synthesis`/`07-implementation-planning` question if ever prioritized). Legibility risk (carried from `ADS-104`/`FS-111`): whether unlabeled bars actually read as useful to a first-time listener is a `09-content-review` judgment call, not resolvable here. `FS-111` Open Question 1 (shared vs. narrower tile set for `OCTAVE_IDX`/`SCALE_IDX`) resolved pragmatically by this package (shared 8-level set, simplest/cheapest) — a first-guess placeholder, not a final content decision. |
| **Rollback Considerations** | Fully additive (8 new tile patterns, 5 new tilemap-cell reservations in previously-unused tilemap space, one new routine, one new call site in `build_visuals_update_asm`, one extended call site in `build_visuals_init_asm`) — reverting is a straightforward commit revert; no existing WRAM address, tile pattern, tilemap cell, or routine is reused or modified. |
