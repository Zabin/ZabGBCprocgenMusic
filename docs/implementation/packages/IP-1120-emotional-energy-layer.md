# IP-1120 — Emotional/Energy Layer

| Field | Content |
|---|---|
| **Package ID** | `IP-1120` · mirrors `FS-112` · **Executor: `08-code-implementation`** · roadmap R7, `FEAT-1120` |
| **Objective** | Add two derived WRAM bytes, `AROUSAL` and `VALENCE`, computed from already-tracked steering state (`TEMPO_IDX`/`DENSITY_IDX` for `AROUSAL`; `SCALE_IDX` for `VALENCE`) and recomputed **only** at the 6 write sites that can change those inputs — never as an unconditional per-frame call. Zero player-visible or audible change; this package lays groundwork for roadmap R9's future mood-reactive visualizer work, which remains separately blocked on its own unrun research thread. |
| **Requirements Covered** | `FR-1390`, `FR-1400`, `FR-1410`, `FR-1420`, `NFR-1170`, `NFR-1180`. |
| **Architecture Components** | [`ADS-105`](../../architecture/ADS-105-emotional-energy-layer.md) (the design synthesis and Decision Log — authoritative for the recompute-on-write approach); [`FS-112`](../../features/fs-112-emotional-energy-layer.md) (the behavior contract and the corrected 6-trigger-site count); [`GDS-09` §5](../../architecture/09-interface-specification.md) (per-frame call-order contract governing where each recompute call must sit relative to its trigger's own write); [`GDS-07` §6](../../architecture/07-data-model.md) (WRAM headroom — next free address `0xC068`, re-confirmed at planning time). |
| **Interfaces** | New routine in `music_engine.py` (name: `_emit_mood_update`, matching this project's `_emit_*` naming convention for per-frame/per-event emitter functions), called from 6 sites across `input_map.py`/`music_engine.py` (see Files to Create/Modify). No change to `build_engine_asm`'s or `build_input_asm`'s own signatures (both already return nothing, post-`IP-8010`). `visuals.py` and `build_rom.py` are untouched. |
| **Files to Create/Modify** | **`music_engine.py`**: (1) add `AROUSAL = 0xC068` and `VALENCE = 0xC069` WRAM constants, in the same declaration block as the other steering-derived state; (2) add `VALENCE_TABLE = [10, 6, 12, 4]` as a new Python-level data table (4 entries, one per `SCALE_IDX` value; ROM-resident once emitted); (3) add `_emit_mood_update(rom)`, emitting: read `TEMPO_IDX`, read `DENSITY_IDX`, `ADD`, store to `AROUSAL`; read `SCALE_IDX`, index into a ROM-resident `VALENCE_TABLE`, store to `VALENCE`; (4) call `_emit_mood_update(rom)` from `_emit_song_tick` (`music_engine.py:1067`, at the point after that tick's own `TEMPO_IDX`/`DENSITY_IDX` writes land — confirm exact insertion point against the routine's current body, not assumed from the line number alone) and from `build_engine_asm`'s `init_engine` label (`music_engine.py:1120`, after that label's own `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX` writes, serving both the boot path and the Select-reset path). **`input_map.py`**: add a call to `_emit_mood_update(rom)` (imported from `music_engine.py`) immediately after each of the 4 `_step_on_bit` calls that touch `AROUSAL`/`VALENCE`'s inputs — `input_map.py:54` (`J_UP`→`TEMPO_IDX`), `:55` (`J_DOWN`→`TEMPO_IDX`), `:58` (`J_A`→`SCALE_IDX`), `:59` (`J_B`→`DENSITY_IDX`) — **not** after the `OCTAVE_IDX` calls at `:56`/`:57`, which don't feed either formula. **`test_rom.py`**: add the `T20` suite (below). |
| **Implementation Tasks** | (1) Re-confirm `0xC068`/`0xC069` unclaimed by grep before writing (headroom last measured `07`-side at planning time; re-verify at execution time since the tree may have moved). (2) Add `AROUSAL`/`VALENCE`/`VALENCE_TABLE` to `music_engine.py`. (3) Write `_emit_mood_update`: `AROUSAL = TEMPO_IDX + DENSITY_IDX` (two `LD_A_nn`/`ADD_A_n`-family ops, no overflow risk — max `7+7=14`, fits in the required 0-15 range with headroom to spare); `VALENCE = VALENCE_TABLE[SCALE_IDX]` (a `LD_A_nn(SCALE_IDX)` then an indexed table read via the same pointer-table pattern `gbc_lib.py`'s existing note-lookup emitters already use — reuse, don't invent a new table-read idiom). (4) Wire the call into all 6 sites listed in Files to Create/Modify, each placed *after* that site's own input-changing write, per `GDS-09` §5's call-order contract (`FS-112`'s own Interfaces Used field states this explicitly — get it wrong and the recompute reads a stale pre-write value on that specific trigger, a defect `T20`'s per-site checks are designed to catch). (5) Add `T20` per Tests to Add. (6) Rebuild, run the full suite. |
| **Tests to Add** | New `test_rom.py` suite **`T20` — Emotional/Energy Layer**: (a) drive `TEMPO_IDX` to min/max (via repeated Up/Down taps) holding `DENSITY_IDX` fixed, assert `AROUSAL` is non-decreasing; same with `DENSITY_IDX` varied, `TEMPO_IDX` fixed (`FR-1390`). (b) drive `SCALE_IDX` through all 4 values (via A taps), assert `VALENCE` matches `VALENCE_TABLE[SCALE_IDX]` at each (`FR-1400`). (c) **all 6 trigger sites independently, not just one** — for each of Up/Down/A/B, tap once and assert `AROUSAL`/`VALENCE` reflect the new value on the same frame; drive to an empirically-derived song-form transition frame (reuse `T17`'s own derivation method) and assert `AROUSAL` reflects the new phase's `TEMPO_IDX`/`DENSITY_IDX` on that exact frame; drive Select and assert `AROUSAL`/`VALENCE` reflect the restored preset on the reset frame itself (`FR-1410`). (d) fresh boot, assert `AROUSAL`/`VALENCE` already correct on the first tested frame, before any input (`FR-1420`, boot half). (e) full regression — `T1`-`T19` still green. **Named limit, not glossed** (per `FS-112`'s own Risks field): every `T20` check computes its own expected value via the *same formula* this package implements (`TEMPO_IDX+DENSITY_IDX`, `VALENCE_TABLE[SCALE_IDX]`) — there is no independent consumer yet to check against, so a shared error in both the check and the implementation would not be caught. This is a real, accepted coverage gap, not an oversight; it closes once roadmap R9 gives this feature a real consumer with its own independent acceptance criteria. |
| **Documentation Updates** | `GDS-07` — add `AROUSAL`/`VALENCE` rows (`0xC068`/`0xC069`), update §6's headroom figure (84 bytes used, next free `0xC06A`). `Claude.md` — test count (→ ~135-ish across `T1`-`T20`; exact count once `T20`'s checks are finalized), WRAM quick-reference addition, a new Known Good Behavior entry naming this as infrastructure-only (no audible/visible change, consumer is future roadmap R9). `memory.md` — WRAM quick-reference table row. No `visuals.py`/`input_map.py` control-mapping documentation changes — nothing player-visible moved. |
| **Definition of Done** | `AROUSAL`/`VALENCE` are written correctly (per the formulas in Implementation Tasks) at all 6 trigger sites; `T20` exists and passes, with each of (a)-(e) exercised independently. Full suite passes (`T1`-`T20`). `visuals.py` untouched — confirmed by diff, not merely by intent. ROM builds to exactly 32768 bytes with a valid header. |
| **Verification Checklist** | ROM builds, exactly 32768 bytes, valid header (G5). Full `test_rom.py` suite passes including `T20` (G5). `09-package-verification` independently re-derives at least one `AROUSAL`/`VALENCE` value from a fixture of its own construction (the standing non-default-scenario convention, `VR-1070` through `VR-1110`) — given `T20`'s own named coverage limit (checks the same formula the implementation uses), verification should additionally **hand-compute** the expected `AROUSAL`/`VALENCE` for at least one non-trivial input combination independently of reading the implementation's own code, as the closest available substitute for an independent consumer. Verification should also confirm `visuals.py` is byte-for-byte unchanged (this package's own equivalence-adjacent claim, even though it isn't a refactoring package) since Module Responsibilities explicitly promises it stays untouched. |
| **Dependencies** | `FEAT-1010`/`FEAT-1020` (`VERIFIED`, shipped) — the input-steering and reset-to-preset behavior this package's 6 trigger sites hook into. No dependency on `FEAT-1080`/`1090`/`1100`/`1110`, confirmed per `FS-112`'s own Dependencies field. All dependencies `VERIFIED`, so this package is `READY`. |
| **Risks** | **The 6-site call-graph is more moving parts than a per-frame call would be** — `FS-112`'s own Risks field already names this: a future package adding a 7th way to write `TEMPO_IDX`/`DENSITY_IDX`/`SCALE_IDX` without also calling `_emit_mood_update` silently produces stale `AROUSAL`/`VALENCE`, with no test failure, since nothing currently consumes them to notice. Mitigation: `T20`'s per-site checks are this package's entire defense; any future package touching those 3 WRAM addresses should be flagged for a `T20` review during its own planning, not discovered later. **No-consumer-yet coverage gap** (Tests to Add) is inherent to this feature's scope, not a defect of this package's own execution — named, not hidden. **Formula choice is a first-guess, not tuned** — `VALENCE_TABLE`'s 4 entries are illustrative placement values, same `BL-0005`-class deferral as every other untuned preset/threshold this project has shipped; a future `09-content-review` pass, once R9 gives this a real consumer, is the right place to retune by ear/observation rather than guessing values now with nothing to judge them against. **ROM budget**: ~2 WRAM bytes + a 4-byte lookup table + a handful of instructions at 6 call sites, negligible against `GDS-07`'s measured headroom. |
| **Rollback Considerations** | Additive: 2 new WRAM bytes, 1 new routine, 6 new call sites, 1 new test suite. Reverting is a straightforward commit revert; no existing address, requirement, or behavior is modified — every trigger site's *own* existing write is unchanged, only a new call is appended after it. |
