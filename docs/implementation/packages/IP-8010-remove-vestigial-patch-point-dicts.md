# IP-8010 — Remove the Vestigial Patch-Point Dicts

| Field | Content |
|---|---|
| **Package ID** | `IP-8010` · `IP-8xx0` refactoring series · **Executor: `08-refactoring`** · cites `BL-0064` |
| **Objective** | Remove `build_engine_asm`/`build_input_asm`'s `-> dict` return type and their unused `patches = {}` construction — dead scaffolding inherited from the reference project, never populated, and already discarded by every caller. Purely structural: no behavior, no ROM byte, changes. |
| **Requirements Covered** | None. This package changes no observable behavior; no `FR`/`NFR` is implemented, satisfied, or affected. |
| **Architecture Components** | [`GDS-09` §3](../../architecture/09-interface-specification.md) — the finding this package executes on ("the contract should be either removed or made real, and removal is almost certainly right... a behavior-preserving code change, `08-refactoring` territory, `IP-8xx0`"). [`GDS-03` §1](../../architecture/03-architecture.md) (module write-scope; unaffected). |
| **Interfaces** | `build_engine_asm(rom)` and `build_input_asm(rom)` change signature from `(rom: ROM) -> dict` to `(rom: ROM) -> None` (or no annotation). `build_rom.py`'s call sites already call both as bare statements (`build_engine_asm(rom)` / `build_input_asm(rom)`, lines 87-88), discarding any return value — **no change needed at either call site**. No other file constructs or reads a `patches` dict anywhere in the tree (confirmed by the supersession sweep below). |
| **Files to Create/Modify** | **`music_engine.py`** — `build_engine_asm` (currently line 1123): drop `-> dict` from the signature, delete the `patches = {}` line (currently line 1126) and the `return patches` line (currently line 1287), leaving the function `return`-less (a bare fall-through, matching every other `build_*_asm` emitter in the codebase that returns nothing). **`input_map.py`** — `build_input_asm` (currently line 25): identical treatment (`patches = {}` at line 26, `return patches` at line 86). **No other file is touched** — `build_rom.py`'s call sites need no edit since they already discard the return value; verified, not assumed. |
| **Implementation Tasks** | (1) Capture the baseline per `08-refactoring`'s own Step 3: `Driftune.gbc`'s SHA-256 and the full `test_rom.py` check-name list, before the first edit. (2) In `music_engine.py`, remove `patches = {}` and `return patches` from `build_engine_asm`; update the signature and docstring (the docstring currently says "Returns a patch dict (unused for now, kept for parity with the reference project's build_game_asm return-shape convention)" — this sentence becomes false the moment the dict is removed and must be deleted or reworded, not left stale). (3) Identical treatment in `input_map.py`'s `build_input_asm` (no equivalent docstring sentence there — confirm before editing, don't assume symmetry). (4) Rebuild, diff the ROM hash against the baseline — **must be byte-identical**; any difference is this package's own regression, not an acceptable delta, and blocks completion. (5) Run the full suite; it must pass with the exact same check names as the baseline (a same-count-different-names suite is not equivalence, per `R310` §3). |
| **Tests to Add** | None. This package adds no new observable behavior for a test to assert on; the equivalence proof (byte-identical ROM + identical check-name set) *is* the verification, not a new `test_rom.py` check. Do not add a test asserting the dicts are gone — that would test an implementation detail, not a behavior, and the next refactor that touches these functions would have no reason to keep it green. |
| **Documentation Updates** | **None in this package's scope.** `GDS-09` §3 already documents this finding accurately and is not stale — it describes the vestigial contract as a *finding*, not as a live interface, and explicitly names "removal is almost certainly right" as its own recommendation; nothing there needs correcting once this ships, though `GDS-09` §3's own text could optionally note the removal happened (a `03-architecture-design-synthesis` edit, not this package's). **`GDS-03`'s "patch-point contract" language remains stale after this ships and is explicitly out of this package's scope** — `GDS-09` §3's own Merge decision already records that this correction "is this skill's own [`03`'s] to amend on a future pass," not a doc-scoped refactoring task. Routing it into this package would cross a design-ladder-document's content-ownership boundary that `08-refactoring`'s write scope (structure/meaning-preservation, never content decisions) does not extend to — a *description* of what the code does is a content claim `03` owns, not a structural artifact this skill restructures. **The six `FS-1xx` *Interfaces Used* fields that used to cite "patch-point dict keys" were already corrected in an earlier pass** (`BL-0066`, verified clean by grep before this package was authored — no `FS-1xx` file currently mentions "patch-point") — confirmed not stale, no action needed. |
| **Definition of Done** | `build_engine_asm`/`build_input_asm` no longer construct or return a `patches` dict; both docstrings/signatures reflect the change. ROM is **byte-identical** to the pre-refactor baseline (SHA-256 match). Full `test_rom.py` suite passes with the identical set of check names as the baseline. No other file was touched. |
| **Verification Checklist** | ROM builds, exactly 32768 bytes, valid header (G5). Full `test_rom.py` suite passes (G5). **Equivalence contract: byte-identical ROM** (SHA-256 hash match, pre- vs. post-refactor) — the default and only acceptable outcome for this package; any predicted delta would mean this isn't actually a refactor. `09-package-verification` independently rebuilds from a clean checkout and confirms the same hash the Implementation Summary reports, rather than trusting the reported hash. |
| **Dependencies** | None — `music_engine.py`/`input_map.py` exist and are stable; no `IP-xxxx` package is a prerequisite. Quiescence check (per `08-refactoring`'s Eligibility #3): confirm no other package is `IN PROGRESS` or `COMPLETE`-but-unverified touching `music_engine.py`/`input_map.py` before starting — `IP-9030` (this session's prior package) touched only `visuals.py`/`test_rom.py` and is `COMPLETE`, not overlapping. |
| **Risks** | Essentially none — this is the smallest possible category of refactor (deleting two dead local variables and a return statement, no logic touched, no label moved, no byte emitted or removed from the ROM itself since `patches` never reached `rom.data`). The only real risk is a false equivalence claim: if the ROM hash does *not* match after this change, that is a signal something else about the function was touched, not a deviation to explain away — stop and investigate rather than record a predicted delta. |
| **Rollback Considerations** | Trivial — revert the commit. No traceability, no address, no requirement is affected either way. |
