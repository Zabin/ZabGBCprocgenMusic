# IP-9020 — Overload threshold recalibration (remediation for `BL-0017`)

| Field | Content |
|---|---|
| **Package ID** | `IP-9020` |
| **Objective** | Recalibrate `OVERLOAD_THRESHOLD`/`ONSET_WINDOW_FRAMES` (`music_engine.py:56-57`) so `BAD_ZONE_FLAGS` bit2 (OVERLOAD) is actually reachable under realistic play, closing `BL-0017`. `VR-0007` computed the engine's own maximum possible onset rate at `≈8.8` onsets per 32-frame window (fastest tempo + max density simultaneously) against a threshold of `20` — structurally unreachable, not merely untuned. |
| **Requirements Covered** | `FR-1100` ("...sets `BAD_ZONE_FLAGS` bit2 (`OVERLOAD`) when the count exceeds the overload threshold within the window") |
| **Architecture Components** | GDS-03 §4c (overload detection), R204 (bad-zone heuristics grounding — the dissonance/stale thresholds there are already grounded per `BL-0005`/R204 SS5; the overload threshold was not part of that grounding pass and remains this package's own responsibility to justify) |
| **Interfaces** | None new — `OVERLOAD_THRESHOLD` and `ONSET_WINDOW_FRAMES` are existing module-level constants in `music_engine.py`'s threshold block (`:54-57`), read only by `_emit_badzone_tick` (`:466-483`) and consumed identically by `IP-0007`'s overload-driven reload-doubling (`:313-323`, `:375-383`) — no call-site changes needed anywhere, this is a pure constant-value change. |
| **Files to Create/Modify** | `music_engine.py` only — change `OVERLOAD_THRESHOLD` (currently `20`) and/or `ONSET_WINDOW_FRAMES` (currently `32`) so the ceiling `VR-0007` computed (`2×(ONSET_WINDOW_FRAMES/min_tempo_reload) + ONSET_WINDOW_FRAMES/(2×min_tempo_reload) + (ONSET_WINDOW_FRAMES/min_noise_step)×max_k`) exceeds the new threshold at realistic (not just maximum) settings — i.e. OVERLOAD should be reachable well before both tempo and density are simultaneously maxed, not only exactly at that corner. Recompute the ceiling at a few representative points (default preset, one notch above default, max) before picking the final constant, not just at the one extreme `VR-0007` used to *prove unreachability* — the target is "reachable during genuinely dense play," not merely "reachable in principle at the theoretical maximum." |
| **Implementation Tasks** | (1) Recompute the onset-rate ceiling formula (documented in `VR-0007`) across the tempo/density preset grid, not just the single max/max corner point. (2) Choose `OVERLOAD_THRESHOLD` (and, if the ceiling curve is too flat to give a good default-vs-max separation, `ONSET_WINDOW_FRAMES` too) so overload is reachable at high-but-not-maximal density/tempo combinations a player could plausibly reach through normal B/Up presses, while remaining implausible at the sparse default (density 0) — avoiding a threshold so low it fires constantly at default settings, which would be a new, opposite-direction defect. (3) Update the inline comment at `music_engine.py:56` (`"onset events within the ONSET_WINDOW_FRAMES window"`) to record the new value's justification (the recomputed ceiling), the same way `DISSONANCE_WEIGHT_BY_IC`'s comment cites its R204 grounding — so this constant doesn't silently become another `BL-0005`-style unexplained placeholder. |
| **Tests to Add** | Extend `test_rom.py`'s `T8` suite (or a small addition to `T10`) with a check that drives `DENSITY_IDX`/`TEMPO_IDX` toward their denser/faster end (not necessarily the absolute max — whatever the recalibrated threshold's own realistic reach point is) and asserts `BAD_ZONE_FLAGS` bit2 (`0x04`) is observed set at least once within a bounded frame budget — the direct regression guard `BL-0017`'s root cause (an untested, unreachable branch) was missing. Also confirm the default/sparse preset does *not* spuriously trigger OVERLOAD over a long run, guarding against the opposite failure mode task 2 warns about. |
| **Documentation Updates** | `docs/pipeline/backlog.md` (`BL-0017` → `DONE` once verified); no architecture/requirements doc changes needed (`FR-1100`'s text doesn't reference the specific threshold value, only the mechanism, which is unchanged). |
| **Definition of Done** | `BAD_ZONE_FLAGS` bit2 is empirically observed set within the new test's bounded frame budget at a realistic (not necessarily maximal) tempo/density combination; the default/sparse preset does not spuriously trigger it over an equivalently long run; every pre-existing test still passes; ROM still builds to 32768 bytes with a valid header. |
| **Verification Checklist** | ROM builds, exactly 32768 bytes, valid header (G5). Full `test_rom.py` suite passes, including the new check (G5). `09-package-verification` independently re-drives a realistic-but-non-maximal tempo/density combination live and confirms OVERLOAD triggers within a reasonable frame budget — not just trusting the new test's own fixture, per this project's tunable-parameter verification standard. |
| **Dependencies** | None blocking — pure constant change on top of already-`VERIFIED` `IP-0004`/`IP-0007` code. If sequenced after `IP-9010` per the TWBS's recommendation, no functional dependency exists between them (disjoint constants/regions) — the ordering is a session-hygiene recommendation, not a technical requirement. |
| **Risks** | Overcorrection risk (task 2's own warning): a threshold set too low could make OVERLOAD fire during ordinary play, constantly doubling note-timer reloads and audibly slowing the engine down in a way that reads as a new bug rather than the intended rare recovery behavior — the "does not spuriously trigger at default" test guards this, but the exact value still needs judgment, not just a formula. No ROM-budget impact (constant-only change, zero bytes added). |
| **Rollback Considerations** | Single-constant change (plus a documented comment and a test addition) — trivially revertible; no WRAM/interface impact. |
